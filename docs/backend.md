# Backend (`server/`)

Reference for working on the API. The source of truth is the code; routes and middleware per endpoint are in `src/routes/*.routes.ts`.

## Stack

- Node.js 24, Express 5 (`express@5.2.1`, `@types/express@5`), TypeScript, ESM (`"type": "module"`, `module: nodenext`)
- PostgreSQL through raw `pg` queries (no ORM), migrations with `node-pg-migrate`
- Auth: `jsonwebtoken` + `bcrypt` (10 salt rounds), JWT in an httpOnly cookie, `cookie-parser`, `cors`
- Uploads: `multer` (disk storage for logos, memory storage for CSV imports), CSV parsing with `csv-parse`. Scheduled work: `node-cron`
- Email: `nodemailer` for SMTP (Mailpit); Resend through its HTTP API with `fetch` (no SDK). See Emails.
- Tests: Vitest + supertest (see Testing)

Express 5 notes: `req.query` is a read-only getter (read it, never assign to it), and wildcard routes must be named (`/*splat`). Neither is used today.

## Scripts and environment

- `npm run dev`: `concurrently "tsc --watch" "node --watch dist/server.js"`. The server runs the compiled `dist/`, so run `npm run build` once on a fresh clone.
- `npm run build` (`tsc`), `npm start` (`node dist/server.js`)
- `npm run migrate up|down`, `npm run migrate create <name>` (loads `.env` with `dotenv run`, the CLI of the `dotenv` package)
- Env files: the npm scripts load them with `dotenv run -q -f <file> --` (the CLI of `dotenv` 18; `dotenv-cli` was removed because both packages install a `dotenv` binary). Variables already set in the environment win and `${VAR}` references are not expanded. At runtime `server.ts`, `seed` and `create-admin` load `.env` with `import "dotenv/config"` (quiet since dotenv 18, existing variables win), so on a host the dashboard's variables are used.
- `npm test` (Vitest + supertest, `.env.test`, files run one at a time; the full suite runs in CI, see CI below). Single file: `npm test -- tests/products.test.ts`. Single test: `npm test -- -t "name"`. Watch mode: `npm run test:watch`.
- `npm run typecheck`: `tsc --noEmit -p tsconfig.test.json` (source and tests).
- `npm run seed` (destructive reset, see Seed); builds first and runs from `dist/`.
- `npm run create-admin -- <email> <password> [first name] [last name]`: builds, then inserts an `ADMIN` account (same email and password rules as the API; a duplicate email is refused). Used for the first admin; later accounts are created in the app.
- Env: `DATABASE_URL`, `JWT_SECRET`, optional `PORT`, `NODE_ENV`, `CLIENT_ORIGIN` (allowed frontend origin for CORS and the origin check, default `http://localhost:5173`; a comma-separated list is allowed), `TRUST_PROXY` (number of proxy hops in front of the server, for `app.set("trust proxy")`; unset or 0 = off, which is right locally; Render needs `1`), `APP_TIMEZONE` (business time zone for `CURRENT_DATE` and cron, default `Europe/Sarajevo`), `DISABLE_RATE_LIMITS` (`true` turns the rate limiters off; only for the e2e server, never on a deployment), and the email variables `EMAIL_PROVIDER`, `EMAIL_FROM`, `EMAIL_REDIRECT_TO`, `RESEND_API_KEY`, `SMTP_HOST`, `SMTP_PORT` (see Emails). `.env.test` points at the separate database `food_saver_test_db`. `server/.env.example` lists every variable with comments (the only committed env file; `server/.gitignore` excepts it).

`tsconfig.json`: `strict`, `module/moduleResolution nodenext`, `target esnext`, `rootDir ./src`, `outDir ./dist`, `types: ["node"]`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `isolatedModules`, `declaration`, `sourceMap`, `include: ["src"]`. Migrations and tests live outside `src/`, so the build never emits them. `tsconfig.test.json` extends it with `rootDir: "."`, `noEmit`, `types: ["node", "vitest/globals"]` and includes `tests/`, so the tests are type-checked with the same strict options.

## Request pipeline (`app.ts`)

Order: `trust proxy` setting (from `TRUST_PROXY`) → `cors({ origin: allowedOrigins, credentials: true })` → `checkOrigin` → `/api` rate limit (`rateLimiters.api`) → `express.json()` → `req.body ??= {}` (Express 5 leaves it undefined for requests without a body; controllers destructure it) → `cookieParser()` → routers → `/uploads` static (with `X-Content-Type-Options: nosniff`) → JSON 404 for any unknown path (`"Route not found."`) → error handler (see Business logic).

Origin check (`middleware/origin.middleware.ts`), defence in depth against CSRF next to the `sameSite: "strict"` cookie: `allowedOrigins` is `CLIENT_ORIGIN` split on commas, parsed once at startup and shared with `cors()`. For `POST`, `PUT`, `PATCH` and `DELETE`, the `Origin` header (or, when it is missing, the origin of the `Referer`) must be one of them, otherwise 403 `"Request origin not allowed."` (an unparseable `Referer` is refused too). A request with neither header (non-browser clients, supertest) passes; `GET`, `HEAD` and `OPTIONS` are not checked. No CSRF token library is used.

Rate limits (`middleware/rateLimit.middleware.ts`, `express-rate-limit`): over the limit the answer is 429 `{ error: "Too many requests. Please try again later." }` with the standard `RateLimit`/`RateLimit-Policy` headers (draft-8) and `Retry-After`.

| Limiter | Where | Limit | Key |
|---|---|---|---|
| `api` | everything under `/api` | 1000 per 15 min | IP |
| `login` | `POST /api/auth/login` | 10 **failed** attempts per 15 min (a successful login gives its slot back) | IP + lowercased email |
| `password` | `PUT /api/users/me/password`, `PATCH /api/admin/users/:id/password`, `PATCH /api/company/branches/:id/password` | 10 per 15 min | user |
| `upload` | `POST /api/users/me/logo`, `POST /api/company/me/logo`, `POST /api/products/import` (one shared count) | 30 per hour | user |
| `forgotPassword` | `POST /api/auth/forgot-password` | 10 per hour; over it the answer is the **normal 200** and nothing is sent (not 429) | IP |

The per-user limiters run after `authenticate` and before multer, so a refused upload is never read. The general limit is far above normal use (notifications are polled every 50 s, a page loads several endpoints). Behind a proxy `req.ip` is the proxy's address unless `TRUST_PROXY` is set, and then every user would share one limit. The counters live in memory (one per limiter), which is right for one instance; more instances would need a shared store (for example Redis via `rate-limit-redis`). Under Vitest (`NODE_ENV=test`) the limiters are skipped, and so they are with `DISABLE_RATE_LIMITS=true` (the e2e server, see `docs/e2e.md`; the server logs a warning at startup when it is set); `tests/rateLimit.test.ts` mocks the module with `createRateLimiters(lowLimits, true)` and empties the counters after each test.

Routers: `/api/auth`, `/api/products`, `/api/orders`, `/api/cart`, `/api/users`, `/api/notifications`, `/api/favorites`, `/api/product-templates`, `/api/reports`, `/api/donations`, `/api/admin`, `/api/announcements`, `/api/credits`, `/api/dashboard`, `/api/stats`, `/api/cities`, `/api/company`

Routes chain `authenticate` → `authorize('<ROLE>', ...)` (one or more allowed roles) → controller. Every store/restaurant route names its roles (`authorize('STORE', 'RESTAURANT')` where both are allowed), so an `ADMIN` reaches only `/api/admin`, `/api/notifications`, `GET`/`PUT /api/users/me` and `/api/auth`. The admin router applies `authenticate, authorize('ADMIN')` to all of its routes with `router.use`. A `COMPANY` (headquarters) user reaches only `/api/auth`, `GET`/`PUT /api/users/me`, `PUT /api/users/me/password`, `/api/notifications`, `/api/announcements`, `GET /api/stats/impact`, `GET /api/cities` (its branches' cities) and `/api/company`; every store, restaurant, admin and `/api/credits` route rejects it with 403 through its `authorize` list (its branches' credits are under `/api/company`).

## Auth

- `register`: kept for the planned public roles (individuals, public kitchens, humanitarian organizations), none of which exists yet (`PUBLIC_ROLES` is empty). It validates first_name, last_name, email, password and role first, then answers 403 `"Store and restaurant accounts are created by an administrator."` for `STORE`, `RESTAURANT`, `ADMIN` and `COMPANY` and 400 `"Role is not valid."` for anything else. Store, restaurant and admin accounts are created by an admin (`POST /api/admin/users`, with an invitation email or a temporary password).
- `login`: bcrypt compare; a blocked account (checked only after the password matched, so a block is not revealed to someone without the password) gets 403 `"Your account is blocked. Reason: <reason>"` and no cookie. The **effective block** applies: the account's own block (with its reason) comes first, otherwise a blocked company blocks its users with the company's reason, and a deactivated branch gets 403 `"This branch has been deactivated. Contact your company."`; `setSessionCookie` (`utils/session.ts`): `jwt.sign({ id, role, sv: session_version }, JWT_SECRET, { expiresIn: "7d" })`, sets cookie `token` (`httpOnly`, `secure` only when `NODE_ENV === "production"`, `sameSite: "strict"`, 7-day `maxAge`). Returns `{ message, user: { id, first_name, last_name, email, role } }`. Wrong email and wrong password return the same message.
- `logout`: `clearCookie` with the same options. `GET /auth/me` returns only the token payload (`{ id, role }`); the client uses `GET /users/me` for full data.
- `authenticate`: reads `req.cookies.token`, `jwt.verify`, rejects non-object payloads, then reads `users.role`, the effective block (`NOT notBlocked("users")`: the user's own flag or its company's) and `users.must_change_password` for the token's id (one query per request). A missing user, or a token whose `sv` differs from `users.session_version` (a token without `sv`, from before session versions, counts as 0), is 401 `"Token is invalid or has expired."`: raising the version (a password reset) signs out every session of the user; a blocked one 401 `"Your account is blocked."` (so blocking an account or its company ends a session at once). While `must_change_password` is set (a temporary password from an admin), only `GET /api/auth/me`, `GET`/`PUT /api/users/me`, `POST /api/users/me/logo`, `PUT /api/users/me/password` and `GET /api/cities` (for the profile form) pass (`ALLOWED_BEFORE_PASSWORD_CHANGE`, matched on method + path without the query string); everything else is 403 `"You must change your password before continuing."`. This also applies to an existing session once an admin resets the password. The login response includes `must_change_password`. `req.user` (`AuthUser = JwtPayload & { id: number; role: Role }`, `Role = 'STORE' | 'RESTAURANT' | 'ADMIN' | 'COMPANY'`) takes the role from the database, not from the token. Other failures are 401; a database error is 500.
- **Forgot password** (`password.controller.ts`, no session): `POST /forgot-password { email }` (rate limiter `forgotPassword`): a malformed email is 400 `"Email is not valid."`; otherwise the answer is always 200 `{ message: "If an account exists for this email, we sent a link to set a new password." }` (`FORGOT_PASSWORD_MESSAGE`), whether the account exists, is blocked (also a blocked company or a deactivated branch) or is over its limit, so it reveals nothing. For an active account with fewer than 3 reset tokens in the last hour (`RESET_LINKS_PER_HOUR`, counted in `auth_tokens`, so it holds across restarts and instances) it creates a `PASSWORD_RESET` token, queues the system email `PASSWORD_RESET` and logs `PASSWORD_RESET_REQUESTED` with the IP, in one transaction. `POST /reset-password/check { token }`: 200 `{ message: "The link is valid.", purpose }` or 400 `{ error: "This link is invalid or has expired.", code: "INVALID_LINK" }` (the page checks first, so the user does not type a password for nothing). `POST /reset-password { token, password }`: the password rule (400 with the usual message, the token stays usable), then in one transaction the token is locked (`FOR UPDATE`; two requests with one token: one wins, the other gets `INVALID_LINK`), the password hash set, `must_change_password` cleared and `session_version` + 1 (every session signed out), the token used and the user's other open tokens revoked, a `PASSWORD_CHANGED` notification (its email is a system email) and the account event `PASSWORD_RESET`. An `INVITATION` token is accepted the same way (password, flags, session version, token), but with no `PASSWORD_CHANGED` notification, the event `INVITATION_ACCEPTED` and `last_login_at` set, and the user is signed in at once (`setSessionCookie` with the new version): `{ message: "Your password was set. Welcome to FoodWise.", purpose: "INVITATION", user }` (the user as in the login response). For a reset the response clears this browser's cookie and answers `{ purpose: "PASSWORD_RESET", message: "Your password was changed. You can log in now." }`.
- **Tokens** (`services/authTokens.ts`, table `auth_tokens`): 32 random bytes as base64url (43 characters) go only into the email; the table stores `hashToken` (SHA-256, hex). `createAuthToken(db, userId, purpose, createdBy?)` revokes every open token of the user (any purpose) and stores the new one with `expires_at = NOW() + TOKEN_LIFETIME_MINUTES[purpose]` (`PASSWORD_RESET`: 60, `INVITATION`: 72 × 60). `services/accountEmails.ts`: `sendPasswordResetLink(client, userId, senderId?)` and `sendInvitation(client, userId, senderId, sender = "ADMIN")` (`sender` `COMPANY` when a headquarters invites a branch) create the token and queue its system email in the caller's transaction. `findValidToken(db, token, lock?)` finds it unused, unrevoked, unexpired and with an unblocked user (anything else, also a malformed or 200+ character token, is null). `consumeToken` sets `used_at` and revokes the user's other open tokens.
- `authorize(...roles)`: 403 with "You do not have the required role for this action." when the caller's role is not one of them (`authorize('STORE')`, `authorize('STORE', 'RESTAURANT')`).
- Controllers read `req.user!.id` (non-null assertion is safe because `authenticate` runs first).

## Database

Enum types: user role (`STORE`, `RESTAURANT`, `ADMIN`, `COMPANY`), admin action (`CREATE_USER`, `RESET_PASSWORD`, `BLOCK_USER`, `UNBLOCK_USER`, `REMOVE_PRODUCT`, `REMOVE_DONATION`, `CANCEL_RESERVATION` (no longer written), `CANCEL_ORDER`, `UPDATE_PROFILE`, `CREATE_ANNOUNCEMENT`, `END_ANNOUNCEMENT`, `APPROVE_CREDIT_REQUEST`, `REJECT_CREDIT_REQUEST`, `ADJUST_CREDITS`, `CREATE_COMPANY`, `UPDATE_COMPANY`, `BLOCK_COMPANY`, `UNBLOCK_COMPANY`, `DEACTIVATE_BRANCH`, `REACTIVATE_BRANCH`, `ATTACH_BRANCH`, `SEND_INVITATION`, `RESEND_INVITATION`, `SEND_PASSWORD_RESET_LINK`), the credit enums (`subscription_status`, `credit_transaction_type`, `credit_actor`, `credit_request_type`, `credit_request_status`, `credit_request_source`; values in the table below), announcement audience (`ALL`, `STORE`, `RESTAURANT`), product status (`Available`, `Sold`, `Expired`, `Removed`), reservation status (the **item** status: `Pending`, `Confirmed`, `Completed`, `Rejected`, `Cancelled`). `Rejected` = refused by the store; `Completed` = picked up (set by the store); `Cancelled` = withdrawn by the restaurant, cancelled by the expiry job, moderation, a block or a closed branch, or by the store after a missed pickup. The order enums: `order_status` (the same five values, derived from the items, see Orders), `fulfilment_method` (`PICKUP`; phase 2 adds `DELIVERY`), `order_change_reason` (`NOT_ENOUGH_STOCK`, `QUALITY`, `OTHER`), `order_event_source` (`RESTAURANT`, `STORE`, `ADMIN`, `SYSTEM`). Donation type (`FREE`, `SPONSORED`) and donation status (`Available`, `Expired`, `Removed`; claim and funding statuses come with the recipient roles). Category and unit are stored as codes in VARCHAR columns (validated against fixed lists, see Validation); labels are a frontend concern.

`DATE` columns (`expiry_date`) come back from `pg` as plain `YYYY-MM-DD` strings: `config/db.ts` overrides the default parser, which would turn them into a JS `Date` at local midnight and serialize the previous day in UTC+ time zones. Every pool session also runs with `timezone = APP_TIMEZONE`, so `CURRENT_DATE` is the local business day.

#### CSV import

- `uploadCsvFile` (multer memory storage, nothing is written to disk) accepts one file in field `file`, at most 1MB (`MAX_CSV_SIZE_MB`), with a `.csv` extension and a MIME type of `text/csv`, `application/csv`, `application/vnd.ms-excel`, `text/plain` or `application/octet-stream` (browsers disagree on the type of a .csv). Otherwise 400 `"Only CSV files are allowed."` / `"The file can be at most 1MB."`; no file → 400 `"A CSV file is required."`. Logo and CSV uploads share the `handleUpload` wrapper, which turns multer errors into 400 JSON.
- `utils/productCsv.ts` → `parseProductCsv(buffer)`: columns `name, description, category, original_price, discounted_price, quantity, unit, expiry_date` (`CSV_COLUMNS`; header names are trimmed and lowercased, order does not matter, `description` is optional). The delimiter (`,` or `;`) is read from the header line, so a `;` file can use an unquoted decimal comma. A UTF-8 BOM is skipped and empty lines are ignored. Values are normalized before `validateProductFields`: `2,50` → `2.50`, and the expiry date → `YYYY-MM-DD` from any form Excel writes when it saves a CSV (a cell longer than 40 characters is left as it is and rejected, before the time-part patterns, which would backtrack on long input): a time part (`T...`, ` 00:00:00`, ` 12:00 AM`), spaces and a trailing dot are dropped, then `YYYY-M-D` / `YYYY.M.D` / `YYYY/M/D` (year first), `D.M.YYYY` / `D-M-YYYY` (day first, also with a 2-digit year → `20YY`), `A/B/YYYY` (day first, unless some slashed date in the same file only works month first, like `12/25/2026`; then the whole file is read as US `M/D/YYYY`), and a 5-digit Excel serial (days since 1899-12-30). Anything else is left as is, so the validator rejects it. Category and unit are the server codes (`Meat`, `kg`).
- File-level errors (400): `"The CSV file could not be read."` (e.g. an unclosed quote), `"The CSV file does not contain any products."`, `"The CSV file is missing columns: ..."`, `"The CSV file can contain at most 500 products."` (`MAX_CSV_ROWS`).
- All or nothing: every row is validated first. If any fails, the response is 400 `{ error: "The CSV contains invalid rows.", rowErrors: [{ row, error }] }` (`row` is the line number in the file, header = 1) and nothing is inserted. For an invalid date the row error quotes the raw value: `Expiry date is not valid: "<value>". Use the format 31.12.2026.` (the plain `POST /` message is unchanged). Otherwise all rows are inserted in one transaction.

### Validation

- `utils/validateProduct.ts`: `validateProductFields` (create and update) returns an English error string or `null`:
  - required: name, category, original_price, discounted_price, quantity, unit, expiry_date (description optional) → `"All fields are required."`
  - category and unit must be in `CATEGORIES` / `UNITS` (keep in sync with `client/src/utils/categories.ts` and `units.ts`) → `"Category is not valid."`, `"Unit of measure is not valid."`
  - prices and quantity must be numbers above 0 → `"Prices and quantity must be positive numbers."`
  - discounted_price may not exceed original_price → `"Discounted price cannot be higher than the original price."`
  - expiry_date must be a real `YYYY-MM-DD` date → `"Expiry date is not valid."`, and not before today in `APP_TIMEZONE` → `"Expiry date cannot be in the past."`
- `validateTemplateFields` applies the category/unit lists and checks optional numbers when they are given.
- `utils/params.ts`: `parseId` (positive integer or `null`), `parseNumber`, `parseNonNegativeInt`. A non-numeric `:id` returns the resource's normal 404 instead of a Postgres cast error.
- `utils/dates.ts`: `APP_TIMEZONE`, `todayInAppTimezone()`, `isValidDate`, `isValidDateTime`.

Body: `{ items: [{ item_id, action: "ACCEPT" \| "ACCEPT_LESS" \| "REJECT", quantity?, reason?, note?, record_shop_sale? }] }` with every Pending item exactly once, or `{ reject_order: true, reason, note?, shop_sales?: [{ product_id, quantity }] }`. 400: not Pending `"Only pending orders can be accepted or rejected."`; items missing, repeated, unknown or an unknown action `"Decide every item of the order."`; partial off and anything but all `ACCEPT` or `reject_order` `"This order must be accepted in full or rejected."`; `ACCEPT_LESS` quantity not above 0 or not below ordered `"The accepted quantity must be more than zero and less than ordered."`; a reduction or rejection without a valid reason `"Choose a reason."`; `OTHER` without a note, or any note over 300 characters, `"Describe the reason (at most 300 characters)."`; a shop sale without `NOT_ENOUGH_STOCK`, not above 0 or above what the decision frees `"The amount sold in the shop is not valid."`; an accepted item of an expired product `"An expired product cannot be accepted."`. Then the items get `Confirmed` (with the accepted quantity) or `Rejected`, `decided_at`, reason and note; shop sales are inserted with `order_id`; `markSoldIfFullyConfirmed` per product; `syncOrderStatus`; the restaurant gets `ORDER_ACCEPTED`, `ORDER_PARTIALLY_ACCEPTED` (anything reduced or rejected) or `ORDER_REJECTED`. `{ message: "Order decision saved.", order }`. |
| `POST /:id/cancel` | RESTAURANT | Pending only (400 `"Only pending orders can be cancelled."`): every item `Cancelled`, the store gets `ORDER_CANCELLED`. `{ message: "Order cancelled.", order }`. |
| `POST /:id/complete` | STORE | Confirmed only (400 `"Only accepted orders can be marked as picked up."`): the Confirmed items `Completed` with `picked_up_at`, the order's `picked_up_at`, `ORDER_COMPLETED`. `{ message: "Order marked as picked up.", order }`. |
| `POST /:id/cancel-overdue` | STORE | Confirmed and the pickup day has passed (400 `"Only overdue pickups can be cancelled."`): the Confirmed items `Cancelled`, `releaseSoldProduct` per product, `ORDER_PICKUP_MISSED`. `{ message: "Overdue order cancelled.", order }`. |

**The service** (`services/orders/`):
- `codes.ts`: `generateOrderCode` (4 characters of `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` with `crypto.randomInt`), `formatOrderCode` (`#K7PM`), `parseOrderCode` (search input), `insertOrder` (`ON CONFLICT (store_id, code) DO NOTHING`, at most 10 draws).
- `status.ts`: `deriveOrderStatus` (any item Pending → Pending, else Completed, else Confirmed, else Rejected, else Cancelled), `syncOrderStatus(client, orderId, { source, actorId, reason })` (stores the derived status and writes the history row when it changed), `recordOrderCreated`, `recordItemChanges`, `lockOrder` (with `is_overdue`), `lockOrderItems` (the items with their products locked in ascending id), `moveItems`.
- `cascades.ts`: `cancelPendingOrders(client, where, values, recipient, { storeClosed })` cancels whole Pending orders matching a condition on `orders` (blocking a user or company, deactivating a branch; source `SYSTEM`) with one notification per order (`ORDER_CANCELLED_BY_ADMIN` or `ORDER_CANCELLED_STORE_CLOSED`); `lockOrdersHoldingProducts` and `cancelPendingItemsOfProducts(client, orders, productIds, "EXPIRED" | "REMOVED", event)` drop the Pending items of expired or removed products: an order with partial fulfilment off, or with nothing left, is cancelled whole; the restaurant gets `ORDER_ITEMS_EXPIRED`/`ORDER_EXPIRED` or `ORDER_ITEMS_REMOVED`/`ORDER_CANCELLED_BY_ADMIN`.
- `actions.ts`: `cancelOrder`, `completeOrder`, `cancelOverdueOrder`, `adminCancelOrder` (the caller logs the admin action).
- `queries.ts`: the lists, counts and details above.
- **Locking:** every order path locks the order(s) first (ascending id), then the products (ascending id), then the store's subscription. Paths that start from products (expiry, moderation) lock the affected Pending orders first (`lockOrdersHoldingProducts`).
- `queries.ts` also serves the admin (`listAdminOrders`, and `getOrderDetails(orderId, null)`, which skips the party check) and the headquarters (`listStoreOrders` for a branch). Nothing reads `reservations.pickup_date` any more; the insert still writes it until orders PR 6 drops the column.

### Cart `/api/cart` (RESTAURANT)

`controllers/cart.controller.ts` over `services/cart.ts` (design: `docs/orders-design.md`, section 4). Every success answers the whole cart as `{ message, cart }`: `{ store: { id, business_name } | null, items, totals: { lines, total }, pending_orders, max_pending_orders }`. Each line has the product fields (`product_id`, `name`, `category`, `unit`, `expiry_date`, `original_price`, `discounted_price` (current)), `quantity`, `unit_price_seen`, `available_quantity` ("0" when unavailable), `added_at` and `flags`: `unavailable` with `unavailable_reason` (`REMOVED`, `EXPIRED`, `STORE_UNAVAILABLE` (blocked, its company blocked, a deactivated branch), `SOLD_OUT` (Sold or nothing free), checked in that order), `quantity_exceeds` (free < the line's quantity), `price_lowered` and `price_raised` (the current price against `unit_price_seen`, in cents). `totals.total` is what would be sent now: available lines without a higher price, at most the free quantity, at the current price. Lines come in the order they were added.

| Endpoint | Behavior |
|---|---|
| `GET /` | The cart. `"Cart fetched successfully."` |

### Users `/api/users`
- `GET /me`: full profile (explicit column list, never `password_hash`), including `must_change_password`, `company_id`, `company_name`, `company_logo_url` (the company's logo; a `COMPANY` user's avatar, and a branch's when it has none) and `company_description`. `logo_url` and `description` are the user's own (not resolved).

Required: first_name, last_name, business_name, city_id, address, phone (400 `"First name, last name, business name, city, address and phone are required."`). `city_id` (a number or a numeric string) must be a city from the list, otherwise 400 `"Invalid city."`. The response's `user` has `city_id` and `city` (the name; `CITY_NAME` in `utils/cities.ts`, a subquery, because `RETURNING` cannot join). The other fields use `COALESCE`, so they cannot be cleared back to null. For an `ADMIN` only `first_name` and `last_name` are read (both required, 400 `"First and last name are required."`); the response has `id, first_name, last_name, email, role`. For a `COMPANY` user only `first_name`, `last_name` and `phone` (all required, 400 `"First name, last name and phone are required."`); the response adds `phone` and `company_id`. Business fields in the body are ignored. A **branch** (STORE with `company_id`) cannot change its own `business_name` or `city_id`: `updateUser` passes `{ lockBranchFields: true }`, which replaces them with the stored values (like `logo_url` is ignored in the admin edit), so only its headquarters (`PUT /company/branches/:id`) or an admin (`PUT /admin/users/:id/profile`) change them. An empty `description` is stored as `""`, which counts as none (see Branding).
- `DELETE /me/logo` (STORE, RESTAURANT): clears `logo_url` and deletes the file. 200 `{ message: "Logo removed." }`. A branch then shows its company's logo again.
- `PATCH /me/email-notifications` (any role, admins and headquarters included): body `{ enabled: boolean }` (anything else → 400 `"Email notifications must be turned on or off."`). Sets the caller's `email_notifications` and answers `{ message: "Email notifications turned on." | "Email notifications turned off.", email_notifications }`. `GET /me` returns `email_notifications`.
- `PUT /me/password` (any role): body `current_password`, `new_password`. 400 `"All fields are required."`, `"Current password is incorrect."` (bcrypt compare), the password-length message, `"The new password must be different from the current one."`. Stores the new hash and clears `must_change_password`. 200 `{ message: "Password changed." }`. Repeating the new password is checked on the client.
- `POST /me/logo` (STORE, RESTAURANT): `uploadLogoFile` (multer, single file field `logo`, JPEG/PNG/WEBP, max 5MB) stores `/uploads/logos/<userId>-<timestamp>.<ext>` in `logo_url` (a `COMPANY` user's company logo, `POST /api/company/me/logo`, is named `company-<userId>-<timestamp>.<ext>`). The extension comes from the checked MIME type, never from the uploaded file name, and `/uploads` is served with `nosniff`, so an uploaded file can only ever be an image. The previous logo file is deleted. Rejected uploads answer 400 JSON: `"Only JPEG, PNG and WEBP images are allowed."`, `"The image can be at most 5MB."`; no file: `"No image was uploaded."`.
- `GET /stores` (RESTAURANT): store list without blocked stores and stores that have no `business_name` yet; filters `city_id` (see the products filter), `business_name`, `favorites=true` (only the caller's favorite stores; an empty value means no filter, anything else → 400 `"Invalid filter."`), `radius` (as on `GET /products`). Each store has `distance_km`. `sort`: `distance` (default: nearest first, then by name) or `name` (by name only); anything else → 400. Paged (default 12, `{ message, stores, total, outside_radius_count }`). Each store has `active_products` (COUNT, a string): its `Available` products with `expiry_date >= CURRENT_DATE`.
- `GET /stores/:id` (route: STORE, RESTAURANT; the controller returns 403 for STORE, so in practice restaurants only; 404 for a blocked store): returns `{ store, stats, myOrders }`. The store's offers are paged through `GET /products?store_id=` (available, unexpired, with stock left). `stats` = `sold_articles` (count of products with status Sold that restaurants bought some of: an accepted or picked-up item) and `successful_orders` (count of the store's picked-up, i.e. `Completed`, orders). `myOrders` = `{ my_orders_count }`, the calling restaurant's `Completed` orders at this store. Pending, Confirmed (not picked up yet), Rejected and Cancelled are not counted.

### Dashboard `/api/dashboard` (STORE, RESTAURANT)
`GET /stats` (`dashboard.controller.ts`): the dashboard stat cards over all of the caller's data, all numbers, `{ message, stats }`. The counts are **orders**: `pending_orders` waiting for the store's decision, `successful_orders` accepted (Confirmed + Completed; the "Prihvaćene narudžbe" card). Food saved and savings sum the picked-up (`Completed`) **items** with their accepted quantities.
- Store: `{ active_products, pending_orders, successful_orders, saved: { kg, l, pieces } }`. `active_products` counts its products with status `Available` (no expiry check, the midnight job sets `Expired`). Orders are those with `orders.store_id` = the store; `saved` sums `Completed` item quantities on its products by the product's unit: kg + g/1000 → kg, l + ml/1000 → l, kom + pak → pieces (the impact report's rules).
- Restaurant: `{ pending_orders, successful_orders, savings }`, its own orders; `savings` = Σ (the product's **current** `original_price` − `unit_price`) × quantity over its `Completed` items, not clamped. The "available offers" card uses the `total` of `GET /products` (sent with `radius=10`; when that radius has fewer than 3 offers the client asks 20 km, then 50 km, then all cities to fill the soonest-expiring list, and the card shows the total of the widest radius asked for).
- An account without data gets zeros. ADMIN → 403.

### Nearby offers (radius and distance)
Restaurants see offers and stores near their own city first. Rules (`GET /products` and `GET /users/stores`):
- **Distance** = `city_distance_km(from_city, to_city)`, a SQL function (migration `add-city-distance-function`): the straight-line (Haversine, R = 6371) distance in **whole km** between the two cities' centres, not addresses, so the same city is 0 and 5 km usually means the own city. NULL when either id is null or unknown. It is the one place the formula lives; queries build the call with `cityDistance(from, to)` from `utils/cities.ts` (later features such as branches and donations reuse it). From Visoko: Breza 7, Ilijaš 9, Kakanj 16, Sarajevo 24, Zenica 32.
- The starting point is the **restaurant's** `city_id` (`userCityId`), passed as a parameter. A store calling `GET /products` gets `distance_km` null and no radius.
- **Radius** (`parseRadius`): 5, 10, 20 or 50 km or `all`; missing = 10 (`DEFAULT_RADIUS`). Rows farther than the radius are left out, and `outside_radius_count` counts the rows that match every other filter but lie beyond it (a second COUNT with `>` instead of `<=`).
- The radius is **not applied** (and `outside_radius_count` is 0) with `radius=all`, a `city_id` filter (choosing a city is explicit), `store_id` (a store's profile shows all its offers), `favorites=true` on the store list, or when the restaurant has no city yet.
- Several stores in range (e.g. later two branches of a chain) all show, sorted by distance.

### Reports `/api/reports` (STORE, RESTAURANT)
Downloadable CSV reports. Both cover only **Completed** order items whose `picked_up_at::date` is between `from` and `to` (local day, the session runs in `APP_TIMEZONE`). Ownership is `pickupOwnership(role)` in `services/reports.ts`: a store gets the items on its products, a restaurant its own; `parties` is the other side.
- Query: `from`, `to` (`YYYY-MM-DD`, required, `from <= to`, at most 366 days including both ends; otherwise 400 `{ error: "Invalid period." }`) and optional `lang` (`en`; anything else means `bs`) for the column headers, category labels, the total label and the file name. Reports are files read outside the app, so they follow the UI language rather than the English-only rule for server text.
- Success: 200 with `Content-Type: text/csv; charset=utf-8` and `Content-Disposition: attachment; filename="<name>-<from>-<to>.csv"` (not the usual JSON). Errors stay JSON; 500 `"An error occurred while generating the report."`.
- `GET /sales`: one row per picked-up item, ordered by `picked_up_at`, then order and item: pickup date, the order's code (`#K7PM`, column "Narudžba" / "Order"; the items of one order share it), product, category label, other party (`business_name`, else first + last name, else email), its city, quantity, unit, `unit_price`, the product's **current** `original_price` (there is no snapshot of it), total (`unit_price × quantity`), savings (`(original_price − unit_price) × quantity`, never negative). Last row: totals of the two money columns (quantities have mixed units). File name `prodaja`/`sales` for a store, `kupovine`/`purchases` for a restaurant.
- `GET /impact`: one row per month (`YYYY-MM`) plus a total row (`GROUPING SETS`, so partners are counted once over the whole period): pickups (distinct **orders**: an order with three items is one pickup), distinct partners (restaurants for a store, stores for a restaurant), food in kg (g/1000), l (ml/1000) and pieces (kom + pak) like the dashboard's food-saved card, value and savings in KM. An empty period still has the total row with zeros. File name `uticaj`/`impact`.
- `utils/csv.ts` → `toCsv(headers, rows)`: UTF-8 BOM, `;` delimiter, CRLF, integers as they are and other numbers with two decimals and a decimal comma (`2,50`), so Bosnian Excel splits the columns and reads the numbers; cells with `;`, `"` or a line break are quoted; text starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'` (CSV formula injection: product and business names are user input). `utils/reportLabels.ts` holds the headers and category labels per language.
- The queries and helpers are shared with the company reports (`services/reports.ts`): `parsePeriod`, `sendCsv`, `salesRows(scope, owner, period, lang, { withBranch })` and `impactRows(scope, owner, period, lang)`, where a `PickupScope` is `{ owner, partyJoin }` (`pickupOwnership(role)` here, `storesScope()` for a set of store ids), plus `IMPACT_COLUMNS`, `PICKED_UP_IN_PERIOD` and `impactCells`.
- Adding a report: a query in `services/reports.ts` (or the controller), its headers in `reportLabels.ts`, a route, and an entry in the client's `REPORTS` list (for a company report: `companyReports.controller.ts` and `CompanyReportsPage`).

### Donations `/api/donations` (STORE and RESTAURANT)
Donation offers of the humanitarian module. `FREE` = given away; `SPONSORED` = given at `donation_price`, which a third party will pay. Until the recipient roles exist, a donation is visible only to its donor (`donor_id = req.user.id`).
- `POST /`: create; `donor_id` from `req.user`. 201 `{ message: "Donation published successfully.", donation }`.
- `GET /mine`: own donations except `Removed`, `Available` first, then newest. Filters `type`, `status` (`Available`/`Expired`), `name` (ILIKE); anything else → 400 `"Invalid filter."`. Paged (default 12): `{ donations, total }`, each with `days_until_expiry`.
- `GET /:id`: own and not removed, else 404 `"Donation not found."`.
- `PUT /:id`: same body as create. 404, 403 `"You are not allowed to edit this donation."`, 400 `"Only active donations can be edited."` unless `Available`. 200 `{ message: "Donation updated successfully.", donation }`.
- `DELETE /:id`: soft delete (`Removed`), any status. 404, 403 `"You are not allowed to delete this donation."`, 200 `{ message: "Donation deleted." }`.
- `POST /from-product/:productId` (STORE only, "Prebaci u donaciju"): body `donation_type`, optional `quantity` (default: everything available), `donation_price` (SPONSORED). Stock-safe transaction with `FOR UPDATE` on the product. 404 `"Product not found."` (also for `Removed`), 403 `"You are not allowed to donate this product."`, 400 `"Only available products can be moved to donations."` (not `Available` or expired), 400 `"Quantity must be greater than zero."`, 400 `"Not enough product available."` when it exceeds `quantity − Pending − Confirmed − Completed`. The donation copies name, description, category, unit, `original_price` and `expiry_date` and stores `source_product_id`. A repeated move adds to the product's `Available` donation with the same `donation_type` and `donation_price` (locked `FOR UPDATE`): its quantity grows and the response is 200 `{ message: "Quantity added to the existing donation.", donation }`; a different type or price, or an earlier donation that expired or was deleted, gives a new donation. Then: nothing reserved and everything donated → product `Removed` and `refundForProduct` (its credit back on the day of the charge); otherwise `products.quantity` drops by the donated amount (reservations keep theirs), `markSoldIfFullyConfirmed` may mark it `Sold`, and the credit stays spent. 201 `{ message: "Product moved to donations.", donation, creditRefunded }` (also on the 200 merge response).
- `POST /:id/return-to-product` (STORE only, undoes a move): one transaction that locks the donation and then its source product. 404 `"Donation not found."` (missing or `Removed`), 403 `"You are not allowed to edit this donation."`, 400 `"Only active donations from the offer can be returned."` (not `Available`, or no source product), 400 `"Product has expired and cannot be returned to the offer."`. The product becomes `Available` (also from `Sold` or `Removed`); its quantity grows by the donation's quantity, except for a `Removed` product, which kept its old quantity when everything was moved and is rebuilt as Pending + Confirmed + Completed + sold in shop + the donation's quantity (so exactly the donation becomes free again). The donation becomes `Removed`. A product that was `Removed` is published again and costs 1 credit (`chargeForProduct`; 402 rolls the whole return back), unless its last charge was never refunded (`hasOpenProductCharge`: the move came after the charge day), in which case that charge still covers it; returning to a product that stayed on offer is free. 200 `{ message: "Donation returned to the offer.", product }`.

Validation (`utils/validateDonation.ts`, `validateDonationFields` + `normalizeDonationFields`):
- Required: donation_type, name, category, quantity, unit, original_price, expiry_date → `"All fields are required."`. Category in `DONATION_CATEGORIES` (product categories + `Meals`), unit in `DONATION_UNITS` (product units + `portion`) → the product messages. Quantity and value above 0 → `"Quantity and value must be positive numbers."`.
- `validateDonationPrice` (also used by from-product): unknown type → `"Donation type is not valid."`; SPONSORED needs a price above 0 → `"Donation price is required and must be greater than zero."` and below the value → `"Donation price must be lower than the product's value."`. A FREE donation's price is stored as NULL.
- Expiry date as for products. Pickup times `HH:MM[:SS]` → `"Pickup time is not valid."`, start before end → `"Pickup start must be before pickup end."`.
- `allergens` must be codes from `ALLERGENS` (the 14 EU allergens) → `"Allergens are not valid."`; `serving_temperature` one of `HOT`, `COLD`, `FROZEN` → `"Serving temperature is not valid."`. Both are stored only for `Meals` and cleared otherwise.
- Keep the lists in sync with `client/src/utils/donations.ts`.

### Admin `/api/admin` (ADMIN)

| Endpoint | Behavior |

### Credits `/api/credits` (STORE)
Only stores pay credits: restaurants order for free, so the router allows only `STORE` (a restaurant gets the role 403).
Controller `credits.controller.ts`. Payment is offline, so every subscription and top-up is a request an admin approves. User responses never contain `admin_note` (`CREDIT_REQUEST_COLUMNS` leaves it out). A request row: id, user_id, request_type, plan_id, topup_package_id, period_month, auto_renew, status, source, created_at, reviewed_at, requested_by, company_note, company_reviewed_at, plan_name, credits, price. The request rules live in `services/creditRequests.ts`, shared with the headquarters' endpoints.

**Branches** (a STORE with `company_id`, `getManagingCompany`): their headquarters asks and pays for their plans (see Company credits). Their credits work exactly as for any store (balance, charges, refunds, history); only who asks changes. Independent stores and restaurants are unchanged. `credits` and `price` are the request's own snapshot, so a later plan change never alters what was quoted or what an approval grants.
- `GET /plans` → `{ plans }` (active, by credits: id, name, credits_per_period, price). `GET /topup-packages` → `{ packages }`.
- `GET /me` → `{ credits }` = `creditSummary`: `getBalance` (`periodStart`, `periodEnd`, `subscription`, `hasActiveSubscription`, `total`, `used`, `available`) + `nextSubscription` (next month's, or null) + `pendingRequests` (the open ones: PENDING, and for a branch COMPANY_REVIEW) + `managedByCompany` (true for a branch) and `companyName` (its company, else null).
- `GET /me/history?year=` (default the current credit year; 2000–2100, else 400 `"Invalid filter."`) → `{ history: { year, months: [{ month, hasSubscription, total, used }] × 12, categories: [{ category, used }] } }` (`getUsageHistory`: a charge refunded in its own month never counts, so the categories add up to the months).
- `GET /requests` → `{ requests, total }`, every status, newest first, paged (default 10).
- `POST /requests`: `request_type` `SUBSCRIPTION` (`plan_id`, `period` `current`/`next`, optional boolean `auto_renew`) or `TOPUP` (`topup_package_id`, always this month). 400 `"Request type is not valid."`, `"Period is not valid."`, `"Auto-renew must be true or false."`; 404 `"Plan not found."` / `"Top-up package not found."` (also for inactive ones); 400 `"You already have a subscription for this month."`, `"An active subscription for the current month is required to buy extra credits."`, and from the partial unique indexes (`23505`) `"You already have a pending subscription request for this month."` / `"You already have a pending top-up request."`. Notifies every admin in the same transaction. 201 `{ message: "Request sent.", request }`; `requested_by` is the user. A **branch**: `SUBSCRIPTION` → 403 `"Your company manages your plan."`; `TOPUP` (same validation and "active subscription this month" rule) is created as `COMPANY_REVIEW` with source `BRANCH` and goes to its headquarters instead of the admins (`BRANCH_TOPUP_REQUESTED` to every unblocked headquarters login); 201 `"Request sent to your company."`. The open-top-up index answers a second one (at the headquarters or the admin) with `"You already have a pending top-up request."`.
- `DELETE /requests/:id`: withdraws an own PENDING request (`CANCELLED`; the status condition is part of the UPDATE, so it cannot race an admin's decision). 404 `"Request not found."`, 403 `"You are not allowed to withdraw this request."`, 400 `"Only pending requests can be withdrawn."`. 200 `{ message: "Request withdrawn.", request }`. A branch withdraws only a `COMPANY_REVIEW` top-up; a PENDING one (sent by its headquarters) → 403 `"Your company manages your plan."`.
- `PATCH /subscription/auto-renew` body `{ auto_renew: boolean }`: sets it on the user's current and future ACTIVE subscriptions (404 `"You do not have an active subscription."`) and on their PENDING `SUBSCRIPTION` requests (their own and the job's renewals), so approving one later keeps the user's choice. Nothing is cancelled: next month's approved plan or pending request stays, and with auto-renew off it simply does not renew after that month. Turned on in the renewal window (`isRenewalWindow`), it calls `createRenewals(client, now, { userId, explicit: true })` in the same transaction, since the job may already have run for the last time that month; a renewal the user withdrew earlier no longer blocks, one the admin rejected does. 200 `{ message: "Auto-renew turned on." | "Auto-renew turned off.", autoRenew, renewalCreated }`. The logic is `applyAutoRenew(client, userId, autoRenew)` (also used by the headquarters). A branch → 403 `"Your company manages your plan."`.

### Branches `/api/company/branches` (COMPANY)
A branch is a STORE with `company_id`: it publishes products, answers reservations, handles pickups and donations like any store. Its headquarters only creates, names, views and deactivates it (`controllers/companyBranches.controller.ts`; the shared rules are in `services/branches.ts`, which the admin endpoints reuse). Every `/:id` route answers 404 `"Branch not found."` for a branch of another company (or any user that is not one of the caller's stores), so their existence is not revealed. Writes run in a transaction that locks the branch and answer after the commit.
- `GET /branches`: paged (12). Filters `q` (name ILIKE), `city_id` (`parseCityFilter`), `status` (`active`/`deactivated`/`blocked`, else 400 `"Invalid filter."`). Ordered by name. ## Business logic worth knowing

- **Available quantity** is computed, never stored (`services/stock.ts`: `heldByReservations`, `soldInShop`, `availableQuantity` SQL for a product alias, `sellableProduct(product, store)` for whether restaurants can order it at all (Available, not expired, the store visible; used by sending and the cart); `freeQuantity`, `reservedQuantity`, `soldOutCover` for one product): `products.quantity` minus the sum of `Pending` + `Confirmed` + `Completed` item quantities (each item's current quantity, the accepted one once the store decided; picked-up food is gone, so completing must not free it) minus what the store sold in its own shop (`product_shop_sales`). Partial orders are allowed and the product stays `Available` until Confirmed + Completed items plus shop sales cover the full quantity (`markSoldIfFullyConfirmed`, `releaseSoldProduct`, both in `services/stock.ts`). Shop sales count in the marketplace, product details, my products, sending an order, the store's decision, the sold-out status, moving to donations and returning a donation to the offer (rebuilding a `Removed` product). They are never an app sale: reports, statistics and food saved ignore them, and the store profile's `sold_articles` counts a `Sold` product only when it has a Confirmed or Completed reservation.
- **Stock-safe pattern** (`sendOrder`, `decideOrder`, `updateProduct`, shop sales): one transaction, `SELECT ... FOR UPDATE` on the product rows (ascending id) after the order's own lock, compute, write, `COMMIT`; `ROLLBACK` on any error (`inTransaction` in `utils/transaction.ts` for new code, or `pool.connect()`/`BEGIN`/`client.release()` in `finally`). Use the same pattern for anything that touches stock or an order's status, and keep the lock order of Orders. `markSoldIfFullyConfirmed(client, product)` marks a locked product `Sold` once Confirmed + Completed items and shop sales cover its quantity; `releaseSoldProduct(client, productId)` locks the product and turns a `Sold`, unexpired product back to `Available` once they no longer do (missed pickup, an admin's cancel of a Confirmed order).
- **Notifications** are written with `createNotification(db, { userId, type, message, orderId?, productId?, donationId?, details? })` from `utils/notifications.ts` as part of the action; `db` is the pool or the transaction client, so inserts inside a transaction commit or roll back with it. The client translates each one from `type` plus the joined product data; `message` is an **English fallback** (the one exception to "server messages are Bosnian"), for example `"New order #K7PM: 2 items."`. Order notifications are one per order event (the client names the order by its code, `GET /notifications` joins it). Types:

- **Emails** (`src/email/`). No real email is sent yet: development and tests use `log` or Mailpit, and Resend is built but not configured.
  - **Config** (`config.ts`, `loadEmailConfig(env)`, called once in `server.ts`; an invalid setting throws `EmailConfigError`, the server logs `Email configuration error: <message>` and exits with 1 before listening, otherwise it logs `Emails: <provider>[, every email redirected to <address>]`). `EMAIL_PROVIDER`: `log` (default), `smtp` or `resend`. `EMAIL_FROM`: `Name <address>` or a bare address, default `FoodWise <no-reply@foodwise.local>`, required for `resend`. `EMAIL_REDIRECT_TO`: optional, a valid address (lowercased). `RESEND_API_KEY`: required for `resend`. `SMTP_HOST`/`SMTP_PORT`: default `localhost`/`1025` (Mailpit), the port 1–65535. Empty values count as unset. **Safety rule:** `resend` with `NODE_ENV` other than `production` and no `EMAIL_REDIRECT_TO` is refused. Links point to the first `CLIENT_ORIGIN` (`appUrl`, trailing slash removed). Going live changes only these variables.
  - **Transports** (`transports.ts`, one interface `EmailTransport { name, send(message, { idempotencyKey? }) }`, `createEmailTransport(config)` picks one): `log` writes the email (from, to, subject, text) to the console; `smtp` uses nodemailer (`secure` only on port 465; the factory is injectable for tests); `resend` posts `{ from, to: [to], subject, html, text }` to `https://api.resend.com/emails` with `Authorization: Bearer <key>`, the `Idempotency-Key` header (`foodwise-email-<queue id>`, so a retry after a timeout cannot send twice) and a 15 s timeout, and throws `Resend responded with <status>: <message>` on an error (the `fetch` function is injectable for tests).
  - **Redirect** (`redirect.ts`, `applyRedirect(message, redirectTo)`): with `EMAIL_REDIRECT_TO` the email goes to that address and its subject becomes `[to: <real recipient>] <subject>`. The queue keeps the real recipient.
  - **Queue** (`queue.ts`, table `email_queue`). `enqueueNotificationEmails(db, notificationIds)` is called right after notifications are inserted, with the same `db`, so the email rows are written in the notifications' transaction (a rollback drops both; the reminder job runs in one transaction for this). One `INSERT ... SELECT` for any number of notifications (an announcement reaches every store and restaurant): template = the notification's `type`, `data` = `NOTIFICATION_EMAIL_DATA` (`templates/notificationData.ts`), a `jsonb_build_object` over the same joins as `GET /notifications` plus the reservation's restaurant and store, taken at that moment. Untyped (old) notifications, blocked recipients (`notBlocked`: also a blocked company or a deactivated branch) and recipients with `email_notifications` off get no email; a deleted account's emails go with it (`ON DELETE CASCADE`). Returns the number queued. `enqueueEmail(db, { userId, template, data })` queues a single email that is not a notification's (for the coming system emails; none exists yet): never to a blocked user, and only with `email_notifications` on unless the template is a system one; an unknown template throws. The recipient is the user's email; the language is `bs` for every email (`DEFAULT_EMAIL_LANGUAGE`), because the users' language is not stored yet. `processEmailQueue({ transport, config, now?, batchSize?, db? })` (returns `{ sent, retrying, failed, skipped }`): first gives rows stuck in `SENDING` for over 10 minutes (a worker that stopped mid-send) back to `PENDING` (or `FAILED` at the maximum), then claims up to 50 due `PENDING` rows (`next_attempt_at <= now`, oldest first, `FOR UPDATE SKIP LOCKED` so several instances never take the same row) by setting `SENDING`, `attempts + 1` and `locked_at`, returning the recipient's current `email_notifications` and block. A row whose recipient is blocked by now, or (unless its template is a system one) turned email notifications off since it was queued, becomes `SKIPPED` (`last_error` = `The recipient is blocked.` / `The recipient turned email notifications off.`) and is never sent, even if the switch goes on again. Each other row is rendered, redirected and sent: success → `SENT` with `sent_at`; a send error → back to `PENDING` with `last_error` and `next_attempt_at` 1 min, 5 min, 30 min, then 2 h later (`RETRY_DELAYS_SECONDS`), and `FAILED` after the 5th attempt (`MAX_EMAIL_ATTEMPTS`); an unknown template or data that does not fit it → `FAILED` at once. Errors are logged and stay in the queue; they never reach the action that queued the email. `startEmailWorker(config)` (from `server.ts` only; tests call `processEmailQueue`) runs a pass at startup and every 5 s (`EMAIL_POLL_INTERVAL_MS`), never two at once, and logs a failed pass (`"Error while processing the email queue:"`).
  - **Templates** (`templates/`): `renderLayout({ lang, subject, heading, intro, details?, outro?, button })` returns `{ subject, html, text }`: an orange FoodWise header, the heading, paragraphs, a label/value table, a button linking to the page and a footer ("you received this email because you have a FoodWise account" and "FoodWise – Još vrijedi"), as table-based HTML with inline styles (every value escaped with `escapeHtml`) and a plain text version with the same content and the link as `<button label>: <url>`. `format.ts`: `formatQuantity` (`2,5` / `2.5`), `unitLabel` (`kom` → `pcs`, `pak` → `pk` in English), `formatPickup` (`06.11.2026. 14:30` / `06/11/2026 14:30`, midnight = date only). An `EmailTemplate` is `{ system?, render(data, lang, appUrl) }`, `render` pure. `system: true` marks a system email (password reset, email confirmation, login details) that ignores the user's switch; a new template only declares it. Notification emails pass `settingsUrl` to the layout, which adds a footer link "Isključite email obavijesti" / "Turn off email notifications" to `/my-profile#email-notifications` (`EMAIL_SETTINGS_PATH`); system emails leave it out. Server email texts are written in both languages in the templates (like the CSV reports), not through the client's locale files.
  - **System emails** (`templates/systemEmails.ts`, `SYSTEM_TEMPLATES`, all `system: true`, no footer link to the switch), queued with `enqueueEmail`: `INVITATION` (data `{ token, sender }`; "Pozivnica za FoodWise" / "Your FoodWise invitation", the button to `/set-password?token=<token>`, valid 72 hours and once, what to do when it expired; the text names the platform administrator, or for `sender: "COMPANY"` the company's headquarters, and a missing sender means the administrator), `PASSWORD_RESET` (data `{ token }`; "Postavite novu lozinku" / "Set a new password", the button to `/reset-password?token=<token>`, valid 1 hour and once, "ignore this email if you did not ask"). The raw token sits in `email_queue.data` only until the email is finished: `SENT`, `FAILED` and `SKIPPED` also set `data = data - 'token'`. `SYSTEM_NOTIFICATION_TYPES` (`PASSWORD_CHANGED`) are notification types whose email is a system one: `enqueueNotificationEmails` queues them with the switch off, and their template is `system: true`.
  - **Notification emails** (`templates/notificationEmails.ts`): `NOTIFICATION_TEMPLATES` has one template per `NotificationType` (a `Record`, so a missing type fails the typecheck; 36 today), named after the type. Each type's text follows the in-app notification (`notifications.types` / `notifications.credits` on the client), credit types worded per request type (subscription or top-up). The details table shows what the notification links to: product (or donation), the order (`#K7PM`) and the other party (the restaurant for a store, the store for a restaurant), pickup, for credit types the requester (admins only; a branch's as `<company> → <branch>`) and credits, and `details` as **Reason** (an admin's reason) or **Headquarters' note** (`CREDIT_TOPUP_COMPANY_REJECTED`). The admin's note on a credit decision is never in a notification, so never in an email. Order emails add the order's lines under the details (`orderLines` in the data, a snapshot taken when the notification was stored): each line with its amount and line total, a reduced line with "15 kg od 20 kg · nema dovoljno na stanju", rejected and cancelled lines struck through with their reason, then the total of the lines that still count (none when nothing is left); `ORDER_PARTIALLY_ACCEPTED` adds "Novi iznos: X umjesto Y". `parseNotificationData` reads data queued before the order fields existed as without an order. `PLATFORM_ANNOUNCEMENT` uses the announcement's own title (subject `Obavještenje platforme: <title>`) and text (one paragraph per line), in English when the admin wrote one. `notificationLink(type, data)` picks the button's page like `getNotificationLink` on the client: `/company/credits` for `BRANCH_TOPUP_REQUESTED`, the branch page for a headquarters' branch notifications, then the order (`/orders/:id`, button "Otvori narudžbu"), `/reservation/:id` (old notifications; the client redirects it to the role's list), `/products/:id`, `/donate-food`, `/dashboard` (announcements), `/admin/credit-requests`, `/credits`, `/my-profile#topup` / `#subscription`, else the role's list (`/orders` for a store, `/my-orders` for a restaurant). Adding a notification type means adding its copy in both languages there.
- **Expiry job** (`jobs/expireProducts.ts`, started from `server.ts` only): `expireProducts()` finds the `Available` products past `expiry_date`, locks the Pending orders holding them, marks the products `Expired` (the store gets `PRODUCT_EXPIRED`) and cancels their **Pending** items through `cancelPendingItemsOfProducts` (one notification per order), all in one transaction. Confirmed items are left as they are: the store already agreed to hand that food over, and it closes them itself (complete, or cancel-overdue after a missed pickup). In the same transaction it deletes the cart lines of products past their expiry date for more than a day (`expiry_date < CURRENT_DATE - 1`) or `Removed` more than a day ago (`products.updated_at`), so the restaurant still sees for a day why a line became unavailable (lines of a blocked store stay), and `Available` donation offers past `expiry_date` become `Expired` (no notification yet, nobody but the donor sees them). `startExpirationJob()` runs it once at startup (to catch up on midnights missed while the server was down) and then on cron `0 0 * * *` in `APP_TIMEZONE`. Expiry checks in SQL use `expiry_date < CURRENT_DATE`, so a product is still valid on its expiry day.
- **Credit renewal job** (`jobs/creditRenewals.ts`, started from `server.ts` only): `runCreditRenewals(now)`, in one transaction, expires PENDING and COMPANY_REVIEW requests whose month has ended (`EXPIRED`, each requester gets `CREDIT_REQUEST_EXPIRED`, a branch's headquarters `BRANCH_CREDIT_REQUEST_EXPIRED`) and, in the renewal window (`isRenewalWindow`: the last `RENEWAL_DAYS_BEFORE` (2) days of a credit month), calls `createRenewals(client, now)`. `createRenewals` creates a PENDING `AUTO_RENEW` subscription request for the next month with the same plan for every ACTIVE subscription with `auto_renew` and notifies the admins and the user (`CREDIT_RENEWAL_CREATED`). Branches are renewed like any store (`requested_by` null). Skipped: blocked users (also deactivated branches and branches of a blocked company, via `notBlocked`), users who already have next month's subscription, a pending subscription request for it, or an earlier renewal for it in any status (so a withdrawn or rejected renewal is not created again; with `explicit` a withdrawn one does not block). An inactive plan is not renewed; its subscriber gets `CREDIT_RENEWAL_SKIPPED` instead. The insert uses `ON CONFLICT DO NOTHING`, so a request the user sends at the same instant skips only that row instead of failing the whole run. Returns `{ created, expired }`. `startCreditRenewalJob()` runs it at startup and on cron `10 0 * * *` in Europe/London.
- **Reminder job** (`jobs/notificationReminders.ts`, started from `server.ts` only): `sendReminders()` inserts `PRODUCT_EXPIRING_SOON` and `ORDER_PICKUP_TODAY` with `INSERT ... SELECT ... WHERE NOT EXISTS` (same type for the same product or order), so each reminder is sent once no matter how often it runs; it returns `{ expiringSoon, pickupToday }` counts. `startReminderJob()` runs it at startup and on cron `0 7 * * *` in `APP_TIMEZONE`.
- **Soft delete and history:** orders and their items are never deleted (`order_status_history` keeps every change), products are marked `Removed`.
- **Pickups:** only the store moves an order to `Completed` (`POST /orders/:id/complete`) or cancels a missed one (`cancel-overdue`); both act on the whole order (no partial pickup). Statistics of delivered or saved food (store profile counts, dashboard food saved and savings, admin and footer food saved, reports) count only `Completed`; the dashboards' "Prihvaćene narudžbe" card counts accepted orders (Confirmed + Completed).
- **Credits** (the product flows charge and refund as noted in the endpoint tables above; requests and approval are under Credits and Admin credits). Stores pay 1 credit per published product; restaurants pay nothing (reservations are free, and nothing is refunded when one ends); donations are free. Controllers call the service inside their own transaction and answer a thrown `HttpError` (e.g. the 402) with `error.body()` in their catch. Where refunds happen: product delete and complete move to donations (same day, nothing reserved); never for an admin product removal (the store). The renewal job and every credit entry point (`/api/credits`, the admin adjust and ledger) are for stores only. Rules the service implements:
  - **Time:** credit days and months change at 00:00 **Europe/London** (01:00 Sarajevo, also across DST), computed in Node with `utils/creditTime.ts` (`creditDay`, `creditMonth` → `YYYY-MM-01`, `nextMonth`, `monthEnd`), never with `CURRENT_DATE` (the pool session runs in `APP_TIMEZONE`). Every service function takes `now` (default `new Date()`) so tests can move the clock, and writes it as `created_at`.
  - **Balance** (`getBalance(db, userId, now)` → `{ periodStart, periodEnd, subscription, hasActiveSubscription, total, used, available }`) is computed from the ledger rows of the current month, never stored: Total = plan + top-up grants + adjustments + refunds of charges from earlier months; Used = charges − refunds of same-month charges; Available = Total − Used, and 0 without an active subscription for the month (rows recorded for such a month count once the user subscribes in it). Unused credits never move to the next month.
  - **Charges** (`chargeForProduct`, `chargeForProducts` for the all-or-nothing CSV import) lock the user's subscription row for the month (`FOR UPDATE`), check the balance and insert one `-1` row per item with the category snapshot, all in the caller's transaction. Lock order: the order and the product first, then the subscription. No subscription or not enough credits → `InsufficientCreditsError`: 402 `{ error: "Not enough credits.", code: "INSUFFICIENT_CREDITS", hasActiveSubscription, actionUrl }` (`/my-profile#topup` with a subscription, else `/my-profile#subscription`). `HttpError` takes optional `details` that `body()` adds next to `error`.
  - **Refunds** find the newest unrefunded charge of the product and insert `+1` into the **current** month (with that month's subscription, or none), copying the category; `refunds_transaction_id` is UNIQUE and the insert uses `ON CONFLICT DO NOTHING`, so a charge is refunded at most once. They return `{ refunded: true, transaction }` or `{ refunded: false, reason }` (`NO_CHARGE` (also for data from before credits), `DAY_PASSED`, `HAS_RESERVATIONS`, `ALREADY_REFUNDED`). `refundForProduct` (delete, or moved to donations completely): only on the credit day of the charge and only if the product has no Pending/Confirmed/Completed reservation (Rejected and Cancelled do not count). The same-day rule is `isRefundEligible(chargeCreatedAt, now)`. The ledger still has the `RESERVATION_CHARGE` / `RESERVATION_REFUND` types (Postgres cannot drop enum values without rebuilding the type), but nothing writes them.
  - **Grants:** `grantPlan` creates the subscription for its month (current or later; a past month → 400 `"This month has already ended."`, a second one → 400 `"The user already has a subscription for this month."`) and a `PLAN_GRANT` into that month; `grantTopup` adds a `TOPUP_GRANT` to the current month and needs an active subscription there (400 `"An active subscription for the current month is required."`); `adjustCredits` writes an `ADMIN_ADJUSTMENT` (whole number ≠ 0, reason required) into the current month and refuses to take the available balance below zero (400 `"The balance cannot go below zero."`).
- **Global error handling** (`app.ts`, after the routers): unknown routes → 404 `"Route not found."`; `HttpError` (`utils/httpError.ts`, carries a status and optional extra body fields) → that status and `error.body()`; multer errors → 400 (`"The image can be at most 5MB."`); malformed JSON → 400 `"Invalid request format."`; anything else → 500 `"A server error occurred."`. Controllers still handle their own errors; this covers middleware and body parsing.

## Conventions

- Controller shape: `try { ... } catch (error) { console.error(...); return res.status(500).json({ error: "..." }) }`, always `return res...`.
- Failures: `{ error }`; successes: `{ message, <entity> }`. 404 for missing, 403 for not-owner, 400 for validation and invalid state.
- Dynamic filters: build the `WHERE` with `values.push(...)` and `$${values.length}`, add `ORDER BY` last. Declare `values` as `(string | number)[]` when it mixes types.
- **Pagination** (`utils/pagination.ts`): `parsePage(req.query, defaultLimit)` reads `limit` (1–100) and `offset` (≥ 0) and returns null for anything else, which the controller answers with 400 `"Invalid filter."`; `listPage(columns, from, orderBy, values, page)` runs `SELECT COUNT(*) <from>` and the page query. Every paged list keeps its response key and adds `total` (all matches for the current filters, not the page). Defaults: `CARD_PAGE_SIZE` 12 for card lists (marketplace, own products, reservations, completed pickups, stores, donations), `TABLE_PAGE_SIZE` 10 for a store's or restaurant's own credit requests, `ADMIN_PAGE_SIZE` 20 for every admin list (including the credit overview, requests and a user's ledger). Every paged `ORDER BY` ends with `id DESC` (or another unique key before it), so rows with equal timestamps or names never repeat or go missing between pages. Not paged: notifications (50 newest), credit history, reports, pickup counts, today/upcoming pickups.
- **Sorting the admin tables** (`parseSort(req.query, columns, defaultOrder, tieBreaker)` in `utils/pagination.ts`): `sort` must be a key of the endpoint's whitelist (`USER_SORTS`, `PRODUCT_SORTS`, `RESERVATION_SORTS`, `DONATION_SORTS` in `admin.controller.ts`, `OVERVIEW_SORTS` in `adminCredits.controller.ts`), each mapped to an SQL expression in code, so the query value never reaches SQL; `dir` is `asc` (default) or `desc`. Anything else (an unknown key, another table's key, a bad `dir`, also without `sort`) is 400 `"Invalid filter."`. Empty values mean "not set" and keep the default order. The order is `<expression> ASC|DESC NULLS LAST, <table>.id DESC`: empty values come last in both directions and the id keeps the pages stable. Sorting combines with every filter and with paging; `total` is unchanged.
- Priority sorting uses `ORDER BY CASE WHEN status = '...' THEN 0 ... END, created_at DESC`.
- Ownership checks compare the resource owner with `req.user.id` (directly, or through the product's `store_id`).
- All server text is English: error and success messages (asserted by tests) and log lines. The client does the UI translation: notifications are translated from `type` (the stored `message` is an English fallback), the CSV reports take `lang`, and every `error` / `message` is translated on the client by its exact English text (`client/src/i18n/locales/server.bs.json`; a client test fails when a server text has no translation or a translation no longer matches a server text). Adding or rewording a message means updating that file in the same change. Keep messages short and plain. Examples: `"Product created successfully."`, `"All fields are required."`, `"Product not found."`, `"You do not have the required role for this action."`, `"Not enough product available."`, `"Product has active reservations and cannot be deleted."`.

## TypeScript notes

- Local imports use `.js` extensions (nodenext), packages never do.
- `req.body` is `any`; destructure it and annotate with an interface where one exists (`ProductFields`, `RegisterBody`, `LoginBody`). `req.query` values are cast with `as string`. `req.params` values are strings.
- `catch (error)` is `unknown`: use `error instanceof Error && 'code' in error` before reading Postgres codes.
- `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are on: expect `rows[0]` to possibly be undefined.
- `process.env.JWT_SECRET!` is asserted where used.
- Shared types: `types/auth.ts` (`AuthUser`, `Role`), `types/express.d.ts` (augments `Express.Request` with `user?` and `file?`).

## CI

GitHub Actions, `.github/workflows/ci.yml`. Runs on every pull request to `main`, every push to `main` and by hand (`workflow_dispatch`, which runs everything). A new commit on the same PR/branch cancels the run in progress.

- `Detect changes` (`dorny/paths-filter`, pinned to a commit SHA) decides what runs: `server/**` → Backend; `client/**` and `server/src/**` → Frontend (the client test `serverMessages.test.ts` reads the server sources); `e2e/**` → E2E (which also runs whenever Backend or Frontend would); `.github/workflows/**`, the root `package.json` or `package-lock.json` → all three.
- `Backend` (`server/`): Node 24, `npm ci`, a `postgres:15` service container (same major as local development) with database `food_saver_test_db`, a `.env.test` written by the workflow with test-only values (`DATABASE_URL`, `JWT_SECRET`), migrations with `npx dotenv run -q -f .env.test -- node-pg-migrate up`, `npm run typecheck`, `npm test` (default + `github-actions` reporters, so failures show as PR annotations), `npm run build`. `TZ=Europe/Sarajevo`, because the test helpers build dates from the process's local day and must agree with `APP_TIMEZONE`.
- `Frontend` (`client/`): Node 24, `npm ci`, `npm run typecheck`, `npm run lint`, `npm test` (same reporters), `npm run build`.
- `E2E`: Node 24, a `postgres:15` service with `food_saver_e2e_db`, a Mailpit service (`axllent/mailpit:v1.32.0`, SMTP 1025, API 8025), `npm ci` in `server/`, `client/` and `e2e/`, a `.env.e2e` with test-only values (including `EMAIL_PROVIDER=smtp` and `MAILPIT_URL`), Chromium (the download cached by Playwright version, installed `--with-deps`), `npm run typecheck` and `npm run e2e` in `e2e/` (the Playwright web servers build, migrate and start both sides). On failure it uploads the `e2e-report` artifact (HTML report and traces, 14 days). Details in `docs/e2e.md`.
- `CI passed` runs always and fails if any job above failed or was cancelled (skipped is fine). It is the only check required by the `main` branch rules, so its name must not change.
- A failed run: `gh pr checks` shows which job failed, `gh run view <run-id> --log-failed` prints only the failed steps' logs.
- Lint: only `client/` has ESLint (`eslint.config.js`), and the `Frontend` job runs it. The server has no linter; its checks are the strict typecheck and the tests.
- Dependabot (`.github/dependabot.yml`): npm in `/`, `/server`, `/client` and `/e2e`, plus `github-actions`, every Monday at 07:00 Europe/Sarajevo. Minor and patch updates come as one grouped PR per folder/ecosystem, majors as separate PRs; at most 5 open PRs per entry, commit messages prefixed `deps`. Its PRs go through CI like any other (a root lock change runs every job). It also bumps the SHA-pinned `dorny/paths-filter`.
- PR template (`.github/pull_request_template.md`): what and why, how it was tested, and a checklist (tests, i18n keys in `bs` and `en`, docs, safe migration, screenshots for UI changes).

## Seed

`npm run seed` (`src/scripts/seed.ts`, static lists in `src/scripts/seedData.ts`) replaces all data with a platform that looks like it has been in use for the last 61 days. It runs in one transaction and takes a few seconds.

- **Wipe:** deletes all rows (credit ledger (with `app.ledger_maintenance` on), admin actions, notifications, announcements, orders (their items, history and shop-sale links go with them), donation offers, products, users, then companies; everything else cascades from users). `plans` and `topup_packages` stay.
- **Accounts** (password `To12345678`, `SEED_PASSWORD`): admins `admin@demo.com`, `admin2@demo.com`; the company "Bingo d.o.o." (`COMPANIES` in `seedData.ts`) with its headquarters login `bingo@demo.com` (profile filled in, no temporary password, a `CREATE_COMPANY` action) and five branches at the end of `STORES` (`company: "Bingo d.o.o."`, no description or logo of their own, no `CREATE_USER` action since their headquarters created them): Bingo Sarajevo Centar `bingo.sarajevo@demo.com`, Bingo Visoko `bingo.visoko@demo.com`, Bingo Kakanj `bingo.kakanj@demo.com`, Bingo Zenica `bingo.zenica@demo.com`, Bingo Tuzla `bingo.tuzla@demo.com`, which go through the same simulated history as the other stores; 10 stores and 10 restaurants with full profiles spread over Sarajevo, Visoko, Kakanj, Zenica and Tuzla (each of the five has stores and restaurants, for the nearby step; `seedData.ts` names the city and `seed.ts` looks up its id, failing on a name that is not in `cities`), created over the first few days (each with a `CREATE_USER` admin action). Each business has an activity rate, so some stores publish far more than others, and a plan per month (`plans`, e.g. Basic → Standard), with or without auto-renew.
- **Credits:** every subscription goes through an approved `credit_requests` row (the first month right after the account was created, later months by an `AUTO_RENEW` request two days before the month, a plan-change request a few days before, or a request on the 1st), with the admin action and notifications. Every grant, charge and refund is written through `creditService` (`grantPlan`, `grantTopup`, `chargeForProduct`, `refundForProduct`, `adjustCredits`) with the simulated time as `now`, so balances follow the real rules and never go negative. Only stores have subscriptions, requests and ledger rows; restaurants have none. Extras: one rejected, one withdrawn and one expired request, one admin adjustment, and two pending requests (a next-month upgrade and a top-up). Bingo's branches have their plans requested by `bingo@demo.com` (source `COMPANY`; Sarajevo Centar, Zenica and Tuzla with auto-renew, whose renewals are `AUTO_RENEW` with no sender), and the headquarters is told of each decision; Bingo Zenica has a top-up waiting for the headquarters and Bingo Tuzla one the headquarters forwarded to the admin.
- **Day-by-day history:** stores publish products (expiry 2–8 days out); restaurants order from stores in their city (favorites preferred), sometimes 2–3 products of one store in one order. Orders are written in the shapes the order service writes (order, items, history with sources and actors, a random code per store, notifications). Outcomes: mostly Completed (with `picked_up_at`), some of them **partly accepted** (a smaller quantity with `NOT_ENOUGH_STOCK`, often with the difference recorded as sold in the shop from the order, and a rejected item with `QUALITY` or `OTHER` and a note), then cancelled by the restaurant, rejected with a reason, missed pickups, pending orders cancelled when the product expired, and admin cancellations (`CANCEL_ORDER`). About 15% of the orders have partial fulfilment off and some carry `send_changes` (a lowered price or a reduced quantity). Products end as Sold (covered by accepted items and shop sales), Expired, Removed (by the store the same day, refunded, or by an admin) or still Available. Every event writes the notification the app would send, with its timestamp; notifications older than 3 days are mostly read. While the old reservation screens are in use, orders with several items are only in final statuses.
- **Current state:** each store has a current stock (115 products in total, expiry 1–10 days out, ~130 on offer with the history's leftovers), 25 Pending (some with partial fulfilment off) and 20 Confirmed orders of 1 to 4 items of one store (about half have several; pickups from later today up to 3 days out, never after the earliest expiry among the items; their quantities always leave some stock, so these products stay on offer), two late pickups (Confirmed orders, possibly with several items, whose pickup day was yesterday and three days ago), and ~15 available donations.
- **Also:** donation offers of both types from stores (product lines) and restaurants (meals with allergens and temperature), favorites, product templates, three announcements (one expired, one ended by an admin, one active) with notifications and dismissals, and admin log entries for a password reset, a profile edit and a block/unblock. Restoran Ukus has a cart of three lines from the store with the most on offer, one of them added at a lower price (so the cart shows "the price went up").

Random choices use a fixed seed (mulberry32), so every run gives the same data relative to its run date. The script prints counts per status and the logins.

## Pending and known limitations

- **Deployment:** set `TRUST_PROXY=1` on Render (otherwise all users share one rate limit); the rate-limit counters are in memory, so more than one instance needs a shared store. The auth cookie is `sameSite: "strict"`, so the frontend and the API must be served from the same site (the same domain, or subdomains of one domain such as `app.example.com` and `api.example.com`). Do not switch to `sameSite: "none"` without real CSRF protection: the origin check is only a second layer. Set `CLIENT_ORIGIN` to the deployed frontend origin(s); logo uploads on local disk are lost on Render restarts (needs cloud storage; Cloudinary is not available in the owner's country, so evaluate alternatives). With more than one server instance the cron jobs would run once per instance (they are idempotent, but a lock or a separate worker is cleaner).
- **Emails:** every email is in Bosnian until the users' language is stored (the queue already has a `language` column). Every notification type has an email; the only setting is one switch for all of them (`users.email_notifications`). With more than one instance every instance runs the email worker, which is safe (`SKIP LOCKED`). Sent rows stay in `email_queue` (no cleanup job yet).
- Server messages should become error keys translated on the client.
- `PUT /users/me`: replace `COALESCE` with a real PATCH that can clear optional fields.
- Migrations are still JavaScript. They have already run, so they stay as they are; a new migration can be written in TypeScript once `node-pg-migrate` runs with a TS loader (for example `tsx`).
- The server has no ESLint setup.
