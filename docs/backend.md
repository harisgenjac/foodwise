# Backend (`server/`)

Reference for working on the API. The source of truth is the code; routes and middleware per endpoint are in `src/routes/*.routes.ts`.

## Stack

- Node.js 24, Express 5 (`express@5.2.1`, `@types/express@5`), TypeScript, ESM (`"type": "module"`, `module: nodenext`)
- PostgreSQL through raw `pg` queries (no ORM), migrations with `node-pg-migrate`
- Auth: `jsonwebtoken` + `bcrypt` (10 salt rounds), JWT in an httpOnly cookie, `cookie-parser`, `cors`
- Uploads: `multer` (memory storage: images go on to `services/storage.ts`, CSV imports are parsed in memory), CSV parsing with `csv-parse`. Scheduled work: `node-cron`
- Email: `nodemailer` for SMTP (Mailpit); Resend through its HTTP API with `fetch` (no SDK). See Emails.
- Tests: Vitest + supertest (see Testing)

Express 5 notes: `req.query` is a read-only getter (read it, never assign to it), and wildcard routes must be named (`/*splat`). Neither is used today.

## Scripts and environment

- `npm run dev`: `concurrently "tsc --watch" "node --watch dist/server.js"`. The server runs the compiled `dist/`, so run `npm run build` once on a fresh clone.
- `npm run build` (`tsc`), `npm start` (`node dist/server.js`)
- `npm run migrate up|down` (loads `.env` with `dotenv run`, the CLI of the `dotenv` package); `npm run migrate:create -- <name>` writes a new TypeScript migration (node-pg-migrate 9 loads `.ts` files itself, no extra loader)
- `npm run db:reset`: a fresh local database: builds, refuses when `NODE_ENV` is `production` or the database name contains `prod` or `live`, drops and recreates the `public` schema, runs the migrations, empties `UPLOADS_DIR`'s `logos` and `products` (dotfiles stay) and runs the seed (`-- --demo`: the demo seed)
- Env files: the npm scripts load them with `dotenv run -q -f <file> --` (the CLI of `dotenv` 18; `dotenv-cli` was removed because both packages install a `dotenv` binary). Variables already set in the environment win and `${VAR}` references are not expanded. At runtime `server.ts`, `seed` and `create-admin` load `.env` with `import "dotenv/config"` (quiet since dotenv 18, existing variables win), so on a host the dashboard's variables are used.
- `npm test` (Vitest + supertest, `.env.test`, files run one at a time; the full suite runs in CI, see CI below). Single file: `npm test -- tests/products.test.ts`. Single test: `npm test -- -t "name"`. Watch mode: `npm run test:watch`.
- `npm run typecheck`: `tsc --noEmit -p tsconfig.test.json` (source and tests).
- `npm run seed` (the accounts only) and `npm run seed:demo` (the accounts plus two months of activity): destructive resets, see Seed; both build first and run from `dist/`.
- `npm run create-admin -- <email> <password> [first name] [last name]`: builds, then inserts an `ADMIN` account (same email and password rules as the API; a duplicate email is refused). Used for the first admin; later accounts are created in the app.
- Env: `DATABASE_URL`, `JWT_SECRET`, optional `PORT`, `NODE_ENV`, `CLIENT_ORIGIN` (allowed frontend origin for CORS and the origin check, default `http://localhost:5173`; a comma-separated list is allowed), `TRUST_PROXY` (number of proxy hops in front of the server, for `app.set("trust proxy")`; unset or 0 = off, which is right locally; Render needs `1`), `APP_TIMEZONE` (business time zone for `CURRENT_DATE` and cron, default `Europe/Sarajevo`), `DISABLE_RATE_LIMITS` (`true` turns the rate limiters off; only for the e2e server, never on a deployment), `UPLOADS_DIR` (folder for uploaded files, default `uploads`; `vitest.config.ts` sets `uploads-test` and the e2e config `uploads-e2e`, so neither touches or cleans up the dev server's files), and the email variables `EMAIL_PROVIDER`, `EMAIL_FROM`, `EMAIL_REDIRECT_TO`, `RESEND_API_KEY`, `SMTP_HOST`, `SMTP_PORT` (see Emails), and `DELIVERY_PROVIDER`, `DELIVERY_WEBHOOK_SECRET` (see Delivery provider). `.env.test` points at the separate database `food_saver_test_db`. `server/.env.example` lists every variable with comments (the only committed env file; `server/.gitignore` excepts it).

## Request pipeline (`app.ts`)

Order: `trust proxy` setting (from `TRUST_PROXY`) → `cors({ origin: allowedOrigins, credentials: true })` → `checkOrigin` → `/api` rate limit (`rateLimiters.api`) → `express.json()` → `req.body ??= {}` (Express 5 leaves it undefined for requests without a body; controllers destructure it) → `cookieParser()` → routers → `/uploads` static (with `X-Content-Type-Options: nosniff`) → JSON 404 for any unknown path (`"Route not found."`) → error handler (see Business logic).

Origin check (`middleware/origin.middleware.ts`), defence in depth against CSRF next to the `sameSite: "strict"` cookie: `allowedOrigins` is `CLIENT_ORIGIN` split on commas, parsed once at startup and shared with `cors()`. For `POST`, `PUT`, `PATCH` and `DELETE`, the `Origin` header (or, when it is missing, the origin of the `Referer`) must be one of them, otherwise 403 `"Request origin not allowed."` (an unparseable `Referer` is refused too). A request with neither header (non-browser clients, supertest) passes; `GET`, `HEAD` and `OPTIONS` are not checked. No CSRF token library is used.

Rate limits (`middleware/rateLimit.middleware.ts`, `express-rate-limit`): over the limit the answer is 429 `{ error: "Too many requests. Please try again later." }` with the standard `RateLimit`/`RateLimit-Policy` headers (draft-8) and `Retry-After`.

| Limiter | Where | Limit | Key |
|---|---|---|---|
| `api` | everything under `/api` | 1000 per 15 min | IP |
| `login` | `POST /api/auth/login` | 10 **failed** attempts per 15 min (a successful login gives its slot back) | IP + lowercased email |
| `password` | `PUT /api/users/me/password`, `PATCH /api/admin/users/:id/password`, `PATCH /api/company/branches/:id/password` | 10 per 15 min | user |
| `upload` | `POST /api/users/me/logo`, `POST /api/company/me/logo`, `POST /api/products/images`, `POST /api/products/import` (one shared count) | 30 per hour | user |
| `forgotPassword` | `POST /api/auth/forgot-password` | 10 per hour; over it the answer is the **normal 200** and nothing is sent (not 429) | IP |

The per-user limiters run after `authenticate` and before multer, so a refused upload is never read. The general limit is far above normal use (notifications are polled every 50 s, a page loads several endpoints). Behind a proxy `req.ip` is the proxy's address unless `TRUST_PROXY` is set, and then every user would share one limit. The counters live in memory (one per limiter), which is right for one instance; more instances would need a shared store (for example Redis via `rate-limit-redis`). Under Vitest (`NODE_ENV=test`) the limiters are skipped, and so they are with `DISABLE_RATE_LIMITS=true` (the e2e server, see E2E tests in `docs/frontend.md`; the server logs a warning at startup when it is set); `tests/rateLimit.test.ts` mocks the module with `createRateLimiters(lowLimits, true)` and empties the counters after each test.

Routers: `/api/delivery/webhooks` (mounted before `express.json()`, see Delivery webhooks), `/api/auth`, `/api/products`, `/api/orders`, `/api/cart`, `/api/users`, `/api/notifications`, `/api/favorites`, `/api/product-templates`, `/api/reports`, `/api/donations`, `/api/admin`, `/api/announcements`, `/api/credits`, `/api/stats`, `/api/cities`, `/api/company`, `/api/events` (see Live events), and outside production `/api/delivery` (the mock courier, see Delivery webhooks)

Routes chain `authenticate` → `authorize('<ROLE>', ...)` (one or more allowed roles) → controller. Every store/restaurant route names its roles (`authorize('STORE', 'RESTAURANT')` where both are allowed), so an `ADMIN` reaches only `/api/admin`, `/api/notifications`, `GET`/`PUT /api/users/me` and `/api/auth`. The admin router applies `authenticate, authorize('ADMIN')` to all of its routes with `router.use`. A `COMPANY` (headquarters) user reaches only `/api/auth`, `GET`/`PUT /api/users/me`, `PUT /api/users/me/password`, `/api/notifications`, `/api/announcements`, `GET /api/cities` (its branches' cities) and `/api/company`; every store, restaurant, admin and `/api/credits` route rejects it with 403 through its `authorize` list (its branches' credits are under `/api/company`).

## Auth

- `register`: kept for the planned public roles (individuals, public kitchens, humanitarian organizations), none of which exists yet (`PUBLIC_ROLES` is empty). It validates first_name, last_name, email, password and role first, then answers 403 `"Store and restaurant accounts are created by an administrator."` for `STORE`, `RESTAURANT`, `ADMIN` and `COMPANY` and 400 `"Role is not valid."` for anything else. Store, restaurant and admin accounts are created by an admin (`POST /api/admin/users`, with an invitation email or a temporary password).
- `login`: bcrypt compare; a blocked account (checked only after the password matched, so a block is not revealed to someone without the password) gets 403 `"Your account is blocked. Reason: <reason>"` and no cookie. The **effective block** applies: the account's own block (with its reason) comes first, otherwise a blocked company blocks its users with the company's reason, and a deactivated branch gets 403 `"This branch has been deactivated. Contact your company."`; `setSessionCookie` (`utils/session.ts`): `jwt.sign({ id, role, sv: session_version }, JWT_SECRET, { expiresIn: "7d" })`, sets cookie `token` (`httpOnly`, `secure` only when `NODE_ENV === "production"`, `sameSite: "strict"`, 7-day `maxAge`). Returns `{ message, user: { id, first_name, last_name, email, role } }`. Wrong email and wrong password return the same message.
- `logout`: `clearCookie` with the same options. `GET /auth/me` returns only the token payload (`{ id, role }`); the client uses `GET /users/me` for full data.
- `authenticate`: reads `req.cookies.token`, `jwt.verify`, rejects non-object payloads, then reads `users.role`, the effective block (`NOT notBlocked("users")`: the user's own flag or its company's) and `users.must_change_password` for the token's id (one query per request). A missing user, or a token whose `sv` differs from `users.session_version` (a token without `sv`, from before session versions, counts as 0), is 401 `"Token is invalid or has expired."`: raising the version (a password reset) signs out every session of the user; a blocked one 401 `"Your account is blocked."` (so blocking an account or its company ends a session at once). While `must_change_password` is set (a temporary password from an admin), only `GET /api/auth/me`, `GET`/`PUT /api/users/me`, `POST /api/users/me/logo`, `PUT /api/users/me/password` and `GET /api/cities` (for the profile form) pass (`ALLOWED_BEFORE_PASSWORD_CHANGE`, matched on method + path without the query string); everything else is 403 `"You must change your password before continuing."`. This also applies to an existing session once an admin resets the password. The login response includes `must_change_password`. `req.user` (`AuthUser = JwtPayload & { id: number; role: Role }`, `Role = 'STORE' | 'RESTAURANT' | 'ADMIN' | 'COMPANY'`) takes the role from the database, not from the token. Other failures are 401; a database error is 500.
- **Forgot password** (`password.controller.ts`, no session): `POST /forgot-password { email }` (rate limiter `forgotPassword`): a malformed email is 400 `"Email is not valid."`; otherwise the answer is always 200 `{ message: "If an account exists for this email, we sent a link to set a new password." }` (`FORGOT_PASSWORD_MESSAGE`), whether the account exists, is blocked (also a blocked company or a deactivated branch) or is over its limit, so it reveals nothing. For an active account with fewer than 3 reset tokens in the last hour (`RESET_LINKS_PER_HOUR`, counted in `auth_tokens`, so it holds across restarts and instances) it creates a `PASSWORD_RESET` token, queues the system email `PASSWORD_RESET` and logs `PASSWORD_RESET_REQUESTED` with the IP, in one transaction. `POST /reset-password/check { token }`: 200 `{ message: "The link is valid.", purpose }` or 400 `{ error: "This link is invalid or has expired.", code: "INVALID_LINK" }` (the page checks first, so the user does not type a password for nothing). `POST /reset-password { token, password }`: the password rule (400 with the usual message, the token stays usable), then in one transaction the token is locked (`FOR UPDATE`; two requests with one token: one wins, the other gets `INVALID_LINK`), the password hash set, `must_change_password` cleared and `session_version` + 1 (every session signed out), the token used and the user's other open tokens revoked, a `PASSWORD_CHANGED` notification (its email is a system email) and the account event `PASSWORD_RESET`. An `INVITATION` token is accepted the same way (password, flags, session version, token), but with no `PASSWORD_CHANGED` notification, the event `INVITATION_ACCEPTED` and `last_login_at` set, and the user is signed in at once (`setSessionCookie` with the new version): `{ message: "Your password was set. Welcome to Još vrijedi.", purpose: "INVITATION", user }` (the user as in the login response). For a reset the response clears this browser's cookie and answers `{ purpose: "PASSWORD_RESET", message: "Your password was changed. You can log in now." }`.
- **Tokens** (`services/authTokens.ts`, table `auth_tokens`): 32 random bytes as base64url (43 characters) go only into the email; the table stores `hashToken` (SHA-256, hex). `createAuthToken(db, userId, purpose, createdBy?)` revokes every open token of the user (any purpose) and stores the new one with `expires_at = NOW() + TOKEN_LIFETIME_MINUTES[purpose]` (`PASSWORD_RESET`: 60, `INVITATION`: 72 × 60). `services/accountEmails.ts`: `sendPasswordResetLink(client, userId, senderId?)` and `sendInvitation(client, userId, senderId, sender = "ADMIN")` (`sender` `COMPANY` when a headquarters invites a branch) create the token and queue its system email in the caller's transaction. `findValidToken(db, token, lock?)` finds it unused, unrevoked, unexpired and with an unblocked user (anything else, also a malformed or 200+ character token, is null). `consumeToken` sets `used_at` and revokes the user's other open tokens.
- `authorize(...roles)`: 403 with "You do not have the required role for this action." when the caller's role is not one of them (`authorize('STORE')`, `authorize('STORE', 'RESTAURANT')`).
- Controllers read `req.user!.id` (non-null assertion is safe because `authenticate` runs first).

## Database

Enum types: user role (`STORE`, `RESTAURANT`, `ADMIN`, `COMPANY`), admin action (`CREATE_USER`, `RESET_PASSWORD`, `BLOCK_USER`, `UNBLOCK_USER`, `REMOVE_PRODUCT`, `REMOVE_DONATION`, `CANCEL_ORDER`, `UPDATE_PROFILE`, `CREATE_ANNOUNCEMENT`, `END_ANNOUNCEMENT`, `APPROVE_CREDIT_REQUEST`, `REJECT_CREDIT_REQUEST`, `ADJUST_CREDITS`, `CREATE_COMPANY`, `UPDATE_COMPANY`, `BLOCK_COMPANY`, `UNBLOCK_COMPANY`, `DEACTIVATE_BRANCH`, `REACTIVATE_BRANCH`, `ATTACH_BRANCH`, `SEND_INVITATION`, `RESEND_INVITATION`, `SEND_PASSWORD_RESET_LINK`), the credit enums (`subscription_status`, `credit_transaction_type`, `credit_actor`, `credit_request_type`, `credit_request_status`, `credit_request_source`; values in the table below), announcement audience (`ALL`, `STORE`, `RESTAURANT`), product status (`Available`, `Sold`, `Expired`, `Removed`), `order_item_status` (the **item** status: `Pending`, `Confirmed`, `Completed`, `Rejected`, `Cancelled`). `Rejected` = refused by the store; `Completed` = picked up (set by the store, or by the courier's pickup for a delivery order); `Cancelled` = withdrawn by the restaurant, cancelled by the expiry job, moderation, a block or a closed branch, or by the store after a missed pickup. The order enums: `order_status` (the same five values, derived from the items, see Orders), `fulfilment_method` (`PICKUP`, `DELIVERY`), `order_change_reason` (`NOT_ENOUGH_STOCK`, `QUALITY`, `OTHER`), `order_event_source` (`RESTAURANT`, `STORE`, `ADMIN`, `SYSTEM`, `PROVIDER`: the delivery provider, whose pickup webhook completes a delivery order). Donation type (`FREE`, `SPONSORED`) and donation status (`Available`, `Expired`, `Removed`; claim and funding statuses come with the recipient roles). Category and unit are stored as codes in VARCHAR columns (validated against fixed lists, see Validation); labels are a frontend concern.

`DATE` columns (`expiry_date`) come back from `pg` as plain `YYYY-MM-DD` strings: `config/db.ts` overrides the default parser, which would turn them into a JS `Date` at local midnight and serialize the previous day in UTC+ time zones. Every pool session also runs with `timezone = APP_TIMEZONE`, so `CURRENT_DATE` is the local business day.

## API reference

Roles shown are the intent; confirm exact middleware in `src/routes/`.

### Auth `/api/auth`
`POST /register` (closed for every existing role, see Auth), `POST /login`, `POST /logout`, `GET /me` (authenticated), `POST /forgot-password`, `POST /reset-password/check`, `POST /reset-password` (no session; see Auth)

Emails are trimmed and lowercased on register, login and admin account creation (login matches `LOWER(email)`, so accounts created before this rule still log in). Register also requires a valid email format (`"Email is not valid."`; `isValidEmail` in `utils/accounts.ts`: at most 254 characters, no whitespace, exactly one `@`, a non-empty local part and a domain with a dot that is neither its first nor its last character, checked without a regex that could backtrack) and a password of at least 8 characters (`"Password must be at least 8 characters long."`); a duplicate, including one that only differs in case, is 400 `"A user with this email already exists."`. Login without email or password is 400 `"All fields are required."`.

#### Product images

- A product's and a template's `image_url` is `null` (the client shows its generic product image), `suggested:<key>` (one of the 9 suggested images: `meat`, `fish`, `dairy`, `vegetables`, `fruits`, `bakery`, `drinks`, `frozen`, `other`; the client holds the pictures) or `/uploads/products/<file>` uploaded by **the same store** (the file name starts with its id) that still exists. `utils/productImages.ts` → `parseProductImage(value, storeId)` checks it for products and templates (400 `"Image is not valid."`), so a client can never store an outside URL. CSV imports set no image. Cart lines carry `image_url` too.
- `releaseProductImage(db, url)` deletes an upload no product or template references any more; it runs after a product edit or template save replaces an image and after a template is deleted. Products are never deleted (only `Removed`), so an image stays as long as its product.
- `services/storage.ts` is the only code that knows where files live (local disk under `UPLOADS_DIR`, served at `/uploads` with `nosniff`): `saveImage(kind, file, namePrefix)` (kinds `logos` and `products`; the extension comes from the checked MIME type and a random part is added), `removeStoredFile(url)` (ignores anything that is not one of our uploads and a missing file), `storedFileName`, `storedFileExists`, `listStoredFiles`. Moving to cloud storage at the deploy changes only this file.
- **Weekly hours** (`utils/schedule.ts`): `{ mon: { open: "08:00", close: "20:00" } | null, ..., sun }`, one interval a day (no overnight hours), `HH:MM` with `24:00` allowed as a closing time, opening before closing, all seven days present and nothing else. `parseSchedule(value)` (undefined = not sent, null = clear, else the schedule or `{ invalid: true }`), `localWeekdayAndTime(now)` and `isOpenAt(schedule, now)` (open from the opening time until just before closing; a closed day is false; no schedule is null). `openStateAt(schedule, now)` adds when that changes (`{ open_now, closes_at, opens_at, opens_on }`, the shape of the client's `openState`), for Search (`GET /products/by-store`). Lists that show hours return the schedule: `GET /users/stores` and `/favorites` (both), `GET /products/:id` (`store_pickup_schedule`), `GET /orders/pickups` (`party_pickup_schedule`), `GET /orders/:id` (each party's `pickup_schedule`), the admin's user pages and a branch's page (both).
- **Upload cleanup job** (`jobs/cleanupUploads.ts`, daily at 03:30 `APP_TIMEZONE`, started from `server.ts` only): `removeUnusedProductImages()` deletes product uploads older than a day that no product or template uses (an upload whose form was never saved). `available_quantity` on `GET /`, `GET /mine` and `GET /:id` also subtracts shop sales (`availableQuantity`); `GET /mine` and the owner's `GET /:id` add `sold_in_shop` (others never get it).

#### CSV import

- `uploadCsvFile` (multer memory storage, nothing is written to disk) accepts one file in field `file`, at most 1MB (`MAX_CSV_SIZE_MB`), with a `.csv` extension and a MIME type of `text/csv`, `application/csv`, `application/vnd.ms-excel`, `text/plain` or `application/octet-stream` (browsers disagree on the type of a .csv). Otherwise 400 `"Only CSV files are allowed."` / `"The file can be at most 1MB."`; no file → 400 `"A CSV file is required."`. Logo and CSV uploads share the `handleUpload` wrapper, which turns multer errors into 400 JSON.
- `utils/productCsv.ts` → `parseProductCsv(buffer)`: columns `name, description, category, original_price, discounted_price, quantity, unit, expiry_date` (`CSV_COLUMNS`; header names are trimmed and lowercased, order does not matter, `description` is optional). The delimiter (`,` or `;`) is read from the header line, so a `;` file can use an unquoted decimal comma. A UTF-8 BOM is skipped and empty lines are ignored. Values are normalized before `validateProductFields`: `2,50` → `2.50`, and the expiry date → `YYYY-MM-DD` from any form Excel writes when it saves a CSV (a cell longer than 40 characters is left as it is and rejected, before the time-part patterns, which would backtrack on long input): a time part (`T...`, ` 00:00:00`, ` 12:00 AM`), spaces and a trailing dot are dropped, then `YYYY-M-D` / `YYYY.M.D` / `YYYY/M/D` (year first), `D.M.YYYY` / `D-M-YYYY` (day first, also with a 2-digit year → `20YY`), `A/B/YYYY` (day first, unless some slashed date in the same file only works month first, like `12/25/2026`; then the whole file is read as US `M/D/YYYY`), and a 5-digit Excel serial (days since 1899-12-30). Anything else is left as is, so the validator rejects it. Category and unit are the server codes (`Meat`, `kg`).
- File-level errors (400): `"The CSV file could not be read."` (e.g. an unclosed quote), `"The CSV file does not contain any products."`, `"The CSV file is missing columns: ..."`, `"The CSV file can contain at most 500 products."` (`MAX_CSV_ROWS`).
- All or nothing: every row is validated first. If any fails, the response is 400 `{ error: "The CSV contains invalid rows.", rowErrors: [{ row, error }] }` (`row` is the line number in the file, header = 1) and nothing is inserted. For an invalid date the row error quotes the raw value: `Expiry date is not valid: "<value>". Use the format 31.12.2026.` (the plain `POST /` message is unchanged). Otherwise all rows are inserted in one transaction.

### Validation

- `utils/validateProduct.ts`: `validateProductFields` (create and update) returns an English error string or `null`:
  - required: name, category, original_price, discounted_price, quantity, unit, expiry_date (description optional) → `"All fields are required."`
  - category and unit must be in `CATEGORIES` / `UNITS` (keep in sync with `client/src/utils/categories.ts` and `units.ts`) → `"Category is not valid."`, `"Unit of measure is not valid."`
  - prices and quantity must be numbers above 0 → `"Prices and quantity must be positive numbers."`
  - discounted_price may not exceed original_price → `"Discounted price cannot be higher than the original price."`
  - expiry_date must be a real `YYYY-MM-DD` date → `"Expiry date is not valid."`, and not before today in `APP_TIMEZONE` → `"Expiry date cannot be in the past."`
- `validateTemplateFields` applies the category/unit lists and checks optional numbers when they are given.
- `utils/params.ts`: `parseId` (positive integer or `null`), `parseNumber`, `parseNonNegativeInt`. A non-numeric `:id` returns the resource's normal 404 instead of a Postgres cast error.
- `utils/dates.ts`: `APP_TIMEZONE`, `todayInAppTimezone()`, `isValidDate`, `isValidDateTime`.

**The service** (`services/orders/`):
- `codes.ts`: `generateOrderCode` (4 characters of `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` with `crypto.randomInt`), `formatOrderCode` (`#K7PM`), `parseOrderCode` (search input), `insertOrder` (`ON CONFLICT (store_id, code) DO NOTHING`, at most 10 draws).
- `status.ts`: `ORDER_STATUSES` (with `InDelivery`: the courier has a delivery order's goods and has not delivered them), `deriveOrderStatus` (any item Pending → Pending, else InDelivery, else Completed, else Confirmed, else Rejected, else Cancelled), `syncOrderStatus(client, orderId, { source, actorId, reason })` (stores the derived status and writes the history row when it changed), `recordOrderCreated`, `recordItemChanges`, `DELIVERY_ANSWER_MINUTES` (15) and the `AUTO_REJECT_AT` SQL (when a Pending order is rejected automatically: a delivery order's `created_at` + 15 minutes, a pickup order's `pickup_at`; local time, compared with `LOCALTIMESTAMP`; the order lists and `GET /:id` return it as `auto_reject_at` while Pending, else null), `lockOrder` (with `is_past_answer_deadline` and `is_overdue`, the `IS_OVERDUE` SQL: a Confirmed **pickup** order whose pickup day has passed; late logic is only for pickup, so a delivery order is never overdue, has `days_overdue` 0 and is not in the pickup counts' `overdue`), `lockOrderItems` (the items with their products locked in ascending id), `moveItems`.
- `cascades.ts`: `cancelPendingOrders(client, where, values, recipient, { storeClosed })` cancels whole Pending orders matching a condition on `orders` (blocking a user or company, deactivating a branch; source `SYSTEM`) with one notification per order (`ORDER_CANCELLED_BY_ADMIN` or `ORDER_CANCELLED_STORE_CLOSED`); `lockOrdersHoldingProducts` and `cancelPendingItemsOfProducts(client, orders, productIds, "EXPIRED" | "REMOVED", event)` drop the Pending items of expired or removed products (each dropped product runs `absorbShopShortage` with the order, like `moveItems`): an order with partial fulfilment off, or with nothing left, is cancelled whole; the restaurant gets `ORDER_ITEMS_EXPIRED`/`ORDER_EXPIRED` or `ORDER_ITEMS_REMOVED`/`ORDER_CANCELLED_BY_ADMIN`.
- `actions.ts`: `cancelOrder`, `completeOrder`, `cancelOverdueOrder`, `adminCancelOrder` (the caller logs the admin action; a delivery whose courier may still come is cancelled with the provider first, `cancelOpenDelivery`, and kept as CANCELLED `CANCELLED_BY_ADMIN` even when the provider refuses), `switchToPickup`, `cancelFailedDelivery`.
- `queries.ts`: the lists, counts and details above.
- **Locking:** every order path locks the order(s) first (ascending id), then the products (ascending id), then the store's subscription. Paths that start from products (expiry, moderation) lock the affected Pending orders first (`lockOrdersHoldingProducts`).
- `queries.ts` also serves the admin (`listAdminOrders`, and `getOrderDetails(orderId, null)`, which skips the party check) and the headquarters (`listStoreOrders` for a branch).

### Cart `/api/cart` (RESTAURANT)

`controllers/cart.controller.ts` over `services/cart.ts`. Every success answers the whole cart as `{ message, cart }`: `{ store: { id, business_name, orders_paused, orders_paused_until } | null, items, totals: { lines, total }, pending_orders, max_pending_orders }`. Each line has the product fields (`product_id`, `name`, `category`, `unit`, `expiry_date`, `original_price`, `discounted_price` (current)), `quantity`, `unit_price_seen`, `available_quantity` ("0" when unavailable), `added_at` and `flags`: `unavailable` with `unavailable_reason` (`REMOVED`, `EXPIRED`, `STORE_UNAVAILABLE` (blocked, its company blocked, a deactivated branch), `SOLD_OUT` (Sold or nothing free), checked in that order), `quantity_exceeds` (free < the line's quantity), `price_lowered` and `price_raised` (the current price against `unit_price_seen`, in cents). `totals.total` is what would be sent now: available lines without a higher price, at most the free quantity, at the current price. Lines come in the order they were added.

| Endpoint | Behavior |
|---|---|
| `GET /` | The cart. `"Cart fetched successfully."` |
| `GET /delivery` | The delivery choice (delivery phase 2): whether the cart's store can deliver to the restaurant now, today as soon as possible (`services/deliveryQuote.ts`). 400 `"The cart is empty."`. `{ message: "Delivery checked.", delivery }` with `{ available: true, price, estimated_pickup_at, estimated_delivery_at }` (the provider's quote for the cart's `totals.total`, ready after the store's `preparation_minutes`) or `{ available: false, reason }`, checked in this order: `STORE_NO_DELIVERY` (delivery off), `STORE_PAUSED`, `STORE_CLOSED` (closed now by its weekly hours; no weekly hours counts as open), `STORE_NO_LOCATION`, `RESTAURANT_NO_LOCATION` (no pin), then the provider's `OUT_OF_ZONE` / `UNAVAILABLE`. ### Users `/api/users`
- `GET /me`: full profile (explicit column list, never `password_hash`), including `must_change_password`, `company_id`, `company_name`, `company_logo_url` (the company's logo; a `COMPANY` user's avatar, and a branch's when it has none) and `company_description`. `logo_url` and `description` are the user's own (not resolved).
- `PUT /me`: updates profile through `updateProfile(db, userId, role, body)` (exported, also used by the admin's `PUT /admin/users/:id/profile`). Required: first_name, last_name, business_name, city_id, address, phone (400 `"First name, last name, business name, city, address and phone are required."`). `city_id` (a number or a numeric string) must be a city from the list, otherwise 400 `"Invalid city."`. The response's `user` has `city_id` and `city` (the name; `CITY_NAME` in `utils/cities.ts`, a subquery, because `RETURNING` cannot join). The other fields use `COALESCE`, so they cannot be cleared back to null, except the weekly hours: `opening_schedule` and (stores only; ignored for a restaurant) `pickup_schedule` are left as they are when not sent, cleared with `null`, else checked by `parseSchedule` (400 `"Opening hours are not valid."` / `"Pickup hours are not valid."`). `location` works the same way (not sent keeps the pin, `null` clears it), otherwise `{ latitude, longitude }` as numbers (`parseLocation`; anything else, a missing or out-of-range coordinate, is 400 `"Location is not valid."`), rounded to 6 decimals and at most `MAX_KM_FROM_CITY` (30) km from the centre of the profile's city (`kmFromCity`, after a branch's locked city is applied; 400 `"The location on the map is too far from the chosen city."`). The response has `latitude` and `longitude` (null without a pin). For an `ADMIN` only `first_name` and `last_name` are read (both required, 400 `"First and last name are required."`); the response has `id, first_name, last_name, email, role`. For a `COMPANY` user only `first_name`, `last_name` and `phone` (all required, 400 `"First name, last name and phone are required."`); the response adds `phone` and `company_id`. Sets the caller's `email_notifications` and answers `{ message: "Email notifications turned on." | "Email notifications turned off.", email_notifications }`. `GET /me` returns `email_notifications`.
- `PATCH /me/order-settings` (STORE): a store's order settings, each saved at once (see Store order settings). Body: any of `delivery_enabled` (boolean), `preparation_minutes` (15, 30, 45, 60, 90 or 120), `orders_paused` (boolean) with an optional `orders_paused_until` (ISO date-time with `Z` or an offset, after now and at most `MAX_PAUSE_DAYS` = 30 days ahead; ignored when `orders_paused` is false, which clears it). - `POST /me/logo` (STORE, RESTAURANT): `uploadLogoFile` (multer, single file field `logo`, JPEG/PNG/WEBP, max 5MB) stores `/uploads/logos/<userId>-<timestamp>-<random>.<ext>` in `logo_url` through `services/storage.ts` (a `COMPANY` user's company logo, `POST /api/company/me/logo`, is named `company-<userId>-<timestamp>-<random>.<ext>`). The extension comes from the checked MIME type, never from the uploaded file name, and `/uploads` is served with `nosniff`, so an uploaded file can only ever be an image. The previous logo file is deleted. Rejected uploads answer 400 JSON: `"Only JPEG, PNG and WEBP images are allowed."`, `"The image can be at most 5MB."`; no file: `"No image was uploaded."`.
- `GET /stores` (RESTAURANT): store list without blocked stores and stores that have no `business_name` yet; filters `city_id` (see the products filter), `business_name`, `favorites=true` (only the caller's favorite stores; an empty value means no filter, anything else → 400 `"Invalid filter."`), `radius` (as on `GET /products`, but a `city_id` keeps it, see Nearby offers). Each store has `distance_km`: `businessDistance("me", "users")` (`utils/location.ts`), the straight line between the restaurant's and the store's map pins rounded to one decimal, or the city distance (whole km) when either has no pin; the sort and the radius use the same distance. `max_discount` (integer): the biggest discount of its products on offer now in whole percent, 0 without offers (a subquery in the list, no request per card). `sort`: `distance` (default: nearest first, then by name) or `name` (by name only); anything else → 400. Paged (default 12, `{ message, stores, total, outside_radius_count }`). Each store has `active_products` (COUNT, a string): its products on the marketplace right now (`onOffer`: sellable and with a free quantity above 0), so the card matches the store's offers and `orders_paused` / `orders_paused_until`. The restaurant dashboard's store carousel asks `radius=all&limit=20` (nearest first from all cities).
- `GET /stores/:id` (route: STORE, RESTAURANT; the controller returns 403 for STORE, so in practice restaurants only; 404 for a blocked store): returns `{ store, stats }`. `store` has the resolved logo and description, `opening_schedule`, `pickup_schedule`, the order settings `delivery_enabled`, `preparation_minutes`, `orders_paused` / `orders_paused_until` (the pause now), `distance_km` from the restaurant (as on the list) and `open_now` (`isOpenAt(opening_schedule)` in `APP_TIMEZONE`: true/false, null without weekly hours). `stats` = `{ active_offers, expiring_today, max_discount }` (integers) over the store's products on offer now (`onOffer`, not expired, as the marketplace): how many, how many expire today, and the biggest discount in whole percent (0 without offers). The offers themselves come from `GET /products?store_id=`, and the restaurant's orders at the store from `GET /orders/mine?store_id=&scope=all&sort=newest` (paged, its `total` is the tab's count).

### Stats `/api/stats` (RESTAURANT, STORE)
`GET /store-home` (STORE only; other roles 403): the store home page's data in one request (`getStoreHome` in `services/storeHome.ts`), `{ message: "Store home fetched successfully.", today, orders, products }`; 500 `"An error occurred while fetching the store home."`.
- `today` (`countStoreToday` in `services/orders/queries.ts`): `pending` (Pending orders) and `first_deadline` (the earliest `AUTO_REJECT_AT` among them); `to_prepare` (Confirmed, ready time (`READY_TIME`, as the packing list: a delivery's `ready_at`, else `pickup_at`) today and still ahead) with `first_ready_at`; `hand_over_courier` / `hand_over_pickup` (Confirmed with the ready time passed, missed days included, by `fulfilment_method`; a delivery leaves once InDelivery). An order is in at most one of these. `expiring_today`: Available products expiring today with free quantity.
- `orders` (`listUrgentPendingOrders`): the 4 (`STORE_HOME_ORDERS`) Pending orders with the closest `AUTO_REJECT_AT`, then the oldest; list rows (`ORDER_COLUMNS`, all items) with the restaurant's `business_name`, `city` and `party_logo_url`.
- `products`: the 4 (`STORE_HOME_PRODUCTS`) Available, unexpired products with free quantity, soonest `expiry_date` first (then id), with `description`, `quantity`, `available_quantity`, `reserved_quantity` (Pending, Confirmed and InDelivery items) and `days_until_expiry`. The home's price editor saves through `PUT /products/:id`.

`GET /my-impact` (RESTAURANT and STORE; other roles 403): the home page's stats, always the caller's own numbers. A restaurant gets `{ message: "Impact stats fetched successfully.", impact: { food_kg, co2_kg, savings } }`, all numbers, not rounded (the client formats them). `getRestaurantImpact` (`services/impactStats.ts`) reuses `getSavedTotals` with `{ restaurantId }`, which adds `order_items.restaurant_id = $1` to the same query, so the rules are those of the admin stats and the impact report: `Completed` items only, with their accepted quantities. `food_kg` = kg + l (g/1000 and ml/1000 included; a litre counts as a kilogram; kom and pak are left out). `co2_kg` = `food_kg × CO2_KG_PER_FOOD_KG`, a named constant (2.5) marked in the code as an estimate to verify before launch. `savings` = Σ `GREATEST(original_price − unit_price, 0) × quantity` with the product's current full price, rounded to 2 decimals, the same as the purchases and impact reports. Always the restaurant's own numbers: one that has picked nothing up gets zeros. A **store** gets `impact: { food_kg, co2_kg, revenue }` from `getStoreImpact`, the same query with `{ storeId }` (adds `products.store_id = $2`): what restaurants picked up from it (`Completed` items of any restaurant), `food_kg` and `co2_kg` as above, and `revenue` ("Vraćeno u kasu") = Σ `unit_price × quantity`, the agreed prices (a later price change does not alter it), rounded to 2 decimals (the query's `value`). A store with no pickups gets zeros. Errors: 500 `"An error occurred while fetching impact statistics."`.

### Cities `/api/cities` (STORE, RESTAURANT, ADMIN, COMPANY)

### Nearby offers (radius and distance)
Restaurants see offers and stores near their own city first. Rules (`GET /products` and `GET /users/stores`):
- **Distance** = `city_distance_km(from_city, to_city)`, a SQL function (in the baseline migration): the straight-line (Haversine, R = 6371) distance in **whole km** between the two cities' centres, not addresses, so the same city is 0 and 5 km usually means the own city. NULL when either id is null or unknown. It is the one place the formula lives; queries build the call with `cityDistance(from, to)` from `utils/cities.ts` (later features such as branches and donations reuse it). From Visoko: Breza 7, Ilijaš 9, Kakanj 16, Sarajevo 24, Zenica 32.
- **The store list and the store page** use `businessDistance(from, to)` (`utils/location.ts`) instead: `pinDistance` (the same haversine between the two businesses' map pins, also used by `GET /products/home`) and the city distance when either has no pin.
- The starting point is the **restaurant's** `city_id` (`userCityId`), passed as a parameter (on the store list the restaurant is joined as `me`). A store calling `GET /products` gets `distance_km` null and no radius.
- **Radius** (`parseRadius`): 5, 10, 20 or 50 km or `all`; missing = 10 (`DEFAULT_RADIUS`). Rows farther than the radius are left out, and `outside_radius_count` counts the rows that match every other filter but lie beyond it (a second COUNT with `>` instead of `<=`).
- The radius is **not applied** (and `outside_radius_count` is 0) with `radius=all`, a `city_id` filter on `GET /products` (choosing a city is explicit; the store list keeps the radius with a city, so a restaurant can narrow its own city, and its client sends `radius=all` for another city), `store_id` (a store's profile shows all its offers), `favorites=true` on the store list, or when the restaurant has no city yet.
- Several stores in range (e.g. later two branches of a chain) all show, sorted by distance.

### Live events `/api/events` (any logged-in user)
Delivery phase 2: Server-Sent Events, so the order pages and the notification bell update without reloading (`controllers/events.controller.ts`, `live/`).
- `GET /` (behind `authenticate`, so 401 without a login and 403 with a temporary password) answers `text/event-stream` (`Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no` for proxies), first `retry: 10000` and the event `ready`, then the caller's events, each `event: <kind>` with `data:` JSON: `order` `{ kind, order_id }` (an order of the caller, one of its items or its delivery changed), `notification` `{ kind }` (the caller got a notification) and `resync` `{ kind }` (events may have been missed: reload). An event names what changed, never its content; the client loads that through the API, which checks access as usual. A `: ping` comment every 25 s (`HEARTBEAT_MS`) keeps the stream open, and the stream ends when the login token expires (the browser's reconnect then gets 401). At most 10 streams per user (`MAX_STREAMS_PER_USER`, one per tab); another one closes the oldest.
- Where the events come from: the live event triggers (`notify_order_change()` after INSERT or UPDATE on `orders`, `order_items` and `deliveries`, with the order's `store_id` and `restaurant_id`; `notify_new_notification()` after INSERT on `notifications`) call `pg_notify('live_events', json)`. Postgres delivers a NOTIFY only when its transaction commits and once per identical payload in a transaction, so a rolled-back change sends nothing and a decision on many items one `order` event. Nothing in the services sends events, so a new way of changing an order needs no extra code.
- `startLiveListener()` (`live/listener.ts`, from `server.ts` only; the tests start their own) keeps one dedicated connection (`application_name` `josvrijedi-live-events`, not from the pool) with `LISTEN live_events` and passes each event (`parseLiveEvent`, which drops anything malformed) to the open streams of its `user_ids` in this process (`live/hub.ts`: `addStream`, `removeStream`, `sendToUsers`, `sendToAll`). A lost connection is retried every 5 s and then every open stream gets `resync`. Every server instance listens, so this works with several instances.

### Reports `/api/reports` (STORE, RESTAURANT)
Downloadable CSV reports. Both cover only **Completed** order items whose `picked_up_at::date` is between `from` and `to` (local day, the session runs in `APP_TIMEZONE`). Ownership is `pickupOwnership(role)` in `services/reports.ts`: a store gets the items on its products, a restaurant its own; `parties` is the other side.
- Query: `from`, `to` (`YYYY-MM-DD`, required, `from <= to`, at most 366 days including both ends; otherwise 400 `{ error: "Invalid period." }`) and optional `lang` (`en`; anything else means `bs`) for the column headers, category labels, the total label and the file name. Reports are files read outside the app, so they follow the UI language rather than the English-only rule for server text.
- Success: 200 with `Content-Type: text/csv; charset=utf-8` and `Content-Disposition: attachment; filename="<name>-<from>-<to>.csv"` (not the usual JSON). Errors stay JSON; 500 `"An error occurred while generating the report."`.
- `GET /sales`: one row per picked-up item, ordered by `picked_up_at`, then order and item: pickup date, the order's code (`#K7PM`, column "Narudžba" / "Order"; the items of one order share it), product, category label, other party (`business_name`, else first + last name, else email), its city, quantity, unit, `unit_price`, the product's **current** `original_price` (there is no snapshot of it), total (`unit_price × quantity`), savings (`(original_price − unit_price) × quantity`, never negative). Last row: totals of the two money columns (quantities have mixed units). File name `prodaja`/`sales` for a store, `kupovine`/`purchases` for a restaurant.
- `GET /impact`: one row per month (`YYYY-MM`) plus a total row (`GROUPING SETS`, so partners are counted once over the whole period): pickups (distinct **orders**: an order with three items is one pickup), distinct partners (restaurants for a store, stores for a restaurant), food in kg (g/1000), l (ml/1000) and pieces (kom + pak) like the admin statistics, value and savings in KM. An empty period still has the total row with zeros. File name `uticaj`/`impact`.
- `utils/csv.ts` → `toCsv(headers, rows)`: UTF-8 BOM, `;` delimiter, CRLF, integers as they are and other numbers with two decimals and a decimal comma (`2,50`), so Bosnian Excel splits the columns and reads the numbers; cells with `;`, `"` or a line break are quoted; text starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'` (CSV formula injection: product and business names are user input). `utils/reportLabels.ts` holds the headers and category labels per language.
- The queries and helpers are shared with the company reports (`services/reports.ts`): `parsePeriod`, `sendCsv`, `salesRows(scope, owner, period, lang, { withBranch })` and `impactRows(scope, owner, period, lang)`, where a `PickupScope` is `{ owner, partyJoin }` (`pickupOwnership(role)` here, `storesScope()` for a set of store ids), plus `IMPACT_COLUMNS`, `PICKED_UP_IN_PERIOD` and `impactCells`.
- Adding a report: a query in `services/reports.ts` (or the controller), its headers in `reportLabels.ts`, a route, and an entry in the client's `REPORTS` list (for a company report: `companyReports.controller.ts` and `CompanyReportsPage`).

### Donations `/api/donations` (STORE and RESTAURANT)
Donation offers of the humanitarian module. `FREE` = given away; `SPONSORED` = given at `donation_price`, which a third party will pay. Until the recipient roles exist, a donation is visible only to its donor (`donor_id = req.user.id`).
- `POST /`: create; `donor_id` from `req.user`. 201 `{ message: "Donation published successfully.", donation }`.
- `GET /mine`: own donations except `Removed`, `Available` first, then newest. Filters `type`, `status` (`Available`/`Expired`), `name` (ILIKE); anything else → 400 `"Invalid filter."`. Paged (default 12): `{ donations, total }`, each with `days_until_expiry`.
- `GET /:id`: own and not removed, else 404 `"Donation not found."`.
- `PUT /:id`: same body as create. 404, 403 `"You are not allowed to edit this donation."`, 400 `"Only active donations can be edited."` unless `Available`. 200 `{ message: "Donation updated successfully.", donation }`.
- `DELETE /:id`: soft delete (`Removed`), any status. 404, 403 `"You are not allowed to delete this donation."`, 200 `{ message: "Donation deleted." }`.
- `POST /from-product/:productId` (STORE only, "Prebaci u donaciju"): body `donation_type`, optional `quantity` (default: everything available), `donation_price` (SPONSORED). Stock-safe transaction with `FOR UPDATE` on the product. 404 `"Product not found."` (also for `Removed`), 403 `"You are not allowed to donate this product."`, 400 `"Only available products can be moved to donations."` (not `Available` or expired), 400 `"Quantity must be greater than zero."`, 400 `"Not enough product available."` when it exceeds `quantity − Pending − Confirmed − Completed`. The donation copies name, description, category, unit, `original_price` and `expiry_date` and stores `source_product_id`. A repeated move adds to the product's `Available` donation with the same `donation_type` and `donation_price` (locked `FOR UPDATE`): its quantity grows and the response is 200 `{ message: "Quantity added to the existing donation.", donation }`; a different type or price, or an earlier donation that expired or was deleted, gives a new donation. Then: nothing ordered and everything donated → product `Removed` and `refundForProduct` (its credit back on the day of the charge); otherwise `products.quantity` drops by the donated amount (order items keep theirs), `markSoldIfFullyConfirmed` may mark it `Sold`, and the credit stays spent. 201 `{ message: "Product moved to donations.", donation, creditRefunded }` (also on the 200 merge response).
- `POST /:id/return-to-product` (STORE only, undoes a move): one transaction that locks the donation and then its source product. 404 `"Donation not found."` (missing or `Removed`), 403 `"You are not allowed to edit this donation."`, 400 `"Only active donations from the offer can be returned."` (not `Available`, or no source product), 400 `"Product has expired and cannot be returned to the offer."`. The product becomes `Available` (also from `Sold` or `Removed`); its quantity grows by the donation's quantity, except for a `Removed` product, which kept its old quantity when everything was moved and is rebuilt as Pending + Confirmed + Completed + sold in shop + the donation's quantity (so exactly the donation becomes free again). The donation becomes `Removed`. A product that was `Removed` is published again and costs 1 credit (`chargeForProduct`; 402 rolls the whole return back), unless its last charge was never refunded (`hasOpenProductCharge`: the move came after the charge day), in which case that charge still covers it; returning to a product that stayed on offer is free. 200 `{ message: "Donation returned to the offer.", product }`.

Validation (`utils/validateDonation.ts`, `validateDonationFields` + `normalizeDonationFields`):
- Required: donation_type, name, category, quantity, unit, original_price, expiry_date → `"All fields are required."`. Category in `DONATION_CATEGORIES` (product categories + `Meals`), unit in `DONATION_UNITS` (product units + `portion`) → the product messages. Quantity and value above 0 → `"Quantity and value must be positive numbers."`.
- `validateDonationPrice` (also used by from-product): unknown type → `"Donation type is not valid."`; SPONSORED needs a price above 0 → `"Donation price is required and must be greater than zero."` and below the value → `"Donation price must be lower than the product's value."`. A FREE donation's price is stored as NULL.
- Expiry date as for products. Pickup times `HH:MM[:SS]` → `"Pickup time is not valid."`, start before end → `"Pickup start must be before pickup end."`.
- `allergens` must be codes from `ALLERGENS` (the 14 EU allergens) → `"Allergens are not valid."`; `serving_temperature` one of `HOT`, `COLD`, `FROZEN` → `"Serving temperature is not valid."`. Both are stored only for `Meals` and cleared otherwise.
- Keep the lists in sync with `client/src/utils/donations.ts`.

### Credits `/api/credits` (STORE)
Only stores pay credits: restaurants order for free, so the router allows only `STORE` (a restaurant gets the role 403).
Controller `credits.controller.ts`. Payment is offline, so every subscription and top-up is a request an admin approves. User responses never contain `admin_note` (`CREDIT_REQUEST_COLUMNS` leaves it out). A request row: id, user_id, request_type, plan_id, topup_package_id, period_month, auto_renew, status, source, created_at, reviewed_at, requested_by, company_note, company_reviewed_at, plan_name, credits, price. The request rules live in `services/creditRequests.ts`, shared with the headquarters' endpoints.

**Branches** (a STORE with `company_id`, `getManagingCompany`): their headquarters asks and pays for their plans (see Company credits). Their credits work exactly as for any store (balance, charges, refunds, history); only who asks changes. Independent stores and restaurants are unchanged. `credits` and `price` are the request's own snapshot, so a later plan change never alters what was quoted or what an approval grants.
- `GET /plans` → `{ plans }` (active, by credits: id, name, credits_per_period, price). `GET /topup-packages` → `{ packages }`.
- `GET /me` → `{ credits }` = `creditSummary`: `getBalance` (`periodStart`, `periodEnd`, `subscription`, `hasActiveSubscription`, `total`, `used`, `available`) + `nextSubscription` (next month's, or null) + `pendingRequests` (the open ones: PENDING, and for a branch COMPANY_REVIEW) + `managedByCompany` (true for a branch) and `companyName` (its company, else null).
- `GET /me/history?year=` (default the current credit year; 2000–2100, else 400 `"Invalid filter."`) → `{ history: { year, months: [{ month, hasSubscription, total, used }] × 12, categories: [{ category, used }] } }` (`getUsageHistory`: a charge refunded in its own month never counts, so the categories add up to the months).
- `GET /requests` → `{ requests, total }`, every status, newest first, paged (default 10).
- `POST /requests`: `request_type` `SUBSCRIPTION` (`plan_id`, `period` `current`/`next`, optional boolean `auto_renew`) or `TOPUP` (`topup_package_id`, always this month). 400 `"Request type is not valid."`, `"Period is not valid."`, `"Auto-renew must be true or false."`; 404 `"Plan not found."` / `"Top-up package not found."` (also for inactive ones); 400 `"You already have a subscription for this month."`, `"An active subscription for the current month is required to buy extra credits."`, and from the partial unique indexes (`23505`) `"You already have a pending subscription request for this month."` / `"You already have a pending top-up request."`. Notifies every admin in the same transaction. 201 `{ message: "Request sent.", request }`; `requested_by` is the user. A **branch**: `SUBSCRIPTION` → 403 `"Your company manages your plan."`; `TOPUP` (same validation and "active subscription this month" rule) is created as `COMPANY_REVIEW` with source `BRANCH` and goes to its headquarters instead of the admins (`BRANCH_TOPUP_REQUESTED` to every unblocked headquarters login); 201 `"Request sent to your company."`. The open-top-up index answers a second one (at the headquarters or the admin) with `"You already have a pending top-up request."`.
- `DELETE /requests/:id`: withdraws an own PENDING request (`CANCELLED`; the status condition is part of the UPDATE, so it cannot race an admin's decision). 404 `"Request not found."`, 403 `"You are not allowed to withdraw this request."`, 400 `"Only pending requests can be withdrawn."`. 200 `{ message: "Request withdrawn.", request }`. A branch withdraws only a `COMPANY_REVIEW` top-up; a PENDING one (sent by its headquarters) → 403 `"Your company manages your plan."`.
- `PATCH /subscription/auto-renew` body `{ auto_renew: boolean }`: sets it on the user's current and future ACTIVE subscriptions (404 `"You do not have an active subscription."`) and on their PENDING `SUBSCRIPTION` requests (their own and the job's renewals), so approving one later keeps the user's choice. Nothing is cancelled: next month's approved plan or pending request stays, and with auto-renew off it simply does not renew after that month. Turned on in the renewal window (`isRenewalWindow`), it calls `createRenewals(client, now, { userId, explicit: true })` in the same transaction, since the job may already have run for the last time that month; a renewal the user withdrew earlier no longer blocks, one the admin rejected does. 200 `{ message: "Auto-renew turned on." | "Auto-renew turned off.", autoRenew, renewalCreated }`. The logic is `applyAutoRenew(client, userId, autoRenew)` (also used by the headquarters). A branch → 403 `"Your company manages your plan."`.

### Branches `/api/company/branches` (COMPANY)

Every `/:id` route answers 404 `"Branch not found."` for a branch of another company (or any user that is not one of the caller's stores), so their existence is not revealed. ### Company dashboard `/api/company/dashboard` (COMPANY)
The headquarters' overview (`controllers/companyDashboard.controller.ts`). ## Business logic worth knowing

- **Shop shortage** (`products.shop_shortage`, decimal ≥ 0, default 0): food the store's till sold that Pending items still hold. It does not change the available quantity (those items already hold it); it limits the store's decision and turns into shop sales as Pending quantity is freed. `decideOrder` (`checkShopShortage`) refuses an item that accepts more than its quantity minus the shortage: with partial fulfilment off 400 `"This order must be rejected: {product} was sold in your shop (only N kg left)."`; with it on 400 `"Not enough in stock for {product}: at most N kg can be accepted after the sale in your shop. Accept less or reject it."`, or `"Not enough in stock for {product}: it was sold in your shop and must be rejected."` when nothing is left. A shop sale recorded in the decision (`record_shop_sale`, `shop_sales`) lowers the shortage by its amount. Then `absorbShopShortage(client, productId, { orderId, actorId })` (`services/stock.ts`) runs for each product of the order: it locks the product, takes `min(shortage, freeQuantity)`, writes it as a shop sale with the order, lowers the shortage and marks an `Available` product Sold when covered (no notification). `moveItems` runs it too when Pending items become Cancelled or Rejected (the restaurant's cancel, an admin's cancel, blocking and removal cascades), so food the till sold never returns to the offer. The shortage is shown only to the owning store (`GET /products/:id` adds `shop_shortage` and `pending_quantity` for the owner, `/products/mine` has both, the marketplace strips it, and `GET /orders/:id` items have `shop_shortage` for the store and the admin only).
- **Available quantity** is computed, never stored (`services/stock.ts`: `heldByOrderItems`, `soldInShop`, `pendingHeld`, `availableQuantity` SQL for a product alias, `sellableProduct(product, store)` for whether restaurants can order it at all (Available, not expired, the store visible; used by sending and the cart), `onOffer(product, store)` = sellable and a free quantity above 0 (the store list's `active_products`; the marketplace list applies the same two conditions); `freeQuantity`, `heldQuantity`, `soldOutCover` for one product): `products.quantity` minus the sum of `Pending` + `Confirmed` + `Completed` item quantities (each item's current quantity, the accepted one once the store decided; picked-up food is gone, so completing must not free it) minus what the store sold in its own shop (`product_shop_sales`). Partial orders are allowed and the product stays `Available` until Confirmed + Completed items plus shop sales cover the full quantity (`markSoldIfFullyConfirmed`, `releaseSoldProduct`, both in `services/stock.ts`). Shop sales count in the marketplace, product details, my products, sending an order, the store's decision, the sold-out status, moving to donations and returning a donation to the offer (rebuilding a `Removed` product). They are never an app sale: reports, statistics and food saved ignore them, and the store profile's `sold_articles` counts a `Sold` product only when it has a Confirmed or Completed order item.
- **Stock-safe pattern** (`sendOrder`, `decideOrder`, `updateProduct`, shop sales): one transaction, `SELECT ... FOR UPDATE` on the product rows (ascending id) after the order's own lock, compute, write, `COMMIT`; `ROLLBACK` on any error (`inTransaction` in `utils/transaction.ts` for new code, or `pool.connect()`/`BEGIN`/`client.release()` in `finally`). Use the same pattern for anything that touches stock or an order's status, and keep the lock order of Orders. `markSoldIfFullyConfirmed(client, product)` marks a locked product `Sold` once Confirmed + Completed items and shop sales cover its quantity; `releaseSoldProduct(client, productId)` locks the product and turns a `Sold`, unexpired product back to `Available` once they no longer do (missed pickup, an admin's cancel of a Confirmed order).

The recipient is the user's email; the language is `bs` for every email (`DEFAULT_EMAIL_LANGUAGE`), because the users' language is not stored yet. `processEmailQueue({ transport, config, now?, batchSize?, db? })` (returns `{ sent, retrying, failed, skipped }`): first gives rows stuck in `SENDING` for over 10 minutes (a worker that stopped mid-send) back to `PENDING` (or `FAILED` at the maximum), then claims up to 50 due `PENDING` rows (`next_attempt_at <= now`, oldest first, `FOR UPDATE SKIP LOCKED` so several instances never take the same row) by setting `SENDING`, `attempts + 1` and `locked_at`, returning the recipient's current `email_notifications` and block. A row whose recipient is blocked by now, or (unless its template is a system one) turned email notifications off since it was queued, becomes `SKIPPED` (`last_error` = `The recipient is blocked.` / `The recipient turned email notifications off.`) and is never sent, even if the switch goes on again. Each other row is rendered, redirected and sent: success → `SENT` with `sent_at`; a send error → back to `PENDING` with `last_error` and `next_attempt_at` 1 min, 5 min, 30 min, then 2 h later (`RETRY_DELAYS_SECONDS`), and `FAILED` after the 5th attempt (`MAX_EMAIL_ATTEMPTS`); an unknown template or data that does not fit it → `FAILED` at once. Errors are logged and stay in the queue; they never reach the action that queued the email. `startEmailWorker(config)` (from `server.ts` only; tests call `processEmailQueue`) runs a pass at startup and every 5 s (`EMAIL_POLL_INTERVAL_MS`), never two at once, and logs a failed pass (`"Error while processing the email queue:"`).

Money is a two-decimal string in KM; times are ISO 8601.
  - **Interface** (`types.ts`): `DeliveryProvider { name, quote, createDelivery(request, idempotencyKey), getDelivery, cancelDelivery(id, reason), parseWebhook(rawBody, headers) }` and the contract's types: `DeliveryLocation`, `Quote`, `QuoteResult` (`{ available: false, code: "OUT_OF_ZONE" | "UNAVAILABLE" }` when delivery is not offered), `Delivery`, `DeliveryStatus` (`CREATED → COURIER_ASSIGNED → PICKED_UP → DELIVERED`, plus `FAILED` and `CANCELLED`) and `DeliveryEvent`. Refusals are `DeliveryError { status, code, message }` with the contract's codes. Their English messages are for logs and the provider and are never shown to users, which is why the module lives outside `services/`, the folder where the client test looks for UI texts.
  - **Config** (`config.ts`): `server.ts` calls `loadDeliveryConfig(env)` once, after the email config.   - **Webhook signature** (`signature.ts`): the headers are `X-JosVrijedi-Timestamp` (unix seconds) and `X-JosVrijedi-Signature: sha256=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>`. `verifyWebhook` refuses the following, all as 401 `INVALID_SIGNATURE`:
    - a missing or repeated header;
    - a timestamp more than 5 minutes from our clock in either direction (`WEBHOOK_TOLERANCE_SECONDS`);
    - a wrong digest (it checks for 64 hex characters, then compares with `timingSafeEqual`).

    `parseDeliveryEvent` (`contract.ts`) then checks the event's shape (400 `INVALID_EVENT`; `delivery.failed` needs a `failure_reason`). The webhook route verifies the **raw** body (`express.raw`, mounted before the global `express.json()`).
  - **Mock** (`mock.ts`, `MockProvider`): keeps its state in memory, so a restart forgets its deliveries, and `now` can be injected. Its rules are in `MOCK_RULES`:
    - distance is straight-line (`haversineKm` in `distance.ts`, the formula of `city_distance_km`);
    - the price is 3.00 KM + 0.70 KM per km, rounded to 0.10, and anything beyond 25 km is `OUT_OF_ZONE`;
    - the courier reaches the store 5 minutes after the later of the ready time and now, and delivers after 3 minutes per km + 5;
    - a quote is valid 10 minutes (`QUOTE_EXPIRED` after that, `QUOTE_NOT_FOUND` for an unknown one);
    - `cash_to_collect` must equal the goods plus the price, and the same idempotency key returns the same delivery;
    - cancelling works before the pickup (`ALREADY_PICKED_UP` or `DELIVERY_CLOSED` otherwise) and sends no webhook.

    `has(id)` and `remember(delivery)` let the dev courier take back a delivery the mock forgot on a restart. `simulate(deliveryId, type, { courier?, failureReason? })` plays the courier: it applies the status change (an out-of-order step is 409 `INVALID_TRANSITION`) and returns the signed webhook call `{ rawBody, headers }` the real provider would send.
- **Delivery at acceptance** (`services/orderDelivery.ts`, delivery phase 2): `createOrderDelivery(client, order, readyAt)` runs inside the decision's transaction. It quotes the accepted goods (the store's pin as pickup; the order's kept address and pin, the restaurant's name, phone and city as dropoff; `ready_at`), then calls `createDelivery` with that quote, `cash_to_collect` = accepted goods + price and the idempotency key `order-<id>`, and stores a `deliveries` row (CREATED, the final price, the cash, the provider's estimates); the order's `pickup_at` becomes the courier's estimated pickup and `delivery_estimated_at` the new estimate. Then:
  - `courier_assigned` (from CREATED or COURIER_ASSIGNED): the courier's name and phone, and `courier_assigned_at` (the event's `occurred_at`, kept from the first assignment);
  - `picked_up` (before the pickup): `picked_up_at`; a Confirmed delivery order becomes **InDelivery** (items InDelivery with `picked_up_at`, `orders.picked_up_at` = when the goods left the store, history source `PROVIDER`), without a notification; it stays the restaurant's active order (My orders, Pickups Today) and is the store's Pickups history;
  - `delivered` (from any open status; a missed pickup is applied first): `delivered_at`, the InDelivery items and the order **Completed** (source `PROVIDER`), `DELIVERY_DELIVERED` to both sides;
  - `failed` (any open status): FAILED with the provider's reason and `failed_at` (the event's time); before the pickup `DELIVERY_FAILED` (the order stays Confirmed until the restaurant chooses), after it `DELIVERY_FAILED_AFTER_PICKUP` (the order stays InDelivery until an admin cancels it);
  - `cancelled` (before the pickup): CANCELLED (`CANCELLED_BY_PROVIDER` without a reason), `failed_at`, and `DELIVERY_FAILED`. An admin's cancel (`cancelOpenDelivery`) also sets `failed_at`.

  An event that would move the delivery backwards is stored with `applied` false and answered `IGNORED`; a cancelled order's parties get no delivery notifications. Answers are 200 `{ message: "Webhook received.", outcome }` (`APPLIED`, `IGNORED`, `DUPLICATE`, `UNKNOWN_DELIVERY`), 500 `"An error occurred while processing the webhook."` (the provider retries). **Dev courier:** outside production `app.ts` mounts `POST /api/delivery/mock/orders/:id/simulate` (STORE, RESTAURANT; only the order's parties, else 404 `"Order not found."`; 404 `"Route not found."` with another provider). Body `{ event }`: `courier_assigned`, `picked_up`, `delivered`, `failed`, `cancelled` (else 400 `"This courier step is not valid."`); no created delivery → 409 `"This order has no delivery to simulate."`; a step the mock refuses → 409 `"This courier step is not possible now."`. It gives the mock back a delivery it forgot (from our row), calls `simulate` and sends the signed webhook through `receiveDeliveryWebhook`. `{ message: "Courier step simulated.", order }` (the order details).
- **Store order settings** (`utils/orderSettings.ts`, delivery phase 2): a store sets them on My profile (`PATCH /users/me/order-settings`) and an admin with the profile (`order_settings`); a branch's headquarters cannot. `delivery_enabled` decides whether the cart offers delivery, and `preparation_minutes` is the cart's quote and the preselected ready time when accepting. The pause is `orders_paused` with an optional end `orders_paused_until`; `ordersPaused(alias)` is the SQL for "paused now" (on, with no end or an end still ahead), so an end that passed needs no job to clear it, and `pauseColumns(alias)` shows the pause that way (`orders_paused_until` null when off). While paused, `sendOrder` refuses with 409 `STORE_PAUSED`; the products stay on offer and in carts, and orders already sent are not touched. The store page, the store list, Search and the cart show the pause.
- **Expiry job** (`jobs/expireProducts.ts`, started from `server.ts` only): `expireProducts()` finds the `Available` products past `expiry_date`, locks the Pending orders holding them, marks the products `Expired` (the store gets `PRODUCT_EXPIRED`) and cancels their **Pending** items through `cancelPendingItemsOfProducts` (one notification per order), all in one transaction. Confirmed items are left as they are: the store already agreed to hand that food over, and it closes them itself (complete, or cancel-overdue after a missed pickup). In the same transaction it deletes the cart lines of products past their expiry date for more than a day (`expiry_date < CURRENT_DATE - 1`) or `Removed` more than a day ago (`products.updated_at`), so the restaurant still sees for a day why a line became unavailable (lines of a blocked store stay), and `Available` donation offers past `expiry_date` become `Expired` (no notification yet, nobody but the donor sees them). `startExpirationJob()` runs it once at startup (to catch up on midnights missed while the server was down) and then on cron `0 0 * * *` in `APP_TIMEZONE`. Expiry checks in SQL use `expiry_date < CURRENT_DATE`, so a product is still valid on its expiry day.
- **Credit renewal job** (`jobs/creditRenewals.ts`, started from `server.ts` only): `runCreditRenewals(now)`, in one transaction, expires PENDING and COMPANY_REVIEW requests whose month has ended (`EXPIRED`, each requester gets `CREDIT_REQUEST_EXPIRED`, a branch's headquarters `BRANCH_CREDIT_REQUEST_EXPIRED`) and, in the renewal window (`isRenewalWindow`: the last `RENEWAL_DAYS_BEFORE` (2) days of a credit month), calls `createRenewals(client, now)`. `createRenewals` creates a PENDING `AUTO_RENEW` subscription request for the next month with the same plan for every ACTIVE subscription with `auto_renew` and notifies the admins and the user (`CREDIT_RENEWAL_CREATED`). Branches are renewed like any store (`requested_by` null). Skipped: blocked users (also deactivated branches and branches of a blocked company, via `notBlocked`), users who already have next month's subscription, a pending subscription request for it, or an earlier renewal for it in any status (so a withdrawn or rejected renewal is not created again; with `explicit` a withdrawn one does not block). An inactive plan is not renewed; its subscriber gets `CREDIT_RENEWAL_SKIPPED` instead. The insert uses `ON CONFLICT DO NOTHING`, so a request the user sends at the same instant skips only that row instead of failing the whole run. Returns `{ created, expired }`. `startCreditRenewalJob()` runs it at startup and on cron `10 0 * * *` in Europe/London.
- **Automatic rejection** (`jobs/autoRejectOrders.ts`, delivery phase 2, started from `server.ts` only): `autoRejectOrders()` rejects every Pending order past `AUTO_REJECT_AT` (a delivery order 15 minutes after sending, a pickup order at its pickup time), each in its own transaction: the order locked with `FOR UPDATE SKIP LOCKED` and checked again (a store deciding it at that moment goes first), then `lockOrderItems`, `moveItems` Pending → Rejected (the quantity is free again and covers a shop shortage, like the store's own rejection; `change_reason` stays null), `syncOrderStatus` with source `SYSTEM` (the only change to Rejected the system makes; the client shows it as an automatic rejection) and `ORDER_AUTO_REJECTED` to the restaurant and the store. A Pending delivery order has no delivery yet, so nothing is cancelled with the provider. Returns the count. `startAutoRejectJob()` runs it at startup and on cron `* * * * *` in `APP_TIMEZONE`, never two runs at once. The store's decision is refused past the deadline, so the minute before the job runs cannot change the outcome.
- **Reminder job** (`jobs/notificationReminders.ts`, started from `server.ts` only): `sendReminders()` inserts `PRODUCT_EXPIRING_SOON` and `ORDER_PICKUP_TODAY` (pickup orders only) with `INSERT ... SELECT ... WHERE NOT EXISTS` (same type for the same product or order), so each reminder is sent once no matter how often it runs; it returns `{ expiringSoon, pickupToday }` counts. `startReminderJob()` runs it at startup and on cron `0 7 * * *` in `APP_TIMEZONE`.
- **Soft delete and history:** orders and their items are never deleted (`order_status_history` keeps every change), products are marked `Removed`.
- **Pickups:** only the store moves a pickup order to `Completed` (`POST /orders/:id/complete`) or cancels a missed one (`cancel-overdue`); a delivery order becomes InDelivery with the courier's pickup and Completed with the delivery (webhooks). All act on the whole order (no partial pickup). Statistics of delivered or saved food (store profile counts, the home pages' impact numbers, admin food saved, reports) count only `Completed` (a delivery order once delivered). The stock held by orders (`heldByOrderItems`, `soldOutCover`), the product delete guard and the credit refund check count InDelivery like Confirmed.
- **Credits** (the product flows charge and refund as noted in the endpoint tables above; requests and approval are under Credits and Admin credits). Stores pay 1 credit per published product; restaurants pay nothing (orders are free, and nothing is refunded when one ends); donations are free. Controllers call the service inside their own transaction and answer a thrown `HttpError` (e.g. the 402) with `error.body()` in their catch. Where refunds happen: product delete and complete move to donations (same day, nothing ordered); never for an admin product removal (the store). The renewal job and every credit entry point (`/api/credits`, the admin adjust and ledger) are for stores only. Rules the service implements:
  - **Time:** credit days and months change at 00:00 **Europe/London** (01:00 Sarajevo, also across DST), computed in Node with `utils/creditTime.ts` (`creditDay`, `creditMonth` → `YYYY-MM-01`, `nextMonth`, `monthEnd`), never with `CURRENT_DATE` (the pool session runs in `APP_TIMEZONE`). Every service function takes `now` (default `new Date()`) so tests can move the clock, and writes it as `created_at`.
  - **Balance** (`getBalance(db, userId, now)` → `{ periodStart, periodEnd, subscription, hasActiveSubscription, total, used, available }`) is computed from the ledger rows of the current month, never stored: Total = plan + top-up grants + adjustments + refunds of charges from earlier months; Used = charges − refunds of same-month charges; Available = Total − Used, and 0 without an active subscription for the month (rows recorded for such a month count once the user subscribes in it). Unused credits never move to the next month.
  - **Charges** (`chargeForProduct`, `chargeForProducts` for the all-or-nothing CSV import) lock the user's subscription row for the month (`FOR UPDATE`), check the balance and insert one `-1` row per item with the category snapshot, all in the caller's transaction. Lock order: the order and the product first, then the subscription. No subscription or not enough credits → `InsufficientCreditsError`: 402 `{ error: "Not enough credits.", code: "INSUFFICIENT_CREDITS", hasActiveSubscription, actionUrl }` (`/my-profile#topup` with a subscription, else `/my-profile#subscription`). `HttpError` takes optional `details` that `body()` adds next to `error`.
  - **Refunds** find the newest unrefunded charge of the product and insert `+1` into the **current** month (with that month's subscription, or none), copying the category; `refunds_transaction_id` is UNIQUE and the insert uses `ON CONFLICT DO NOTHING`, so a charge is refunded at most once. They return `{ refunded: true, transaction }` or `{ refunded: false, reason }` (`NO_CHARGE` (also for data from before credits), `DAY_PASSED`, `HAS_ORDERS`, `ALREADY_REFUNDED`). `refundForProduct` (delete, or moved to donations completely): only on the credit day of the charge and only if the product has no Pending/Confirmed/Completed order item (Rejected and Cancelled do not count). The same-day rule is `isRefundEligible(chargeCreatedAt, now)`.
  - **Grants:** `grantPlan` creates the subscription for its month (current or later; a past month → 400 `"This month has already ended."`, a second one → 400 `"The user already has a subscription for this month."`) and a `PLAN_GRANT` into that month; `grantTopup` adds a `TOPUP_GRANT` to the current month and needs an active subscription there (400 `"An active subscription for the current month is required."`); `adjustCredits` writes an `ADMIN_ADJUSTMENT` (whole number ≠ 0, reason required) into the current month and refuses to take the available balance below zero (400 `"The balance cannot go below zero."`).
- **Global error handling** (`app.ts`, after the routers): unknown routes → 404 `"Route not found."`; `HttpError` (`utils/httpError.ts`, carries a status and optional extra body fields) → that status and `error.body()`; multer errors → 400 (`"The image can be at most 5MB."`); malformed JSON → 400 `"Invalid request format."`; anything else → 500 `"A server error occurred."`. Controllers still handle their own errors; this covers middleware and body parsing. A controller whose service throws `HttpError` answers with `sendError(res, error, message, log?)` from the same file: the `HttpError`'s status and body, anything else a 500 with `message`, logged under `log` (the message by default).

## Conventions

- Controller shape: `try { ... } catch (error) { console.error(...); return res.status(500).json({ error: "..." }) }`, always `return res...`.
- Failures: `{ error }`; successes: `{ message, <entity> }`. 404 for missing, 403 for not-owner, 400 for validation and invalid state.
- Dynamic filters: build the `WHERE` with `values.push(...)` and `$${values.length}`, add `ORDER BY` last. Declare `values` as `(string | number)[]` when it mixes types.
- **Pagination** (`utils/pagination.ts`): `parsePage(req.query, defaultLimit)` reads `limit` (1–100) and `offset` (≥ 0) and returns null for anything else, which the controller answers with 400 `"Invalid filter."`; `listPage(columns, from, orderBy, values, page)` runs `SELECT COUNT(*) <from>` and the page query. Every paged list keeps its response key and adds `total` (all matches for the current filters, not the page). Defaults: `CARD_PAGE_SIZE` 12 for card lists (marketplace, own products, orders, completed pickups, stores, donations), `TABLE_PAGE_SIZE` 10 for a store's or restaurant's own credit requests, `ADMIN_PAGE_SIZE` 20 for every admin list (including the credit overview, requests and a user's ledger). Every paged `ORDER BY` ends with `id DESC` (or another unique key before it), so rows with equal timestamps or names never repeat or go missing between pages. Not paged: notifications (50 newest), credit history, reports, pickup counts, today/upcoming pickups.
- **Sorting the admin tables** (`parseSort(req.query, columns, defaultOrder, tieBreaker)` in `utils/pagination.ts`): `sort` must be a key of the endpoint's whitelist (`USER_SORTS`, `PRODUCT_SORTS`, `DONATION_SORTS` in `admin.controller.ts`, `ADMIN_SORTS` in `services/orders/queries.ts`, `OVERVIEW_SORTS` in `adminCredits.controller.ts`), each mapped to an SQL expression in code, so the query value never reaches SQL; `dir` is `asc` (default) or `desc`. Anything else (an unknown key, another table's key, a bad `dir`, also without `sort`) is 400 `"Invalid filter."`. Empty values mean "not set" and keep the default order. The order is `<expression> ASC|DESC NULLS LAST, <table>.id DESC`: empty values come last in both directions and the id keeps the pages stable. Sorting combines with every filter and with paging; `total` is unchanged.
- Priority sorting uses `ORDER BY CASE WHEN status = '...' THEN 0 ... END, created_at DESC`.
- Ownership checks compare the resource owner with `req.user.id` (directly, or through the product's `store_id`).
- All server text is English: error and success messages (asserted by tests) and log lines. The client does the UI translation: notifications are translated from `type` (the stored `message` is an English fallback), the CSV reports take `lang`, and every `error` / `message` is translated on the client by its exact English text (`client/src/i18n/locales/server.bs.json`; a client test fails when a server text has no translation or a translation no longer matches a server text). Adding or rewording a message means updating that file in the same change. Keep messages short and plain. Examples: `"Product created successfully."`, `"All fields are required."`, `"Product not found."`, `"You do not have the required role for this action."`, `"Not enough product available."`, `"Product has active orders and cannot be deleted."`.

## TypeScript notes

- Local imports use `.js` extensions (nodenext), packages never do.
- `req.body` is `any`; destructure it and annotate with an interface where one exists (`ProductFields`, `RegisterBody`, `LoginBody`). `req.query` values are cast with `as string`. `req.params` values are strings.
- `catch (error)` is `unknown`: use `error instanceof Error && 'code' in error` before reading Postgres codes.
- `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are on: expect `rows[0]` to possibly be undefined.
- `process.env.JWT_SECRET!` is asserted where used.
- Shared types: `types/auth.ts` (`AuthUser`, `Role`), `types/express.d.ts` (augments `Express.Request` with `user?` and `file?`).

## CI

GitHub Actions, `.github/workflows/ci.yml`. Runs on every pull request to `main`, every push to `main` and by hand (`workflow_dispatch`, which runs everything). A new commit on the same PR/branch cancels the run in progress.

- `Detect changes` (`dorny/paths-filter`, pinned to a commit SHA) decides what runs: `server/**` → Backend; `client/**` and `server/src/**` → Frontend (the client test `serverMessages.test.ts` reads the server sources); `e2e/**` → E2E (which also runs whenever Backend or Frontend would); `.github/workflows/**`, the root `package.json` or `package-lock.json` → all three.
- `Backend` (`server/`): Node 24, `npm ci`, a `postgres:15` service container (same major as local development) with database `food_saver_test_db`, a `.env.test` written by the workflow with test-only values (`DATABASE_URL`, `JWT_SECRET`), migrations with `npx dotenv run -q -f .env.test -- node-pg-migrate up`, `npm run typecheck`, `npm test` (default + `github-actions` reporters, so failures show as PR annotations), `npm run build`. `TZ=Europe/Sarajevo`, because the test helpers build dates from the process's local day and must agree with `APP_TIMEZONE`.
- `Frontend` (`client/`): Node 24, `npm ci`, `npm run typecheck`, `npm run lint`, `npm test` (same reporters), `npm run build`.
- `E2E`: Node 24, a `postgres:15` service with `food_saver_e2e_db`, a Mailpit service (`axllent/mailpit:v1.32.0`, SMTP 1025, API 8025), `npm ci` in `server/`, `client/` and `e2e/`, a `.env.e2e` with test-only values (including `EMAIL_PROVIDER=smtp` and `MAILPIT_URL`), Chromium (the download cached by Playwright version, installed `--with-deps`), `npm run typecheck` and `npm run e2e` in `e2e/` (the Playwright web servers build, migrate and start both sides). On failure it uploads the `e2e-report` artifact (HTML report and traces, 14 days). Details in E2E tests in `docs/frontend.md`.
- `CI passed` runs always and fails if any job above failed or was cancelled (skipped is fine). It is the only check required by the `main` branch rules, so its name must not change.
- A failed run: `gh pr checks` shows which job failed, `gh run view <run-id> --log-failed` prints only the failed steps' logs.
- Lint: only `client/` has ESLint (`eslint.config.js`), and the `Frontend` job runs it. The server has no linter; its checks are the strict typecheck and the tests.
- Dependabot (`.github/dependabot.yml`): npm in `/`, `/server`, `/client` and `/e2e`, plus `github-actions`, every Monday at 07:00 Europe/Sarajevo. Minor and patch updates come as one grouped PR per folder/ecosystem, majors as separate PRs; at most 5 open PRs per entry, commit messages prefixed `deps`. Its PRs go through CI like any other (a root lock change runs every job). It also bumps the SHA-pinned `dorny/paths-filter`.
- PR template (`.github/pull_request_template.md`): what and why, how it was tested, and a checklist (tests, i18n keys in `bs` and `en`, docs, safe migration, screenshots for UI changes).

## Pending and known limitations

- **Deployment:** set `TRUST_PROXY=1` on Render (otherwise all users share one rate limit); the rate-limit counters are in memory, so more than one instance needs a shared store. The auth cookie is `sameSite: "strict"`, so the frontend and the API must be served from the same site (the same domain, or subdomains of one domain such as `app.example.com` and `api.example.com`). Do not switch to `sameSite: "none"` without real CSRF protection: the origin check is only a second layer. Set `CLIENT_ORIGIN` to the deployed frontend origin(s); logo uploads on local disk are lost on Render restarts (needs cloud storage; Cloudinary is not available in the owner's country, so evaluate alternatives). With more than one server instance the cron jobs would run once per instance (they are idempotent, but a lock or a separate worker is cleaner).
- **Emails:** every email is in Bosnian until the users' language is stored (the queue already has a `language` column). Every notification type has an email; the only setting is one switch for all of them (`users.email_notifications`). With more than one instance every instance runs the email worker, which is safe (`SKIP LOCKED`). Sent rows stay in `email_queue` (no cleanup job yet).
- Server messages should become error keys translated on the client.
- **Live events:** a stream checks the login only when it opens, so a block or a password reset reaches an open stream when it reconnects or the token expires (its events carry no content, and every load goes through the checked API). Notifications are still polled every 50 s next to the stream, as a fallback for a proxy that cuts it. Each tab holds one connection to the API, and a browser allows only 6 HTTP/1.1 connections per origin, so serve the API over HTTP/2 when deployed (locally, more than about 5 open tabs would make requests wait).
- **Delivery at acceptance** calls the provider inside the decision's transaction (fine for the in-memory mock); moving it to an outbox before Korpa, and the other phase 2 limits, are tasks in `development-plan.md` (Phase 3).
- `PUT /users/me`: replace `COALESCE` with a real PATCH that can clear optional fields.
- The server has no ESLint setup.
