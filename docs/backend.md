# Backend (`server/`)

Reference for working on the API. The source of truth is the code; routes and middleware per endpoint are in `src/routes/*.routes.ts`.

## Stack

- Node.js 24, Express 5 (`express@5.2.1`, `@types/express@5`), TypeScript, ESM (`"type": "module"`, `module: nodenext`)
- PostgreSQL through raw `pg` queries (no ORM), migrations with `node-pg-migrate`
- Auth: `jsonwebtoken` + `bcrypt` (10 salt rounds), JWT in an httpOnly cookie, `cookie-parser`, `cors`
- Uploads: `multer` (disk storage for logos, memory storage for CSV imports), CSV parsing with `csv-parse`. Scheduled work: `node-cron`
- Tests: Vitest + supertest (see Testing)

Express 5 notes: `req.query` is a read-only getter (read it, never assign to it), and wildcard routes must be named (`/*splat`). Neither is used today.

## Scripts and environment

- `npm run dev`: `concurrently "tsc --watch" "node --watch dist/server.js"`. The server runs the compiled `dist/`, so run `npm run build` once on a fresh clone.
- `npm run build` (`tsc`), `npm start` (`node dist/server.js`)
- `npm run migrate up|down`, `npm run migrate create <name>` (uses `.env` through dotenv-cli)
- `npm test` (Vitest + supertest, `.env.test`, files run one at a time; the full suite runs in CI, see CI below). Single file: `npm test -- tests/products.test.ts`. Single test: `npm test -- -t "name"`. Watch mode: `npm run test:watch`.
- `npm run typecheck`: `tsc --noEmit -p tsconfig.test.json` (source and tests).
- `npm run seed` (destructive reset, see Seed); builds first and runs from `dist/`.
- `npm run create-admin -- <email> <password> [first name] [last name]`: builds, then inserts an `ADMIN` account (same email and password rules as the API; a duplicate email is refused). Used for the first admin; later accounts are created in the app.
- Env: `DATABASE_URL`, `JWT_SECRET`, optional `PORT`, `NODE_ENV`, `CLIENT_ORIGIN` (allowed frontend origin for CORS and the origin check, default `http://localhost:5173`; a comma-separated list is allowed), `APP_TIMEZONE` (business time zone for `CURRENT_DATE` and cron, default `Europe/Sarajevo`). `.env.test` points at the separate database `food_saver_test_db`.

`tsconfig.json`: `strict`, `module/moduleResolution nodenext`, `target esnext`, `rootDir ./src`, `outDir ./dist`, `types: ["node"]`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `isolatedModules`, `declaration`, `sourceMap`, `include: ["src"]`. Migrations and tests live outside `src/`, so the build never emits them. `tsconfig.test.json` extends it with `rootDir: "."`, `noEmit`, `types: ["node", "vitest/globals"]` and includes `tests/`, so the tests are type-checked with the same strict options.

## Request pipeline (`app.ts`)

Order: `cors({ origin: allowedOrigins, credentials: true })` → `checkOrigin` → `express.json()` → `req.body ??= {}` (Express 5 leaves it undefined for requests without a body; controllers destructure it) → `cookieParser()` → routers → `/uploads` static (with `X-Content-Type-Options: nosniff`) → JSON 404 for any unknown path (`"Route not found."`) → error handler (see Business logic).

Origin check (`middleware/origin.middleware.ts`), defence in depth against CSRF next to the `sameSite: "strict"` cookie: `allowedOrigins` is `CLIENT_ORIGIN` split on commas, parsed once at startup and shared with `cors()`. For `POST`, `PUT`, `PATCH` and `DELETE`, the `Origin` header (or, when it is missing, the origin of the `Referer`) must be one of them, otherwise 403 `"Request origin not allowed."` (an unparseable `Referer` is refused too). A request with neither header (non-browser clients, supertest) passes; `GET`, `HEAD` and `OPTIONS` are not checked. No CSRF token library is used.

Routers: `/api/auth`, `/api/products`, `/api/reservations`, `/api/users`, `/api/notifications`, `/api/favorites`, `/api/product-templates`, `/api/reports`, `/api/donations`, `/api/admin`, `/api/announcements`, `/api/credits`, `/api/dashboard`, `/api/stats`, `/api/cities`, `/api/company`

Routes chain `authenticate` → `authorize('<ROLE>', ...)` (one or more allowed roles) → controller. Every store/restaurant route names its roles (`authorize('STORE', 'RESTAURANT')` where both are allowed), so an `ADMIN` reaches only `/api/admin`, `/api/notifications`, `GET`/`PUT /api/users/me` and `/api/auth`. The admin router applies `authenticate, authorize('ADMIN')` to all of its routes with `router.use`. A `COMPANY` (headquarters) user reaches only `/api/auth`, `GET`/`PUT /api/users/me`, `PUT /api/users/me/password`, `/api/notifications`, `/api/announcements`, `GET /api/stats/impact`, `GET /api/cities` (its branches' cities) and `/api/company`; every store, restaurant, admin and `/api/credits` route rejects it with 403 through its `authorize` list (its branches' credits are under `/api/company`).

## Auth

- `register`: kept for the planned public roles (individuals, public kitchens, humanitarian organizations), none of which exists yet (`PUBLIC_ROLES` is empty). It validates first_name, last_name, email, password and role first, then answers 403 `"Store and restaurant accounts are created by an administrator."` for `STORE`, `RESTAURANT`, `ADMIN` and `COMPANY` and 400 `"Role is not valid."` for anything else. Store, restaurant and admin accounts are created by an admin (`POST /api/admin/users`).
- `login`: bcrypt compare; a blocked account (checked only after the password matched, so a block is not revealed to someone without the password) gets 403 `"Your account is blocked. Reason: <reason>"` and no cookie. The **effective block** applies: the account's own block (with its reason) comes first, otherwise a blocked company blocks its users with the company's reason, and a deactivated branch gets 403 `"This branch has been deactivated. Contact your company."`; `jwt.sign({ id, role }, JWT_SECRET, { expiresIn: "7d" })`, sets cookie `token` (`httpOnly`, `secure` only when `NODE_ENV === "production"`, `sameSite: "strict"`, 7-day `maxAge`). Returns `{ message, user: { id, first_name, last_name, email, role } }`. Wrong email and wrong password return the same message.
- `logout`: `clearCookie` with the same options. `GET /auth/me` returns only the token payload (`{ id, role }`); the client uses `GET /users/me` for full data.
- `authenticate`: reads `req.cookies.token`, `jwt.verify`, rejects non-object payloads, then reads `users.role`, the effective block (`NOT notBlocked("users")`: the user's own flag or its company's) and `users.must_change_password` for the token's id (one query per request). A missing user is 401 `"Token is invalid or has expired."`, a blocked one 401 `"Your account is blocked."` (so blocking an account or its company ends a session at once). While `must_change_password` is set (a temporary password from an admin), only `GET /api/auth/me`, `GET`/`PUT /api/users/me`, `POST /api/users/me/logo`, `PUT /api/users/me/password` and `GET /api/cities` (for the profile form) pass (`ALLOWED_BEFORE_PASSWORD_CHANGE`, matched on method + path without the query string); everything else is 403 `"You must change your password before continuing."`. This also applies to an existing session once an admin resets the password. The login response includes `must_change_password`. `req.user` (`AuthUser = JwtPayload & { id: number; role: Role }`, `Role = 'STORE' | 'RESTAURANT' | 'ADMIN' | 'COMPANY'`) takes the role from the database, not from the token. Other failures are 401; a database error is 500.
- `authorize(...roles)`: 403 with "You do not have the required role for this action." when the caller's role is not one of them (`authorize('STORE')`, `authorize('STORE', 'RESTAURANT')`).
- Controllers read `req.user!.id` (non-null assertion is safe because `authenticate` runs first).

## Database

Enum types: user role (`STORE`, `RESTAURANT`, `ADMIN`, `COMPANY`), admin action (`CREATE_USER`, `RESET_PASSWORD`, `BLOCK_USER`, `UNBLOCK_USER`, `REMOVE_PRODUCT`, `REMOVE_DONATION`, `CANCEL_RESERVATION`, `UPDATE_PROFILE`, `CREATE_ANNOUNCEMENT`, `END_ANNOUNCEMENT`, `APPROVE_CREDIT_REQUEST`, `REJECT_CREDIT_REQUEST`, `ADJUST_CREDITS`, `CREATE_COMPANY`, `UPDATE_COMPANY`, `BLOCK_COMPANY`, `UNBLOCK_COMPANY`, `DEACTIVATE_BRANCH`, `REACTIVATE_BRANCH`, `ATTACH_BRANCH`), the credit enums (`subscription_status`, `credit_transaction_type`, `credit_actor`, `credit_request_type`, `credit_request_status`, `credit_request_source`; values in the table below), announcement audience (`ALL`, `STORE`, `RESTAURANT`), product status (`Available`, `Sold`, `Expired`, `Removed`), reservation status (`Pending`, `Confirmed`, `Completed`, `Rejected`, `Cancelled`). `Rejected` = refused by the store; `Completed` = picked up (set by the store); `Cancelled` = withdrawn by the restaurant, cancelled by the expiry job, or cancelled by the store after a missed pickup. Donation type (`FREE`, `SPONSORED`) and donation status (`Available`, `Expired`, `Removed`; claim and funding statuses come with the recipient roles). Category and unit are stored as codes in VARCHAR columns (validated against fixed lists, see Validation); labels are a frontend concern.

`DATE` columns (`expiry_date`) come back from `pg` as plain `YYYY-MM-DD` strings: `config/db.ts` overrides the default parser, which would turn them into a JS `Date` at local midnight and serialize the previous day in UTC+ time zones. Every pool session also runs with `timezone = APP_TIMEZONE`, so `CURRENT_DATE` is the local business day.

## API reference

Roles shown are the intent; confirm exact middleware in `src/routes/`.

### Auth `/api/auth`
`POST /register` (closed for every existing role, see Auth), `POST /login`, `POST /logout`, `GET /me` (authenticated)

Emails are trimmed and lowercased on register, login and admin account creation (login matches `LOWER(email)`, so accounts created before this rule still log in). Register also requires a valid email format (`"Email is not valid."`) and a password of at least 8 characters (`"Password must be at least 8 characters long."`); a duplicate, including one that only differs in case, is 400 `"A user with this email already exists."`. Login without email or password is 400 `"All fields are required."`.

### Products `/api/products`
| Endpoint | Who | Behavior |
|---|---|---|
| `POST /` | STORE | Create. `store_id` always comes from `req.user`, never from the body. One transaction with `chargeForProduct` (1 credit); without credits 402 `INSUFFICIENT_CREDITS` and nothing is created. |
| `POST /import` | STORE | Bulk create from a CSV file (multipart field `file`, see CSV import below). 201 `{ message: "Products imported: N.", products }`. Charges 1 credit per product in the same transaction (`chargeForProducts`); fewer credits than rows → 402 and nothing is imported. `?dryRun=true` only checks the file: the same 400s for a bad file, else 200 `{ message: "The file is valid.", count }` with nothing created and nothing charged (the client uses it to confirm the credits before importing). |
| `GET /` | STORE, RESTAURANT (marketplace for restaurants) | Only `Available`, not expired and with `available_quantity > 0` (filtered in SQL), from stores that are not blocked and have a `business_name`. Filters: `category`, `expiryWithinDays` (0 = expires today, 1 = by tomorrow, ...), `name` (ILIKE), `city_id` (the **store's** city, an id from `GET /cities`, like every city filter: empty = no filter, not a valid id or not in the list → 400 `"Invalid filter."`; `parseCityFilter` in `utils/cities.ts`), `store_id` (one store's offers, used by the store profile), `radius` (see Nearby offers below: `5`, `10`, `20`, `50` or `all`; missing or empty = 10; anything else → 400). #### CSV import

- `uploadCsvFile` (multer memory storage, nothing is written to disk) accepts one file in field `file`, at most 1MB (`MAX_CSV_SIZE_MB`), with a `.csv` extension and a MIME type of `text/csv`, `application/csv`, `application/vnd.ms-excel`, `text/plain` or `application/octet-stream` (browsers disagree on the type of a .csv). Otherwise 400 `"Only CSV files are allowed."` / `"The file can be at most 1MB."`; no file → 400 `"A CSV file is required."`. Logo and CSV uploads share the `handleUpload` wrapper, which turns multer errors into 400 JSON.
- `utils/productCsv.ts` → `parseProductCsv(buffer)`: columns `name, description, category, original_price, discounted_price, quantity, unit, expiry_date` (`CSV_COLUMNS`; header names are trimmed and lowercased, order does not matter, `description` is optional). The delimiter (`,` or `;`) is read from the header line, so a `;` file can use an unquoted decimal comma. A UTF-8 BOM is skipped and empty lines are ignored. Values are normalized before `validateProductFields`: `2,50` → `2.50`, and the expiry date → `YYYY-MM-DD` from any form Excel writes when it saves a CSV: a time part (`T...`, ` 00:00:00`, ` 12:00 AM`), spaces and a trailing dot are dropped, then `YYYY-M-D` / `YYYY.M.D` / `YYYY/M/D` (year first), `D.M.YYYY` / `D-M-YYYY` (day first, also with a 2-digit year → `20YY`), `A/B/YYYY` (day first, unless some slashed date in the same file only works month first, like `12/25/2026`; then the whole file is read as US `M/D/YYYY`), and a 5-digit Excel serial (days since 1899-12-30). Anything else is left as is, so the validator rejects it. Category and unit are the server codes (`Meat`, `kg`).
- File-level errors (400): `"The CSV file could not be read."` (e.g. an unclosed quote), `"The CSV file does not contain any products."`, `"The CSV file is missing columns: ..."`, `"The CSV file can contain at most 500 products."` (`MAX_CSV_ROWS`).
- All or nothing: every row is validated first. If any fails, the response is 400 `{ error: "The CSV contains invalid rows.", rowErrors: [{ row, error }] }` (`row` is the line number in the file, header = 1) and nothing is inserted. For an invalid date the row error quotes the raw value: `Expiry date is not valid: "<value>". Use the format 31.12.2026.` (the plain `POST /` message is unchanged). Otherwise all rows are inserted in one transaction.

### Validation

- `utils/validateProduct.ts`: `validateProductFields` (create and update) returns an English error string or `null`:
  - required: name, category, original_price, discounted_price, quantity, unit, expiry_date (description optional) → `"All fields are required."`
  - category and unit must be in `CATEGORIES` / `UNITS` (keep in sync with `client/src/utils/categories.ts` and `units.ts`) → `"Category is not valid."`, `"Unit of measure is not valid."`
  - prices and quantity must be numbers above 0 → `"Prices and quantity must be positive numbers."`
  - discounted_price may not exceed original_price → `"Discounted price cannot be higher than the original price."`
  - expiry_date must be a real `YYYY-MM-DD` date → `"Expiry date is not valid."`, and not before today in `APP_TIMEZONE` → `"Expiry date cannot be in the past."`
- `validateTemplateFields` applies the category/unit lists and checks optional numbers when they are given.
- `utils/params.ts`: `parseId` (positive integer or `null`), `parseNumber`, `parseNonNegativeInt`. A non-numeric `:id` returns the resource's normal 404 instead of a Postgres cast error.
- `utils/dates.ts`: `APP_TIMEZONE`, `todayInAppTimezone()`, `isValidDate`, `isValidDateTime`.

### Users `/api/users`
- `GET /me`: full profile (explicit column list, never `password_hash`), including `must_change_password`, `company_id`, `company_name`, `company_logo_url` (the company's logo; a `COMPANY` user's avatar, and a branch's when it has none) and `company_description`. `logo_url` and `description` are the user's own (not resolved).
- `PUT /me`: updates profile through `updateProfile(db, userId, role, body)` (exported, also used by the admin's `PUT /admin/users/:id/profile`). Required: first_name, last_name, business_name, city_id, address, phone (400 `"First name, last name, business name, city, address and phone are required."`). `city_id` (a number or a numeric string) must be a city from the list, otherwise 400 `"Invalid city."`. The response's `user` has `city_id` and `city` (the name; `CITY_NAME` in `utils/cities.ts`, a subquery, because `RETURNING` cannot join). The other fields use `COALESCE`, so they cannot be cleared back to null. For an `ADMIN` only `first_name` and `last_name` are read (both required, 400 `"First and last name are required."`); the response has `id, first_name, last_name, email, role`. For a `COMPANY` user only `first_name`, `last_name` and `phone` (all required, 400 `"First name, last name and phone are required."`); the response adds `phone` and `company_id`. Business fields in the body are ignored. A **branch** (STORE with `company_id`) cannot change its own `business_name` or `city_id`: `updateUser` passes `{ lockBranchFields: true }`, which replaces them with the stored values (like `logo_url` is ignored in the admin edit), so only its headquarters (`PUT /company/branches/:id`) or an admin (`PUT /admin/users/:id/profile`) change them. An empty `description` is stored as `""`, which counts as none (see Branding).
- `DELETE /me/logo` (STORE, RESTAURANT): clears `logo_url` and deletes the file. 200 `{ message: "Logo removed." }`. A branch then shows its company's logo again.
- `PUT /me/password` (any role): body `current_password`, `new_password`. 400 `"All fields are required."`, `"Current password is incorrect."` (bcrypt compare), the password-length message, `"The new password must be different from the current one."`. Stores the new hash and clears `must_change_password`. 200 `{ message: "Password changed." }`. Repeating the new password is checked on the client.
- `POST /me/logo` (STORE, RESTAURANT): `uploadLogoFile` (multer, single file field `logo`, JPEG/PNG/WEBP, max 5MB) stores `/uploads/logos/<userId>-<timestamp>.<ext>` in `logo_url` (a `COMPANY` user's company logo, `POST /api/company/me/logo`, is named `company-<userId>-<timestamp>.<ext>`). The extension comes from the checked MIME type, never from the uploaded file name, and `/uploads` is served with `nosniff`, so an uploaded file can only ever be an image. The previous logo file is deleted. Rejected uploads answer 400 JSON: `"Only JPEG, PNG and WEBP images are allowed."`, `"The image can be at most 5MB."`; no file: `"No image was uploaded."`.
- `GET /stores` (RESTAURANT): store list without blocked stores and stores that have no `business_name` yet; filters `city_id` (see the products filter), `business_name`, `favorites=true` (only the caller's favorite stores; an empty value means no filter, anything else → 400 `"Invalid filter."`), `radius` (as on `GET /products`). Each store has `distance_km`. `sort`: `distance` (default: nearest first, then by name) or `name` (by name only); anything else → 400. Paged (default 12, `{ message, stores, total, outside_radius_count }`). Each store has `active_products` (COUNT, a string): its `Available` products with `expiry_date >= CURRENT_DATE`.
- `GET /stores/:id` (route: STORE, RESTAURANT; the controller returns 403 for STORE, so in practice restaurants only; 404 for a blocked store): returns `{ store, stats, myReservations }`. The store's offers are paged through `GET /products?store_id=` (available, unexpired, with stock left). `stats` = `sold_articles` (count of products with status Sold) and `successful_reservations` (count of picked-up, i.e. `Completed`, reservations on its products). `myReservations` = `{ my_reservations_count }`, the calling restaurant's `Completed` reservations at this store. Pending, Confirmed (not picked up yet), Rejected and Cancelled are not counted.

### Dashboard `/api/dashboard` (STORE, RESTAURANT)
`GET /stats` (`dashboard.controller.ts`): the dashboard stat cards over all of the caller's data, all numbers, `{ message, stats }`. `successful_reservations` = accepted (Confirmed + Completed; the "Confirmed reservations" card); food saved and savings = picked up (`Completed`) only.
- Store: `{ active_products, pending_reservations, successful_reservations, saved: { kg, l, pieces } }`. `active_products` counts its products with status `Available` (no expiry check, the midnight job sets `Expired`). Reservations are those on its products; `saved` sums `Completed` quantities by the product's unit: kg + g/1000 → kg, l + ml/1000 → l, kom + pak → pieces (the impact report's rules).
- Restaurant: `{ pending_reservations, successful_reservations, savings }`, its own reservations; `savings` = Σ (the product's **current** `original_price` − `unit_price`) × quantity over `Completed` ones, not clamped. The "available offers" card uses the `total` of `GET /products` (sent with `radius=10`; when that radius has fewer than 3 offers the client asks 20 km, then 50 km, then all cities to fill the soonest-expiring list, and the card shows the total of the widest radius asked for).
- An account without data gets zeros. ADMIN → 403.

### Stats `/api/stats` (STORE, RESTAURANT, ADMIN, COMPANY)
`GET /impact` (`stats.controller.ts`): `{ message, kg }`, the platform-wide food saved in kg for the footer's counter. It is `getSavedTotals().kg` (`services/impactStats.ts`), the same query as the admin stats' `saved`: `Completed` reservations only, kg + g/1000 (l, ml, kom and pak are left out). Not rounded; the client rounds. 401 without a session; 403 while a temporary password is set (like every route outside the allow-list).

### Cities `/api/cities` (STORE, RESTAURANT, ADMIN, COMPANY)
`GET /` (`cities.controller.ts`): `{ message: "Cities fetched successfully.", cities: [{ id, name }] }`, the whole list, sorted with `ORDER BY cities.name COLLATE "bs-x-icu"` so Č, Ć, Đ, Š and Ž follow their base letter (the ICU collation ships with PostgreSQL builds that have ICU, which the Windows and Docker images do). It is on the temporary-password allow-list, because the profile form needs it. Coordinates are not returned; distances are computed in SQL (below).

### Nearby offers (radius and distance)
Restaurants see offers and stores near their own city first. Rules (`GET /products` and `GET /users/stores`):
- **Distance** = `city_distance_km(from_city, to_city)`, a SQL function (migration `add-city-distance-function`): the straight-line (Haversine, R = 6371) distance in **whole km** between the two cities' centres, not addresses, so the same city is 0 and 5 km usually means the own city. NULL when either id is null or unknown. It is the one place the formula lives; queries build the call with `cityDistance(from, to)` from `utils/cities.ts` (later features such as branches and donations reuse it). From Visoko: Breza 7, Ilijaš 9, Kakanj 16, Sarajevo 24, Zenica 32.
- The starting point is the **restaurant's** `city_id` (`userCityId`), passed as a parameter. A store calling `GET /products` gets `distance_km` null and no radius.
- **Radius** (`parseRadius`): 5, 10, 20 or 50 km or `all`; missing = 10 (`DEFAULT_RADIUS`). Rows farther than the radius are left out, and `outside_radius_count` counts the rows that match every other filter but lie beyond it (a second COUNT with `>` instead of `<=`).
- The radius is **not applied** (and `outside_radius_count` is 0) with `radius=all`, a `city_id` filter (choosing a city is explicit), `store_id` (a store's profile shows all its offers), `favorites=true` on the store list, or when the restaurant has no city yet.
- Several stores in range (e.g. later two branches of a chain) all show, sorted by distance.

### Reports `/api/reports` (STORE, RESTAURANT)
Downloadable CSV reports. Both cover only **Completed** reservations whose `picked_up_at::date` is between `from` and `to` (local day, the session runs in `APP_TIMEZONE`), with the same ownership as the pickups page (`pickupOwnership`, exported from `reservations.controller.ts`: a store gets reservations on its products, a restaurant its own; `parties` is the other side).
- Query: `from`, `to` (`YYYY-MM-DD`, required, `from <= to`, at most 366 days including both ends; otherwise 400 `{ error: "Invalid period." }`) and optional `lang` (`en`; anything else means `bs`) for the column headers, category labels, the total label and the file name. Reports are files read outside the app, so they follow the UI language rather than the English-only rule for server text.
- Success: 200 with `Content-Type: text/csv; charset=utf-8` and `Content-Disposition: attachment; filename="<name>-<from>-<to>.csv"` (not the usual JSON). Errors stay JSON; 500 `"An error occurred while generating the report."`.
- `GET /sales`: one row per reservation, ordered by `picked_up_at`: pickup date, reservation id, product, category label, other party (`business_name`, else first + last name, else email), its city, quantity, unit, `unit_price`, the product's **current** `original_price` (there is no snapshot of it), total (`unit_price × quantity`), savings (`(original_price − unit_price) × quantity`, never negative). Last row: totals of the two money columns (quantities have mixed units). File name `prodaja`/`sales` for a store, `kupovine`/`purchases` for a restaurant.
- `GET /impact`: one row per month (`YYYY-MM`) plus a total row (`GROUPING SETS`, so partners are counted once over the whole period): pickups, distinct partners (restaurants for a store, stores for a restaurant), food in kg (g/1000), l (ml/1000) and pieces (kom + pak) like the dashboard's food-saved card, value and savings in KM. An empty period still has the total row with zeros. File name `uticaj`/`impact`.
- `utils/csv.ts` → `toCsv(headers, rows)`: UTF-8 BOM, `;` delimiter, CRLF, integers as they are and other numbers with two decimals and a decimal comma (`2,50`), so Bosnian Excel splits the columns and reads the numbers; cells with `;`, `"` or a line break are quoted; text starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'` (CSV formula injection: product and business names are user input). `utils/reportLabels.ts` holds the headers and category labels per language.
- The queries and helpers are shared with the company reports (`services/reports.ts`): `parsePeriod`, `sendCsv`, `salesRows(scope, owner, period, lang, { withBranch })` and `impactRows(scope, owner, period, lang)`, where a `PickupScope` is `{ owner, partyJoin }` (`pickupOwnership(role)` here, `storesScope()` for a set of store ids), plus `IMPACT_COLUMNS`, `PICKED_UP_IN_PERIOD` and `impactCells`.
- Adding a report: a query in `services/reports.ts` (or the controller), its headers in `reportLabels.ts`, a route, and an entry in the client's `REPORTS` list (for a company report: `companyReports.controller.ts` and `CompanyReportsPage`).

### Donations `/api/donations` (STORE and RESTAURANT)
Donation offers of the humanitarian module. `FREE` = given away; `SPONSORED` = given at `donation_price`, which a third party will pay. Until the recipient roles exist, a donation is visible only to its donor (`donor_id = req.user.id`).
- `POST /`: create; `donor_id` from `req.user`. 201 `{ message: "Donation published successfully.", donation }`.
- `GET /mine`: own donations except `Removed`, `Available` first, then newest. Filters `type`, `status` (`Available`/`Expired`), `name` (ILIKE); anything else → 400 `"Invalid filter."`. Paged (default 12): `{ donations, total }`, each with `days_until_expiry`.
- `GET /:id`: own and not removed, else 404 `"Donation not found."`.
- `PUT /:id`: same body as create. 404, 403 `"You are not allowed to edit this donation."`, 400 `"Only active donations can be edited."` unless `Available`. 200 `{ message: "Donation updated successfully.", donation }`.
- `DELETE /:id`: soft delete (`Removed`), any status. 404, 403 `"You are not allowed to delete this donation."`, 200 `{ message: "Donation deleted." }`.
- `POST /from-product/:productId` (STORE only, "Prebaci u donaciju"): body `donation_type`, optional `quantity` (default: everything available), `donation_price` (SPONSORED). Stock-safe transaction with `FOR UPDATE` on the product. 404 `"Product not found."` (also for `Removed`), 403 `"You are not allowed to donate this product."`, 400 `"Only available products can be moved to donations."` (not `Available` or expired), 400 `"Quantity must be greater than zero."`, 400 `"Not enough product available."` when it exceeds `quantity − Pending − Confirmed − Completed`. The donation copies name, description, category, unit, `original_price` and `expiry_date` and stores `source_product_id`. A repeated move adds to the product's `Available` donation with the same `donation_type` and `donation_price` (locked `FOR UPDATE`): its quantity grows and the response is 200 `{ message: "Quantity added to the existing donation.", donation }`; a different type or price, or an earlier donation that expired or was deleted, gives a new donation. Then: nothing reserved and everything donated → product `Removed` and `refundForProduct` (its credit back on the day of the charge); otherwise `products.quantity` drops by the donated amount (reservations keep theirs), `markSoldIfFullyConfirmed` may mark it `Sold`, and the credit stays spent. 201 `{ message: "Product moved to donations.", donation, creditRefunded }` (also on the 200 merge response).
- `POST /:id/return-to-product` (STORE only, undoes a move): one transaction that locks the donation and then its source product. 404 `"Donation not found."` (missing or `Removed`), 403 `"You are not allowed to edit this donation."`, 400 `"Only active donations from the offer can be returned."` (not `Available`, or no source product), 400 `"Product has expired and cannot be returned to the offer."`. The product becomes `Available` (also from `Sold` or `Removed`); its quantity grows by the donation's quantity, except for a `Removed` product, which kept its old quantity when everything was moved and is rebuilt as Pending + Confirmed + Completed + the donation's quantity. The donation becomes `Removed`. A product that was `Removed` is published again and costs 1 credit (`chargeForProduct`; 402 rolls the whole return back), unless its last charge was never refunded (`hasOpenProductCharge`: the move came after the charge day), in which case that charge still covers it; returning to a product that stayed on offer is free. 200 `{ message: "Donation returned to the offer.", product }`.

Validation (`utils/validateDonation.ts`, `validateDonationFields` + `normalizeDonationFields`):
- Required: donation_type, name, category, quantity, unit, original_price, expiry_date → `"All fields are required."`. Category in `DONATION_CATEGORIES` (product categories + `Meals`), unit in `DONATION_UNITS` (product units + `portion`) → the product messages. Quantity and value above 0 → `"Quantity and value must be positive numbers."`.
- `validateDonationPrice` (also used by from-product): unknown type → `"Donation type is not valid."`; SPONSORED needs a price above 0 → `"Donation price is required and must be greater than zero."` and below the value → `"Donation price must be lower than the product's value."`. A FREE donation's price is stored as NULL.
- Expiry date as for products. Pickup times `HH:MM[:SS]` → `"Pickup time is not valid."`, start before end → `"Pickup start must be before pickup end."`.
- `allergens` must be codes from `ALLERGENS` (the 14 EU allergens) → `"Allergens are not valid."`; `serving_temperature` one of `HOT`, `COLD`, `FROZEN` → `"Serving temperature is not valid."`. Both are stored only for `Meals` and cleared otherwise.
- Keep the lists in sync with `client/src/utils/donations.ts`.

### Credits `/api/credits` (STORE, RESTAURANT)
Controller `credits.controller.ts`. Payment is offline, so every subscription and top-up is a request an admin approves. User responses never contain `admin_note` (`CREDIT_REQUEST_COLUMNS` leaves it out). A request row: id, user_id, request_type, plan_id, topup_package_id, period_month, auto_renew, status, source, created_at, reviewed_at, requested_by, company_note, company_reviewed_at, plan_name, credits, price. The request rules live in `services/creditRequests.ts`, shared with the headquarters' endpoints.

**Branches** (a STORE with `company_id`, `getManagingCompany`): their headquarters asks and pays for their plans (see Company credits). Their credits work exactly as for any store (balance, charges, refunds, history); only who asks changes. Independent stores and restaurants are unchanged. `credits` and `price` are the request's own snapshot, so a later plan change never alters what was quoted or what an approval grants.
- `GET /plans` → `{ plans }` (active, by credits: id, name, credits_per_period, price). `GET /topup-packages` → `{ packages }`.
- `GET /me` → `{ credits }` = `creditSummary`: `getBalance` (`periodStart`, `periodEnd`, `subscription`, `hasActiveSubscription`, `total`, `used`, `available`) + `nextSubscription` (next month's, or null) + `pendingRequests` (the open ones: PENDING, and for a branch COMPANY_REVIEW) + `managedByCompany` (true for a branch) and `companyName` (its company, else null).
- `GET /me/history?year=` (default the current credit year; 2000–2100, else 400 `"Invalid filter."`) → `{ history: { year, months: [{ month, hasSubscription, total, used }] × 12, categories: [{ category, used }] } }` (`getUsageHistory`: a charge refunded in its own month never counts, so the categories add up to the months).
- `GET /requests` → `{ requests, total }`, every status, newest first, paged (default 10).
- `POST /requests`: `request_type` `SUBSCRIPTION` (`plan_id`, `period` `current`/`next`, optional boolean `auto_renew`) or `TOPUP` (`topup_package_id`, always this month). 400 `"Request type is not valid."`, `"Period is not valid."`, `"Auto-renew must be true or false."`; 404 `"Plan not found."` / `"Top-up package not found."` (also for inactive ones); 400 `"You already have a subscription for this month."`, `"An active subscription for the current month is required to buy extra credits."`, and from the partial unique indexes (`23505`) `"You already have a pending subscription request for this month."` / `"You already have a pending top-up request."`. Notifies every admin in the same transaction. 201 `{ message: "Request sent.", request }`; `requested_by` is the user. A **branch**: `SUBSCRIPTION` → 403 `"Your company manages your plan."`; `TOPUP` (same validation and "active subscription this month" rule) is created as `COMPANY_REVIEW` with source `BRANCH` and goes to its headquarters instead of the admins (`BRANCH_TOPUP_REQUESTED` to every unblocked headquarters login); 201 `"Request sent to your company."`. The open-top-up index answers a second one (at the headquarters or the admin) with `"You already have a pending top-up request."`.
- `DELETE /requests/:id`: withdraws an own PENDING request (`CANCELLED`; the status condition is part of the UPDATE, so it cannot race an admin's decision). 404 `"Request not found."`, 403 `"You are not allowed to withdraw this request."`, 400 `"Only pending requests can be withdrawn."`. 200 `{ message: "Request withdrawn.", request }`. A branch withdraws only a `COMPANY_REVIEW` top-up; a PENDING one (sent by its headquarters) → 403 `"Your company manages your plan."`.
- `PATCH /subscription/auto-renew` body `{ auto_renew: boolean }`: sets it on the user's current and future ACTIVE subscriptions (404 `"You do not have an active subscription."`) and on their PENDING `SUBSCRIPTION` requests (their own and the job's renewals), so approving one later keeps the user's choice. Nothing is cancelled: next month's approved plan or pending request stays, and with auto-renew off it simply does not renew after that month. Turned on in the renewal window (`isRenewalWindow`), it calls `createRenewals(client, now, { userId, explicit: true })` in the same transaction, since the job may already have run for the last time that month; a renewal the user withdrew earlier no longer blocks, one the admin rejected does. 200 `{ message: "Auto-renew turned on." | "Auto-renew turned off.", autoRenew, renewalCreated }`. The logic is `applyAutoRenew(client, userId, autoRenew)` (also used by the headquarters). A branch → 403 `"Your company manages your plan."`.

### Branches `/api/company/branches` (COMPANY)
A branch is a STORE with `company_id`: it publishes products, answers reservations, handles pickups and donations like any store. Its headquarters only creates, names, views and deactivates it (`controllers/companyBranches.controller.ts`; the shared rules are in `services/branches.ts`, which the admin endpoints reuse). Every `/:id` route answers 404 `"Branch not found."` for a branch of another company (or any user that is not one of the caller's stores), so their existence is not revealed. Writes run in a transaction that locks the branch and answer after the commit.
- `GET /branches`: paged (12). Filters `q` (name ILIKE), `city_id` (`parseCityFilter`), `status` (`active`/`deactivated`/`blocked`, else 400 `"Invalid filter."`). Ordered by name. ## Business logic worth knowing

- **Available quantity** is computed, never stored: `products.quantity` minus the sum of `Pending` + `Confirmed` + `Completed` reservation quantities (picked-up food is gone, so completing a reservation must not free its quantity). Partial reservations are allowed and the product stays `Available` until accepted reservations cover the full quantity.
- **Stock-safe pattern** (`createReservation`, `acceptReservation`, `updateProduct`; reject and cancel lock the reservation row instead): `pool.connect()`, `BEGIN`, `SELECT ... FOR UPDATE` on the product row, compute, write, `COMMIT`; `ROLLBACK` on any early return or error; `client.release()` in `finally`. Use the same pattern for anything that touches stock or a reservation's status. `markSoldIfFullyConfirmed(client, product)` (in `reservations.controller.ts`) marks a locked product `Sold` once Confirmed + Completed cover its quantity. `lockReservation` (same file, exported) locks a reservation row for reject, cancel, complete, cancel-overdue and the admin cancel and also returns `is_overdue`. `releaseSoldProduct(client, productId)` (exported) locks the product and turns a `Sold`, unexpired product back to `Available` once Confirmed + Completed no longer cover its quantity; cancel-overdue and the admin cancel call it after cancelling a Confirmed reservation.
- **Notifications** are written with `createNotification(db, { userId, type, message, reservationId?, productId?, donationId?, details? })` from `utils/notifications.ts` as part of the action; `db` is the pool or the transaction client, so inserts inside a transaction commit or roll back with it. The client translates each one from `type` plus the joined product data; `message` is an **English fallback** (the one exception to "server messages are Bosnian"), for example `"New reservation request: 4kg Chicken"`. Types:

  | type | Recipient | Trigger | Links |
  |---|---|---|---|
  | `RESERVATION_CREATED` | store | `POST /reservations` (in the transaction) | reservation, product |
  | `RESERVATION_ACCEPTED` | restaurant | accept (in the transaction) | reservation, product |
  | `RESERVATION_REJECTED` | restaurant | reject (in the transaction) | reservation, product |
  | `RESERVATION_CANCELLED` | store | cancel by the restaurant (in the transaction) | reservation, product |
  | `PRODUCT_SOLD_OUT` | store | accept, or a move to donations, that makes the product `Sold` (in the transaction) | product |
  | `PRODUCT_EXPIRED` | store | expiry job, per expired product | product |
  | `RESERVATION_EXPIRED` | restaurant | expiry job, per cancelled reservation | reservation, product |
  | `PRODUCT_EXPIRING_SOON` | store | reminder job: `Available` product with `expiry_date = CURRENT_DATE + 1` and at least one Pending reservation | product |
  | `PICKUP_TODAY` | restaurant | reminder job: `Confirmed` reservation with `pickup_date::date = CURRENT_DATE` | reservation, product |
  | `RESERVATION_COMPLETED` | restaurant | complete by the store (in the transaction) | reservation, product |
  | `PICKUP_MISSED` | restaurant | cancel-overdue by the store (in the transaction) | reservation, product |
  | `PRODUCT_REMOVED_BY_ADMIN` | store | admin removes a product (in the transaction; `details` = reason) | product |
  | `DONATION_REMOVED_BY_ADMIN` | donor | admin removes a donation (in the transaction; `details` = reason) | donation |
  | `PLATFORM_ANNOUNCEMENT` | every unblocked store and/or restaurant of the audience | admin sends an announcement (bulk `INSERT ... SELECT` in `createAnnouncement`, not `createNotification`) | announcement (`GET /notifications` adds `announcement_title_bs`, `announcement_title_en`) |
  | `RESERVATION_CANCELLED_BY_ADMIN` | the other party; both parties for a cancelled reservation | admin blocks a user (each Pending reservation) or removes a product (its restaurants), without a reason; admin cancels a reservation, with `details` = reason | reservation, product |
  | `CREDIT_REQUEST_CREATED` | every unblocked admin | a store or restaurant sends a subscription or top-up request, or the renewal job creates one (`notifyAdminsOfCreditRequest`, one `INSERT ... SELECT`) | credit request (`GET /notifications` adds `credit_request_type`, `credit_amount` (the request's `credits`), `credit_requester` (business name, else email)) |
  | `CREDIT_REQUEST_APPROVED` / `CREDIT_REQUEST_REJECTED` | the requester | an admin decides the request (in the transaction; the admin note is never in the notification) | credit request |
  | `CREDIT_RENEWAL_CREATED` | the requester | `createRenewals` creates their renewal (job or the auto-renew switch) | credit request |
  | `CREDIT_REQUEST_EXPIRED` | the requester | the renewal job expires their pending request | credit request |
  | `CREDIT_RENEWAL_SKIPPED` | the subscriber | in the renewal window their auto-renew plan is no longer offered; at most once per 7 days | none |

  | `RESERVATION_CANCELLED_STORE_CLOSED` | restaurant | a branch is deactivated (by its headquarters or an admin), each Pending reservation | reservation, product |
  | `BRANCH_BLOCKED` / `BRANCH_UNBLOCKED` | the branch's headquarters (every unblocked COMPANY user of the company) | an admin blocks (with the reason as `details`) or unblocks a branch | branch (`notifications.branch_id`; `GET /notifications` adds `branch_name`) |
  | `BRANCH_DEACTIVATED` / `BRANCH_REACTIVATED` | the branch's headquarters | an admin deactivates or reactivates a branch (not when the headquarters does it itself) | branch |
  | `BRANCH_TOPUP_REQUESTED` | the branch's headquarters | a branch asks it for a top-up | credit request, branch |
  | `BRANCH_CREDIT_REQUEST_APPROVED` / `_REJECTED` / `_EXPIRED` | the branch's headquarters | an admin decides a branch's request, or the renewal job expires it | credit request, branch |
  | `CREDIT_TOPUP_COMPANY_APPROVED` / `_REJECTED` | the branch | its headquarters forwards its top-up to the admins or rejects it (the note as `details`) | credit request |

  A branch also still gets the requester's types (`CREDIT_REQUEST_APPROVED`, `_REJECTED`, `_EXPIRED`, `CREDIT_RENEWAL_CREATED`). `GET /notifications` adds `credit_company` (the requester's company) so a branch's request reads "Bingo d.o.o. → Bingo Tuzla". `notifyCompanyHqOfCredit(db, requestId, type, message)` sends the headquarters' credit types (one `INSERT ... SELECT` over the unblocked headquarters logins of the requester's company; nothing for a user without one). `notifyCompanyHq(db, branch, type, details?)` in `utils/notifications.ts` sends the branch types (one `INSERT ... SELECT`; nothing for a store without a company). Adding a type means updating `NotificationType` on both sides, the `notifications.types` keys in both locale files and `NOTIFICATION_META` on the client.
- **Expiry job** (`jobs/expireProducts.ts`, started from `server.ts` only): `expireProducts()` marks `Available` products past `expiry_date` as `Expired`, cancels their **Pending** reservations (refunding each restaurant's credit, actor `SYSTEM`) and notifies the stores and those restaurants, all in one transaction. Confirmed reservations are left as they are: the store already agreed to hand that food over, and it closes them itself (complete, or cancel-overdue after a missed pickup). In the same transaction `Available` donation offers past `expiry_date` become `Expired` (no notification yet, nobody but the donor sees them). `startExpirationJob()` runs it once at startup (to catch up on midnights missed while the server was down) and then on cron `0 0 * * *` in `APP_TIMEZONE`. Expiry checks in SQL use `expiry_date < CURRENT_DATE`, so a product is still valid on its expiry day.
- **Credit renewal job** (`jobs/creditRenewals.ts`, started from `server.ts` only): `runCreditRenewals(now)`, in one transaction, expires PENDING and COMPANY_REVIEW requests whose month has ended (`EXPIRED`, each requester gets `CREDIT_REQUEST_EXPIRED`, a branch's headquarters `BRANCH_CREDIT_REQUEST_EXPIRED`) and, in the renewal window (`isRenewalWindow`: the last `RENEWAL_DAYS_BEFORE` (2) days of a credit month), calls `createRenewals(client, now)`. `createRenewals` creates a PENDING `AUTO_RENEW` subscription request for the next month with the same plan for every ACTIVE subscription with `auto_renew` and notifies the admins and the user (`CREDIT_RENEWAL_CREATED`). Branches are renewed like any store (`requested_by` null). Skipped: blocked users (also deactivated branches and branches of a blocked company, via `notBlocked`), users who already have next month's subscription, a pending subscription request for it, or an earlier renewal for it in any status (so a withdrawn or rejected renewal is not created again; with `explicit` a withdrawn one does not block). An inactive plan is not renewed; its subscriber gets `CREDIT_RENEWAL_SKIPPED` instead. The insert uses `ON CONFLICT DO NOTHING`, so a request the user sends at the same instant skips only that row instead of failing the whole run. Returns `{ created, expired }`. `startCreditRenewalJob()` runs it at startup and on cron `10 0 * * *` in Europe/London.
- **Reminder job** (`jobs/notificationReminders.ts`, started from `server.ts` only): `sendReminders()` inserts `PRODUCT_EXPIRING_SOON` and `PICKUP_TODAY` with `INSERT ... SELECT ... WHERE NOT EXISTS` (same type for the same product or reservation), so each reminder is sent once no matter how often it runs; it returns `{ expiringSoon, pickupToday }` counts. `startReminderJob()` runs it at startup and on cron `0 7 * * *` in `APP_TIMEZONE`.
- **Soft delete and history:** reservations are never deleted, products are marked `Removed`.
- **Pickups:** only the store moves a reservation to `Completed` (`PATCH /:id/complete`) or cancels a missed one (`PATCH /:id/cancel-overdue`). Statistics of delivered or saved food (store profile counts, dashboard food saved and savings, admin and footer food saved, reports) count only `Completed`; the dashboards' "Confirmed reservations" card counts accepted ones (Confirmed + Completed).
- **Credits** (the product and reservation flows charge and refund as noted in the endpoint tables above; requests and approval are under Credits and Admin credits). Stores pay 1 credit per published product, restaurants 1 per reservation; donations are free. Controllers call the service inside their own transaction and answer a thrown `HttpError` (e.g. the 402) with `error.body()` in their catch. Where refunds happen: product delete and complete move to donations (same day, nothing reserved); restaurant cancel (same day); store reject, expiry job, admin block / product removal / reservation cancel (forced); never for cancel-overdue (a no-show) or an admin product removal (the store). Rules the service implements:
  - **Time:** credit days and months change at 00:00 **Europe/London** (01:00 Sarajevo, also across DST), computed in Node with `utils/creditTime.ts` (`creditDay`, `creditMonth` → `YYYY-MM-01`, `nextMonth`, `monthEnd`), never with `CURRENT_DATE` (the pool session runs in `APP_TIMEZONE`). Every service function takes `now` (default `new Date()`) so tests can move the clock, and writes it as `created_at`.
  - **Balance** (`getBalance(db, userId, now)` → `{ periodStart, periodEnd, subscription, hasActiveSubscription, total, used, available }`) is computed from the ledger rows of the current month, never stored: Total = plan + top-up grants + adjustments + refunds of charges from earlier months; Used = charges − refunds of same-month charges; Available = Total − Used, and 0 without an active subscription for the month (rows recorded for such a month count once the user subscribes in it). Unused credits never move to the next month.
  - **Charges** (`chargeForProduct`, `chargeForProducts` for the all-or-nothing CSV import, `chargeForReservation`) lock the user's subscription row for the month (`FOR UPDATE`), check the balance and insert one `-1` row per item with the category snapshot, all in the caller's transaction. Lock order: the product/reservation first, then the subscription. No subscription or not enough credits → `InsufficientCreditsError`: 402 `{ error: "Not enough credits.", code: "INSUFFICIENT_CREDITS", hasActiveSubscription, actionUrl }` (`/my-profile#topup` with a subscription, else `/my-profile#subscription`). `HttpError` takes optional `details` that `body()` adds next to `error`.
  - **Refunds** find the newest unrefunded charge of the product/reservation and insert `+1` into the **current** month (with that month's subscription, or none), copying the category; `refunds_transaction_id` is UNIQUE and the insert uses `ON CONFLICT DO NOTHING`, so a charge is refunded at most once. They return `{ refunded: true, transaction }` or `{ refunded: false, reason }` (`NO_CHARGE` (also for data from before credits), `DAY_PASSED`, `HAS_RESERVATIONS`, `ALREADY_REFUNDED`). `refundForProduct` (delete, or moved to donations completely): only on the credit day of the charge and only if the product has no Pending/Confirmed/Completed reservation (Rejected and Cancelled do not count). `refundForReservation(client, id, { forced, by })`: `forced` (store rejected, expiry job, admin cancellations) refunds on any day; not forced (the restaurant's own cancel) follows the same-day rule (`isRefundEligible(chargeCreatedAt, now)`).
  - **Grants:** `grantPlan` creates the subscription for its month (current or later; a past month → 400 `"This month has already ended."`, a second one → 400 `"The user already has a subscription for this month."`) and a `PLAN_GRANT` into that month; `grantTopup` adds a `TOPUP_GRANT` to the current month and needs an active subscription there (400 `"An active subscription for the current month is required."`); `adjustCredits` writes an `ADMIN_ADJUSTMENT` (whole number ≠ 0, reason required) into the current month and refuses to take the available balance below zero (400 `"The balance cannot go below zero."`).
- **Global error handling** (`app.ts`, after the routers): unknown routes → 404 `"Route not found."`; `HttpError` (`utils/httpError.ts`, carries a status and optional extra body fields) → that status and `error.body()`; multer errors → 400 (`"The image can be at most 5MB."`); malformed JSON → 400 `"Invalid request format."`; anything else → 500 `"A server error occurred."`. Controllers still handle their own errors; this covers middleware and body parsing.

## Conventions

- Controller shape: `try { ... } catch (error) { console.error(...); return res.status(500).json({ error: "..." }) }`, always `return res...`.
- Failures: `{ error }`; successes: `{ message, <entity> }`. 404 for missing, 403 for not-owner, 400 for validation and invalid state.
- Dynamic filters: build the `WHERE` with `values.push(...)` and `$${values.length}`, add `ORDER BY` last. Declare `values` as `(string | number)[]` when it mixes types.
- **Pagination** (`utils/pagination.ts`): `parsePage(req.query, defaultLimit)` reads `limit` (1–100) and `offset` (≥ 0) and returns null for anything else, which the controller answers with 400 `"Invalid filter."`; `listPage(columns, from, orderBy, values, page)` runs `SELECT COUNT(*) <from>` and the page query. Every paged list keeps its response key and adds `total` (all matches for the current filters, not the page). Defaults: `CARD_PAGE_SIZE` 12 for card lists (marketplace, own products, reservations, completed pickups, stores, donations), `TABLE_PAGE_SIZE` 10 for a store's or restaurant's own credit requests, `ADMIN_PAGE_SIZE` 20 for every admin list (including the credit overview, requests and a user's ledger). Every paged `ORDER BY` ends with `id DESC` (or another unique key before it), so rows with equal timestamps or names never repeat or go missing between pages. Not paged: notifications (50 newest), credit history, reports, pickup counts, today/upcoming pickups.
- **Sorting the admin tables** (`parseSort(req.query, columns, defaultOrder, tieBreaker)` in `utils/pagination.ts`): `sort` must be a key of the endpoint's whitelist (`USER_SORTS`, `PRODUCT_SORTS`, `RESERVATION_SORTS`, `DONATION_SORTS` in `admin.controller.ts`, `OVERVIEW_SORTS` in `adminCredits.controller.ts`), each mapped to an SQL expression in code, so the query value never reaches SQL; `dir` is `asc` (default) or `desc`. Anything else (an unknown key, another table's key, a bad `dir`, also without `sort`) is 400 `"Invalid filter."`. Empty values mean "not set" and keep the default order. The order is `<expression> ASC|DESC NULLS LAST, <table>.id DESC`: empty values come last in both directions and the id keeps the pages stable. Sorting combines with every filter and with paging; `total` is unchanged.
- Priority sorting uses `ORDER BY CASE WHEN status = '...' THEN 0 ... END, created_at DESC`.
- Ownership checks compare the resource owner with `req.user.id` (directly, or through the product's `store_id`).
- All server text is English: error and success messages (asserted by tests) and log lines. The client does the UI translation: notifications are translated from `type` (the stored `message` is an English fallback), the CSV reports take `lang`, and every `error` / `message` is translated on the client by its exact English text (`client/src/i18n/locales/server.bs.json`; a client test fails when a server text has no translation or a translation no longer matches a server text). Adding or rewording a message means updating that file in the same change. Keep messages short and plain. Examples: `"Product created successfully."`, `"All fields are required."`, `"Product not found."`, `"You do not have the required role for this action."`, `"Not enough product available."`, `"Product has active reservations and cannot be deleted."`.

## TypeScript notes

- Local imports use `.js` extensions (nodenext), packages never do.
- `req.body` is `any`; destructure it and annotate with an interface where one exists (`ProductFields`, `RegisterBody`, `LoginBody`). `req.query` values are cast with `as string`. `req.params` values are strings.
- `catch (error)` is `unknown`: use `error instanceof Error && 'code' in error` before reading Postgres codes.
- `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are on: expect `rows[0]` to possibly be undefined.
- `process.env.JWT_SECRET!` is asserted where used.
- Shared types: `types/auth.ts` (`AuthUser`, `Role`), `types/express.d.ts` (augments `Express.Request` with `user?` and `file?`).

- `vitest.config.ts`: `globals: true` (`describe`/`it`/`expect`/`vi` without imports), `fileParallelism: false` because every file shares the one test database, `setupFiles: ["tests/setup.ts"]`. Each file runs in its own module graph with its own pool; `setup.ts` closes it in `afterAll`.
- `tests/helpers.ts`:
  - `insertCompany(name)` inserts a company row; `insertUser(email, role, businessName?, credits?, companyId?)` takes the company of a `COMPANY` user or a branch store (company users get no business name and no credits). `cleanupCompanies(names)` (after `cleanupUsers`) deletes the companies, their users and the admin actions about them.
  - `registerAndLogin(email, role)` inserts the user straight into the database (public registration is closed; stores and restaurants get `business_name` "Test Business" so the marketplace lists them, admins none) and returns a `request.agent(app)` holding the login cookie (one agent per user when testing ownership). `insertUser(email, role, businessName?, credits?)` and `login(email, password?)` are the two halves; the bcrypt hash is computed once per file. Stores and restaurants get a current-month subscription with `credits` (default 1000; `null` = no subscription), so credits never limit a test that is not about them. `giveSubscription(userId, credits, now?)` adds one for the month of `now`.
  - `createProduct(agent, overrides)`, `createDonation(agent, overrides)` and `reserve(agent, productId, quantity)` throw if the API refuses, so setup failures are obvious. Also `productPayload()`, `donationPayload()`, `userId(email)` and `cityId(name)` (a city id from the migrated list; tests that filter by city use a city no other file uses, e.g. Olovo, Vareš, Kladanj, Breza).
  - `futureDate(days)` / `futurePickup(days)` build dates from the local date, so tests never go stale and agree with `CURRENT_DATE` around midnight.
  - `cleanupUsers(emails)` deletes their credit ledger rows (in a transaction with `app.ledger_maintenance` on), the admin actions and announcements of those users (RESTRICT), their reservations (RESTRICT; both their own and those on their products), then the users, which cascades to products, notifications, favorites and templates.

## CI

GitHub Actions, `.github/workflows/ci.yml`. Runs on every pull request to `main`, every push to `main` and by hand (`workflow_dispatch`, which runs everything). A new commit on the same PR/branch cancels the run in progress.

- `Detect changes` (`dorny/paths-filter`, pinned to a commit SHA) decides what runs: `server/**` → Backend; `client/**` and `server/src/**` → Frontend (the client test `serverMessages.test.ts` reads the server sources); `.github/workflows/**`, the root `package.json` or `package-lock.json` → both.
- `Backend` (`server/`): Node 24, `npm ci`, a `postgres:15` service container (same major as local development) with database `food_saver_test_db`, a `.env.test` written by the workflow with test-only values (`DATABASE_URL`, `JWT_SECRET`), migrations with `npx dotenv -e .env.test -- node-pg-migrate up`, `npm run typecheck`, `npm test` (default + `github-actions` reporters, so failures show as PR annotations), `npm run build`. `TZ=Europe/Sarajevo`, because the test helpers build dates from the process's local day and must agree with `APP_TIMEZONE`.
- `Frontend` (`client/`): Node 24, `npm ci`, `npm run typecheck`, `npm run lint`, `npm test` (same reporters), `npm run build`.
- `CI passed` runs always and fails if any job above failed or was cancelled (skipped is fine). It is the only check required by the `main` branch rules, so its name must not change.
- A failed run: `gh pr checks` shows which job failed, `gh run view <run-id> --log-failed` prints only the failed steps' logs.
- Lint: only `client/` has ESLint (`eslint.config.js`), and the `Frontend` job runs it. The server has no linter; its checks are the strict typecheck and the tests.
- Dependabot (`.github/dependabot.yml`): npm in `/`, `/server` and `/client`, plus `github-actions`, every Monday at 07:00 Europe/Sarajevo. Minor and patch updates come as one grouped PR per folder/ecosystem, majors as separate PRs; at most 5 open PRs per entry, commit messages prefixed `deps`. Its PRs go through CI like any other (a root lock change runs both jobs). It also bumps the SHA-pinned `dorny/paths-filter`.
- PR template (`.github/pull_request_template.md`): what and why, how it was tested, and a checklist (tests, i18n keys in `bs` and `en`, docs, safe migration, screenshots for UI changes).

## Seed

`npm run seed` (`src/scripts/seed.ts`, static lists in `src/scripts/seedData.ts`) replaces all data with a platform that looks like it has been in use for the last 61 days. It runs in one transaction and takes a few seconds.

- **Wipe:** deletes all rows (credit ledger (with `app.ledger_maintenance` on), admin actions, notifications, announcements, reservations, donation offers, products, users, then companies; everything else cascades from users). `plans` and `topup_packages` stay.
- **Accounts** (password `To12345678`, `SEED_PASSWORD`): admins `admin@demo.com`, `admin2@demo.com`; the company "Bingo d.o.o." (`COMPANIES` in `seedData.ts`) with its headquarters login `bingo@demo.com` (profile filled in, no temporary password, a `CREATE_COMPANY` action) and five branches at the end of `STORES` (`company: "Bingo d.o.o."`, no description or logo of their own, no `CREATE_USER` action since their headquarters created them): Bingo Sarajevo Centar `bingo.sarajevo@demo.com`, Bingo Visoko `bingo.visoko@demo.com`, Bingo Kakanj `bingo.kakanj@demo.com`, Bingo Zenica `bingo.zenica@demo.com`, Bingo Tuzla `bingo.tuzla@demo.com`, which go through the same simulated history as the other stores; 10 stores and 10 restaurants with full profiles spread over Sarajevo, Visoko, Kakanj, Zenica and Tuzla (each of the five has stores and restaurants, for the nearby step; `seedData.ts` names the city and `seed.ts` looks up its id, failing on a name that is not in `cities`), created over the first few days (each with a `CREATE_USER` admin action). Each business has an activity rate, so some stores publish far more than others, and a plan per month (`plans`, e.g. Basic → Standard), with or without auto-renew.
- **Credits:** every subscription goes through an approved `credit_requests` row (the first month right after the account was created, later months by an `AUTO_RENEW` request two days before the month, a plan-change request a few days before, or a request on the 1st), with the admin action and notifications. Every grant, charge and refund is written through `creditService` (`grantPlan`, `grantTopup`, `chargeForProduct`, `chargeForReservation`, `refundForProduct`, `refundForReservation`, `adjustCredits`) with the simulated time as `now`, so balances follow the real rules and never go negative. Extras: restaurants that run low buy top-ups, one rejected, one withdrawn and one expired request, one admin adjustment, and two pending requests (a next-month upgrade and a top-up). Bingo's branches have their plans requested by `bingo@demo.com` (source `COMPANY`; Sarajevo Centar, Zenica and Tuzla with auto-renew, whose renewals are `AUTO_RENEW` with no sender), and the headquarters is told of each decision; Bingo Zenica has a top-up waiting for the headquarters and Bingo Tuzla one the headquarters forwarded to the admin.
- **Day-by-day history:** stores publish products (expiry 2–8 days out); restaurants reserve from stores in their city (favorites preferred). Outcomes: mostly Completed (with `picked_up_at`), then cancelled by the restaurant (refunded on the same day), rejected (refunded), missed pickups, pending reservations cancelled when the product expired, and one admin cancellation. Products end as Sold (fully covered by accepted reservations), Expired, Removed (by the store the same day, refunded, or by an admin) or still Available. Every event writes the notification the app would send, with its timestamp; notifications older than 3 days are mostly read.
- **Current state:** each store has a current stock (115 products in total, expiry 1–10 days out, ~130 on offer with the history's leftovers), 25 Pending and 20 Confirmed reservations (pickups from later today up to 3 days out; Pending/Confirmed quantities always leave some stock, so these products stay on offer), and ~15 available donations.
- **Also:** donation offers of both types from stores (product lines) and restaurants (meals with allergens and temperature), favorites, product templates, three announcements (one expired, one ended by an admin, one active) with notifications and dismissals, and admin log entries for a password reset, a profile edit and a block/unblock.

Random choices use a fixed seed (mulberry32), so every run gives the same data relative to its run date. The script prints counts per status and the logins.

## Pending and known limitations

- **Deployment:** the auth cookie is `sameSite: "strict"`, so the frontend and the API must be served from the same site (the same domain, or subdomains of one domain such as `app.example.com` and `api.example.com`). Do not switch to `sameSite: "none"` without real CSRF protection: the origin check is only a second layer. Set `CLIENT_ORIGIN` to the deployed frontend origin(s); logo uploads on local disk are lost on Render restarts (needs cloud storage; Cloudinary is not available in the owner's country, so evaluate alternatives). With more than one server instance the cron jobs would run once per instance (they are idempotent, but a lock or a separate worker is cleaner).
- Server messages should become error keys translated on the client.
- `PUT /users/me`: replace `COALESCE` with a real PATCH that can clear optional fields.
- Migrations are still JavaScript. They have already run, so they stay as they are; a new migration can be written in TypeScript once `node-pg-migrate` runs with a TS loader (for example `tsx`).
- The server has no ESLint setup.
