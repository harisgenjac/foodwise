# Frontend (`client/`)

Reference for working on the UI. The source of truth is the code; exact route paths are in `src/App.tsx`.

## Stack

- React 19, Vite, TypeScript, Tailwind CSS (core utility classes only, with the design system's colour tokens; see Design system), `react-router-dom` 7
- `axios` (one configured instance), `react-hot-toast`, `react-i18next` + `i18next`, `lucide-react` (icons), `leaflet` + `react-leaflet` 5 (the location map, loaded lazily, see MyProfilePage)
- Scripts: `npm run dev` (http://localhost:5173), `npm run build`, `npm run lint`, `npm run preview`, `npm test` (Vitest, once), `npm run test:watch`, `npm run icons` (regenerates the favicon and app icons, see Design system), `npm run typecheck` (`tsc --noEmit`; Vite does the bundling).
- Env: optional `VITE_API_URL` (backend origin without `/api`, default `http://localhost:3000`), for example in `client/.env.local`.
- `tsconfig`: `strict`, `module esnext`, `moduleResolution bundler`, `jsx react-jsx`, `lib` with `dom`, `types: ["vite/client", "vitest/globals"]`, `verbatimModuleSyntax`, `noEmit`, `include: ["src", "vite.config.ts"]`. Everything is TypeScript (no `allowJs`); the only JS file left is `eslint.config.js` (see Pending).
- `vite.config.ts` holds both the Vite and the Vitest config (`test` block).

## Routing and layout

- `/login` and `/forgot-password` are wrapped in `PublicRoute` (redirects to `/dashboard` when logged in); `/reset-password` and `/set-password` (the emailed links) are not, so they work with or without a session. These pages share `components/AuthLayout` (props `title`, `subtitle?`): the photo panel on large screens, the language switch, one card (`p-6`, `sm:p-8`) and the app's footer under all of it (a fragment: the photo and form row is a full screen high, the footer follows).
  - `LoginPage` reads `LoginState` from the navigation state: `registrationClosed` (below) and `passwordReset` (a green `role="status"` box "Lozinka je promijenjena…"). Under the password field a "Zaboravili ste lozinku?" link to `/forgot-password` (44 px on phones).
  - `ForgotPasswordPage`: one email field; `POST /auth/forgot-password`; the server's message (the same for every email) replaces the form in a green `role="status"` box, with a hint to check spam and a link back to login. A server error (an invalid email) shows above the form.
  - `ResetPasswordPage` (`/reset-password?token=…`, and `/set-password?token=…` for an invitation, worded with `auth.invite.*` ("Postavite svoju lozinku"); after an invitation the server signs the user in, so the page calls `refreshUser()` and goes to `/my-profile`, where the account setup continues as after a temporary password): first `POST /auth/reset-password/check` (a spinner meanwhile); no token or a refused one shows "Link više ne vrijedi" with a button to `/forgot-password`. Otherwise the new password twice (`user.newPassword`, `user.repeatPassword`, mismatch checked on the client, the 8-character hint), `POST /auth/reset-password`; on success `refreshUser()` (the server ended this browser's session too, so the 401 clears the user) and `/login` with `state.passwordReset`. An answer with `code: "INVALID_LINK"` switches to the expired view; other errors show above the form. Texts under `auth.forgot.*` and `auth.reset.*`.
- `/register` redirects to `/login` with `state.registrationClosed`, which shows an info banner there: an admin creates store, restaurant and admin accounts. `RegisterPage` stays in the code (not routed) for the planned public roles. `/` redirects to `/dashboard` (`replace`), so a visitor who is not logged in lands on `/login` through `ProtectedRoute` instead of a blank page. Any other unknown path (`*`) renders `pages/NotFoundPage` outside the Layout: "Page not found" (`notFound.*`) with the logo, the language switch and one button to `/dashboard`, or to `/login` for a visitor who is not logged in.
- Everything else is nested under `<ProtectedRoute><Layout /></ProtectedRoute>`, so the Header and Sidebar never render before auth is resolved. `/pickups`, `/reports`, the donation pages (`/donate-food`, `/donate-food/new`, `/donate-food/:id/edit`), `/sponsor`, `/products/:id` and `/orders/:id` are open to both business roles (`<ProtectedRoute role={["STORE", "RESTAURANT"]}>`; the pages adapt to the role), so an admin is sent away from them. `/credits` is store-only (`role="STORE"`): restaurants pay no credits, so a restaurant is sent to `/dashboard`. `/dashboard`, `/my-profile` and `/notifications` are open to every role; `DashboardPage` redirects an admin to `/admin`, which is also where an admin lands after login, and renders `pages/company/CompanyOverviewPage` for a `COMPANY` user. `/company/profile` (`CompanyProfilePage`), `/company/branches`, `/company/branches/new` (declared before `:id`), `/company/branches/:id`, `/company/credits` and `/company/reports` are `<ProtectedRoute role="COMPANY">`; every store, restaurant and admin route sends a `COMPANY` user to `/dashboard`. The admin pages use `<ProtectedRoute role="ADMIN">`: `/admin`, `/admin/users`, `/admin/users/new`, `/admin/users/:id`, `/admin/products` (optional `?store_id=`), `/admin/donations` (optional `?donor_id=`), `/admin/orders` (optional `?user_id=`), `/admin/orders/:id`, `/admin/announcements`, `/admin/actions`, `/admin/credits`, `/admin/credit-requests` (optional `?user_id=`), `/admin/companies`, `/admin/companies/new`, `/admin/companies/:id`. Role-specific pages are also wrapped in `<ProtectedRoute role="STORE">` (`/add-product`, `/import-products`, `/my-products`, `/edit-product/:id`, `/orders`, `/packing`) or `<ProtectedRoute role="RESTAURANT">` (`/search`, `/stores`, `/stores/:id`, `/my-orders`, `/cart`; `/browse-products`, the old address, redirects to `/search`); the wrong role is redirected to `/dashboard`. `Layout` holds `isSidebarOpen` (the desktop rail) and `isMenuOpen` (the phone drawer) and renders `<NotificationsProvider>` around `<Header />`, `<Sidebar />` and `<main><div className="flex-1"><AnnouncementBanner /><CreditBanner /><AccountSetupGate /><Outlet /></div><Footer /></main>`, then `MobileDrawer` (while open and not locked) and `BottomNav` (stores and restaurants), all inside `<CreditsProvider enabled>` (stores and restaurants whose account is set up). **Printing:** the header, rail, banners, footer, drawer and bottom bar sit in `contents print:hidden` wrappers, so a printed page (the packing list) shows only its own content; a page hides its own buttons with `print:hidden` and keeps cards whole with `print:break-inside-avoid`. **The window scrolls, not `<main>`** (root `min-h-dvh`, no `h-screen` or `overflow-y-auto`), so the iOS toolbar collapses and tap-to-top works; the header is `sticky top-0` and the rail `sticky top-16`, and `Layout` scrolls the window to the top on every pathname change. `<main>` is a flex column (the footer sits at the bottom of short pages and after the content of long ones) with 16 px side padding below `sm` (`px-4 sm:px-6`); for stores and restaurants its bottom padding below `md` is `calc(5rem + env(safe-area-inset-bottom))`, so nothing hides behind the bottom bar. Sticky side panels inside a page (the previews on Add/Edit product, donations, CSV import, and the admin and company create forms) use `lg:sticky lg:top-22` so they stop below the header. Full-height screens use `dvh` (`LoadingSpinner fullScreen`, Login, Register). `index.html` sets `viewport-fit=cover` for the safe-area insets.
- **Phone navigation** (below `md`, `components/navigation/`):
  - `SidebarNav` (props `expanded`, `locked`, `onNavigate`) holds every role's links, the humanitarian section and the badge counts; the desktop `Sidebar` rail and the drawer both render it, so links are defined once.   - `MobileDrawer` (prop `onClose`; id `MOBILE_DRAWER_ID` for `aria-controls`): a `role="dialog"` panel (`w-72 max-w-[85vw]`, labelled `sidebar.menu`) over a backdrop, with the logo, a 44 px close button (`sidebar.closeMenu`) and `<SidebarNav expanded>`. Focus moves to the close button, Tab is kept inside, and on close focus goes back to the element that opened it; `<html>` does not scroll while it is open (all through `hooks/useOverlay`, like `Modal`, see Dialogs). Its links (`SidebarNav replace`) replace the drawer's history entry, so Back from the new page goes to the page before it.   - `BottomNav` (props `role`, `onOpenMore`, `isMoreOpen`, `locked`): `nav` labelled `bottomNav.label`, `fixed bottom-0 z-30 md:hidden`, `pb-[env(safe-area-inset-bottom)]`; 5 equal items at least 56 px high (icon above a short `bottomNav.*` label), active like the sidebar (brand text and a bar on top; `/dashboard` matched with `end`), and "More" (`bottomNav.more`, `aria-expanded`) last, which opens the drawer. The pages per role come from one config, `BOTTOM_NAV_ITEMS` in `bottomNavItems.ts` (store: dashboard, my products, orders, pickups; restaurant: dashboard, browse products, my orders, pickups); `hasBottomNav(role)` is true only for stores and restaurants, so admins and company headquarters have the drawer only. Locked like the sidebar (`aria-disabled`, `inert`, dimmed); the `AccountSetupGate` overlay (z-40) covers it. `AnnouncementBanner` (stores, restaurants and company headquarters, which get the store announcements) loads `GET /announcements/active` once and shows each as a blue card (`Megaphone`, `role="status"`) in the interface language, falling back to Bosnian when the English title or body is missing; the X hides it at once and sends `POST /announcements/:id/dismiss`. **Account setup lock:** `utils/accountSetup.ts` → `getAccountSetup(user)` returns `{ needsPassword, missingFields, locked }`: `needsPassword` is `must_change_password` (any role), `missingFields` the empty required fields by role (`REQUIRED_FIELDS_BY_ROLE`: stores and restaurants `REQUIRED_PROFILE_FIELDS` (first and last name, business name, city, phone, address); a `COMPANY` user first name, last name and phone; an admin none). While `locked`: `AccountSetupGate` covers every page except `/my-profile` with a blurred overlay (fixed below the header, `bg-white/40 backdrop-blur-sm`) and a dialog that cannot be dismissed, listing the steps and linking to My profile; on `/my-profile` it shows an amber strip with the same steps instead. The `Sidebar` (`locked`: dimmed, `inert`) and the `Header` (`locked`: toggle, logo link and bell disabled) leave only the profile menu (My profile, logout) and the language switcher usable; `AnnouncementBanner` is hidden; `NotificationsProvider` gets `enabled={false}` while a temporary password is set (the server would answer 403). Saving the profile or the password calls `refreshUser()`, which lifts the lock.

## Auth

`AuthContext` exposes `{ user, loading, login(email, password), logout(), refreshUser() }`. It installs an axios response interceptor: any 401 (except from `/auth/login`) clears `user`, so an expired session sends the user to `/login` instead of leaving a broken page. On mount it calls `GET /users/me` (full profile, not `/auth/me`). The login response has only the basic fields, so `login` calls `refreshUser()` (`GET /users/me`) right after; `MyProfilePage` also calls it after saving the profile or the logo, so the Header and dashboard hero show the current business name and city without a reload. `useAuth()` throws if used outside the provider. The cookie is httpOnly, so the client never touches the token. Role checks in UI use `user?.role === "STORE" | "RESTAURANT" | "ADMIN" | "COMPANY"`; a new role needs every `Record<Role, ...>` (`ROLE_STYLES`, `ROLE_ICONS`, `REQUIRED_FIELDS_BY_ROLE`) and the role branches in `Sidebar`, `Header`, `DashboardPage`, `MyProfilePage`, `AdminUserDetailsPage`, `EditProfileModal` and `getNotificationLink` (a `COMPANY` user falls back to `/dashboard`). Login shows a blocked account's server message (403, it includes the admin's reason) instead of the generic error, and the page no longer links to registration (`auth.accountByAdmin` explains that an admin creates accounts).

## Data fetching

- `useFetch<T>(url, dataKey, params)` returns `{ data: T[], total, meta, loading, fetching, error, refetch }` (`meta` is the whole last response body, for fields next to the list such as `outside_radius_count`; reset with `data`). `dataKey` selects the array from the response (`"products"`, `"orders"`, `"stores"`); `total` is the response `total` for paginated endpoints (else `null`). The first load starts immediately; later changes of `url` or the filters are debounced by 500ms, while a change of only `limit`/`offset` (Load more, a page number) loads at once; `refetch()` runs immediately. A new request aborts the previous one (`AbortController`), and a filter change aborts the request in flight right away (not only when the debounced one starts). Only the latest request may touch the state: a response that still arrives for an older request is ignored, so a slow old response never overwrites newer filters. The optional 4th argument `{ resetKey }` (the selected tab on PickupsPage and MyOrdersPage) marks a different list: when it changes, the data is dropped during that same render (`data = []`, `total = null`, `loading = true`) and the request goes out without the debounce, so a tab never shows the previous tab's list. Text search keeps the previous results visible while the debounce runs. `loading` is true until the first response for the current `resetKey`, `fetching` while any request is in flight, `error` after a failed load (pages then show `LoadErrorState`, never a misleading "no results"). Always pass the type argument: `useFetch<Product>("/products/mine", "products", { name, status, category, expiryWithinDays })`.
- `LiveEventsContext` (provider in `Layout`, outermost, `enabled` false with a temporary password) opens one `EventSource` on `${API_ORIGIN}/api/events` with `withCredentials` per tab (none where the browser or jsdom has no `EventSource`) and passes its `order`, `notification` and `resync` events (`LiveEvent`) to the subscribers; an event only names what changed, so the subscriber loads it through the API. The browser reconnects a dropped stream by itself. Every open of the stream, the first one after a page load included, is passed on as `resync`: events sent before it was connected (while it was down, or after the page loaded its data) are lost, so the pages load again; a refused stream (an expired login, the server down) is opened again after 30 s (`LIVE_RETRY_MS`). `useLiveEvents(listener)` subscribes while mounted (no-op outside the provider; the latest listener is used). `useLiveOrderRefresh(refresh, orderId?)` calls `refresh` 300 ms (`LIVE_REFRESH_DELAY_MS`) after the last `order` event (of `orderId` only, when given) or `resync`, so close events load once, with the page's latest `refresh` (a tab switched meanwhile loads its own list): OrderDetailsPage (its order), MyOrdersPage (the list and the summary), StoreOrdersPage (the list) and PickupsPage (the list and the counts) use it, so the other side's decision, a new order, a pickup or the courier's progress shows without reloading.
- `NotificationsContext` (provider in `Layout`) holds one shared notification state, so the Header bell and NotificationsPage stay in sync. `useNotifications()` returns `{ notifications, unreadCount, loading, markAsRead, markAllAsRead, deleteNotification, deleteRead }` and throws outside the provider. It refreshes on a live `notification` or `resync` event, every 50s (a fallback for a stream that cannot stay open) and when the window regains focus. Mark/delete update the state optimistically; if the request fails they show the `notifications.actionError` toast and reload from the server; `deleteRead` reloads afterwards because the list is capped at 50. The file also exports the `Notification` interface and `NotificationType` union (keep it in sync with `server/src/utils/notifications.ts`).
- `CartContext` (`CartProvider` in `Layout`, enabled for set-up restaurants only) holds one copy of `GET /cart` for the header's cart link, `AddToCartModal` (the line already in the cart) and the cart page, reloaded on every page change and when the window regains focus (another device or staff member may have changed it). `useCart()` returns `{ cart, status ("loading" / "ready" / "error"), count, refresh, setCart }`; every `/cart` call answers the whole cart, which the caller hands to `setCart`. Outside the provider there is no cart (`count` 0).
- `CreditsContext` (`CreditsProvider` in `Layout`, enabled for set-up stores only) holds one copy of `GET /credits/me` for the banner, the form hints, My profile and the Credits page, reloaded on every page change and when the window regains focus. `useCredits()` returns `{ credits, loadedAt, refresh }`; outside the provider (admins, isolated tests) `credits` is null and everything credit-related stays hidden.
- `useLogoPreview()` (My profile and the company profile): `{ file, preview, select(file), clear() }`. `select` accepts only `LOGO_MIME_TYPES` (`image/jpeg`, `image/png`, `image/webp`, the server's list; the inputs use `accept={LOGO_ACCEPT}`, but the picker can be bypassed, so the type is checked again) and returns `false` otherwise, and the page shows `user.invalidImageType`. The preview is only `URL.createObjectURL(file)`, used as an `<img>` `src`, never the file name; it is revoked when replaced, cleared or on unmount.
- Pages that do not use `useFetch` and why: single-record pages (`EditProductPage`, `ProductDetailsPage`, `OrderDetailsPage`), `StoreDetailsPage` (one request returns the store; its products (`/products?store_id=`, the marketplace rules) and its "Moje narudžbe" tab (`/orders/mine?store_id=`) use `useFetch`), the store home page (one request into local state: the impact), the restaurant home page (three independent requests into local state: the impact, the nearest stores and the offer rows), `MyProfilePage`, `AddProductPage` (templates load once into local state).
- **Load more** (card lists): `usePagedLimit(pageSize, resetKey)` → `{ limit, loadMore }`; the page passes `limit` to `useFetch`, `loadMore` raises it by one page, and a new `resetKey` (`JSON.stringify` of the filters) starts from the first page again. Reloading after an action (`refetch()` after accept, reject, cancel, delete, move to donations, add to cart) keeps the current `limit`, so the list does not collapse to the first page. `components/LoadMore` (props `shown`, `total`, `fetching`, `onLoadMore`) shows "Showing 12 of 40" (`common.showingOf`) and a "Load more" button (`common.loadMore`, "Loading..." and disabled while fetching), and renders nothing once everything is shown. Count pills use the server `total` (`total ?? data.length`). Used with `CARD_PAGE_SIZE` (12) on BrowseProducts, MyProducts, StoreOrders, MyOrders (Active; History uses `HISTORY_PAGE_SIZE` = 20), Stores, StoreDetails (both tabs), DonateFood and the Picked up tab of Pickups, and with `LIST_PAGE_SIZE` (10) for the credit requests in `SubscriptionSection`. Admin tables use numbered `Pagination` instead; a page never has both.
- Pattern for typed responses: `const data: Product[] = response.data.products; setList(data);`. Do not wrap an array response in another array.
- Query params are camelCase in state and snake_case on the wire where the backend expects it (`business_name`, `store_id`).

## TypeScript patterns

- `import type { ... }` for type-only imports; local imports end in `.js` even though the files are `.ts`/`.tsx`.
- Inline handlers need no annotations (`onChange={(e) => setName(e.target.value)}`). A standalone handler does, for example `(e: React.ChangeEvent<HTMLInputElement>)`. For form submit use `React.SyntheticEvent<HTMLFormElement>` (`FormEvent` is deprecated in current `@types/react`).
- Props are typed with an interface or inline object: `({ children }: { children: React.ReactNode })`.
- Non-null assertion only where the app guarantees it: `useParams()` id inside a route that requires it, `document.getElementById("root")!`, `selectedProduct!` inside a handler that only runs with the modal open.
- `catch (err)`: use `apiErrorMessage(err)` from `api/axios.ts` (the server's `error` text or null), then fall back to a `t()` message. Server-provided messages are English (backend rule) and are shown as-is, in either UI language.
- Optional values used as an object key need a fallback: `categories[product.category || ""]`.

- **Server texts.** The server sends `error`, `message` and CSV `rowErrors[].error` in English. The axios response interceptor in `api/axios.ts` runs them through `translateServerData` / `translateServerMessage` (`i18n/serverMessages.ts`), so pages read `err.response.data.error` and `response.data.message` already translated (blob errors on Reports call `translateServerMessage` themselves). - Same key name in different sections is fine (`product.editTitle`, `user.editTitle`). Reuse an existing key rather than duplicating it. Add a shared `common` section only when a string is repeated in many places.
- Categories, units and statuses are objects: `const categories = t("categories", { returnObjects: true }) as Record<string, string>;` then `categories[product.category] || product.category`. Same for `units`, `productStatus`, `orderStatus`. Dropdown options come from `Object.entries(categories)`.

- Some existing keys contain typos (`noNofiticationsTitle`). They are consistent across both JSON files and the code; renaming one means changing both files and every usage together.
- Raw codes that need no translation stay as they are (the unit code where a label shows it raw). `CATEGORY_IMAGES` is language-neutral and stays.
- `utils/categories.ts` and `utils/units.ts` still hold the old Bosnian label maps; the UI no longer reads them for display, but the keys mirror the backend codes.
- A few placeholders and fallback strings may still be hard-coded Bosnian; grep when touching a page.

## Design system

The brand is **Još vrijedi** (`BRAND_NAME` in `utils/brand.ts`, never translated). The palette and the logo files are in `design/brand/` (its README lists every token with its hex).

- **Colour tokens** (`client/src/index.css`, Tailwind v4 `@theme`). Tailwind's own palette is switched off (`--color-*: initial`), so only these exist (plus `white` and `black`) and a class such as `bg-orange-500` generates nothing:
  - `brand` (the green scale): the main colour. Primary buttons, active navigation, links, focus rings and key headings use `brand-800` (#166534), hover `brand-900`; light backgrounds `brand-50`/`100`.
  - `accent` (the orange scale): prices, discount badges, highlights and attention points only (text `accent-700`, soft backgrounds `accent-100`/`200`). Never the colour of a main button.
  - `neutral` (stone, warm grey): the page background `neutral-50` (#FAFAF7), white cards and surfaces, borders `neutral-200`, body text `neutral-800`, muted text `neutral-500`.
  - `sand` (#F3F1EA, one shade): the warm beige of the home pages' bands only: the section band under the hero (and the hero's bottom curve) and the donation band.
  - `lime` (#BEF264, one shade): the highlight on the dark green (`brand-900`) of the home pages' hero and of the footer only: the second word of the brand (hero and footer), the hero's buttons, the tooltip titles and info buttons, the slider's arrows, the footer's focus rings and link hover. Never on a light background.
  - Status colours, each with one fixed meaning, used for every order, product, donation and credit status badge: `success` (green, a soft badge `bg-success-100 text-success-800` so it does not look like a button), `warning` (amber: pending, waiting), `danger` (red: errors, "expires today"), `info` (sky: neutral information). Status text on a soft background uses the 700 shade (800 for success).
- **60-30-10:** about 60% neutral (page, cards, text), 30% brand, 10% accent.
- **One primary button per screen** (filled `brand-800`, white text). Secondary buttons are white with a `brand-800` border and text.
- **Contrast:** text and interactive elements meet WCAG AA (4.5:1 for text, 3:1 for large text and UI borders): no text lighter than `neutral-500` on white, status text at 700. `e2e/tests/contrast.spec.ts` runs axe's `color-contrast` rule on the restaurant home, search, the store list, the store page, the store home, the store's products and orders, and the admin overview.
- **Charts:** brand for the main series, accent for the second, neutral for "unused" or "none", and the status colours where a chart shows statuses (the credit usage bar: success up to 70%, warning above 70%, danger from 90%).
- **Illustrations** (the home pages' chef, shopkeeper and background drawings in `HomeIllustrations.tsx`, the How it works drawings, the footer's drawings, the store tones in `utils/storeTone.ts`, the logo) keep their own hex colours, with greens and oranges from the palette and no teal.
- **Logo** (`components/brand/Logo`, props `variant`, `className` for the mark's size, `textClassName` for the name's, `decorative`): `mark` is the full mark (`design/brand/logo.svg`) as inline SVG; `full` is the mark plus the name as real text in the app font, bold, "Još" in `brand-800` and "vrijedi" in `accent-700` (like `logo-horizontal.svg`, whose SVG text is only a reference); `icon` is `app-icon.svg` (the simplified mark on a green square). The header shows `full` from `md` up with the sidebar open and the `mark` on phones and with the sidebar collapsed; the drawer and the 404 page show `full`; the login page a large `mark` with the name in white on the photo and `full` above the form on phones.
- **Fonts:** the app's default font everywhere, except the restaurant and store home pages' content, the restaurant and store My profile and the footer (`font-jakarta`, Plus Jakarta Sans 400–800) and their uppercase headings (`font-condensed`, Barlow Condensed 800: the donation band's heading and the footer's information links). The families are `--font-jakarta` and `--font-condensed` in `index.css`.

## Dialogs

- **`components/product/Modal`** (props `onClose`, `labelledBy` = the title's id, `children`) and its parts `ModalHeader`, `ModalBody`, `ModalFooter` (each takes `className`), plus `modalFormStyle` for a `<form>` that holds the body and the footer. Closing any other way goes back over the entry, deferred so that a dialog replaced by another at once (and React StrictMode's remount) keeps it, and Back that lands on an entry left behind by an overlay that navigated away is skipped.

## Confirmations

- **When to ask.** Confirm an action that cannot be undone, notifies another party, or spends credits in bulk: deciding or cancelling an order (the decision has its own summary step), a pickup or a missed pickup, deleting a product, the CSV import, "Delete read" notifications, withdrawing an automatic renewal request, and the admin's block, unblock, removals, order cancels and announcements. Do not ask for easily reversible actions (favorites, mark as read, deleting one notification, the auto-renew switch, withdrawing a request the user sent, a product template, which has its own two-step inline delete): dialogs shown too often get clicked blindly. Forms and explanation dialogs that already are the confirming step (`AddToCartModal`, the cart's checkout, `DonateProductModal`, `SubscribeModal`, `TopupModal`, the admin forms) get no extra one. `DonateFoodPage` keeps its own `Modal`, because a moved donation offers three choices.

## Feedback

Every message is shown in exactly one place: a toast or inline, never both.

- **Toaster.** `components/AppToaster` (rendered once in `main.tsx`) wraps react-hot-toast's `Toaster`: top right, 5000 ms for every type (set in `toastOptions`; calls pass no `duration`), at most 3 visible (an effect on `useToasterStore()` dismisses older ones), a close button on each toast (`ToastBar` render with `toast.dismiss`, `aria-label` from `common.closeToast`), pause on hover (the default), full width at the top below `sm`, `z-index` 9999 so toasts sit above modals (`z-50`) and may overlap the header.
- **Toast:** a one-time success, and a one-sentence action error the user does not fix in a form field: form submit errors from the server (product add/edit, donation add/edit, My profile, logo upload, password change, admin create user, announcement send, CSV import summary), errors of actions in lists and modals (add to cart, send an order, move to donations, credit requests, admin decisions, block/unblock, set password, credit adjustment, delete/cancel/accept/reject, favorites); adding or removing a favourite store also shows a success toast with the store's name, logout, notification and announcement-dismiss failures. Server messages (`{ error }`, `{ message }`) are shown in the interface language (see i18n: server texts), with an i18n fallback when there is none.
- **Inline:** field validation (`FormField`/`FieldError`, see Form conventions), `InsufficientCreditsNotice` (it has a link), the CSV `rowErrors` table, the error inside `EditProfileModal` (the form stays open), the login error box (blocked account with the admin's reason, the server's "try again later" after too many failed attempts (429); wrong credentials share it), load error states (`LoadErrorState`, empty states), `CreditBanner`, `AnnouncementBanner`, `AccountSetupGate`.
- **No success toast when the screen already shows the result:** a switch flips, an item leaves a list, a notification is marked read or deleted, an announcement is dismissed, logout lands on the login page, a CSV download starts. Failures always show something.
- Tests spy on `toast.success` / `toast.error` and assert that the text is not also rendered inline. `AppToaster.test.tsx` stubs `matchMedia` (jsdom has none; react-hot-toast reads it).

## Form conventions

Every form with input follows the same rules for required fields and errors.

- **Field size on phones.** `inputStyle` (`components/form/FormField`) is `text-base sm:text-sm`: below `sm` field text is 16 px, so iOS does not zoom into a focused field, and a field is 46 px high (with `min-h-11` as a floor: Chromium on Linux draws a native `select` from the font metrics, not the line height, which gave 41 px); from `sm` up it is 14 px and 42 px as before. Every input, select and textarea built from it follows (FormField, `CitySelect`, `DateInput`, `FilterBar`, the sort and radius selects, the modals); the few fields with their own classes (template search, the ConfirmModal reason, the Credits page year) use the same `text-base sm:text-sm`. The FormField icon (`top-3.5 sm:top-3`) and suffix (`top-3 sm:top-2.5`) follow the taller phone field. `e2e/tests/mobile-layout.spec.ts` checks that no field on My profile, Add product or New donation is under 16 px at 375 px.
- **Numeric keyboards.** Number fields keep `type="number"` and add `inputMode`: `decimal` for prices and quantities (quantities accept decimals, 2.5 kg), so the phone shows a number pad with a decimal point; `DateInput` uses `numeric`. The admin's credit adjustment (+5 / -2) has no inputMode, because the number pad has no minus sign.
- **DateInput on phones.** The number pad has no "/", so `formatDateTyping(next, previous)` (`utils/expiry.ts`) shows typed digits as dd/mm/yyyy while typing (`0511` → `05/11/`; a one-digit day or month closed with a slash gets its zero; "." and "-" count as slashes; no slash is added back while deleting), and `parseDisplayDate` also reads eight bare digits (`05112026`). The calendar button covers the right 44 px of the field over its full height (`inset-y-0 right-0 w-11`; the field has `min-h-11 pr-12`).
- **Category buttons** (product and donation forms) are at least 44 px high (`min-h-11`) and their labels wrap to two lines (`break-words leading-tight`) instead of being truncated.

- **Required marker.** Required fields carry a red `*` on their label: `FormField` prop `required` (it also sets `aria-required` on the field), `PickerField` prop `required` for a field that is not one input (category buttons, the CSV file picker), and `FormSection` prop `required` for a section that is one preset choice (donation type, account role, announcement audience). The `*` is CSS (`requiredMark`, `after:content-['*']`), so it is not part of the accessible name. A conditionally required field toggles `required` with the condition (the donation price for a paid donation, each English announcement field once the other is filled, the business fields by role). Each form shows one `RequiredHint` ("Fields marked * are required", key `user.requiredHint`), usually next to the submit button.
- **Error state.** `FormField` prop `error` (a translated message) turns the field red (`invalidStyle`), sets `aria-invalid` and `data-invalid`, and shows `FieldError` below it, linked with `aria-describedby`; the message sits outside the `<label>`, so it stays out of the field's name. `PickerField` gives its group a red outline and the same message. `FormField`'s `icon` is optional for plain fields (the `ConfirmModal` reason, announcements, credit adjustment).
- **When errors show.** `hooks/useFormValidation(errors)` takes a `FieldErrors` map (`utils/validation.ts`: field → i18n key, recomputed from the current values on every render) and returns `formRef`, `errorFor(field)`, `blur(field)`, `validate()` and `reset()`. A field shows its error after it loses focus (`onBlur={blur("name")}`) or after a submit attempt; a fresh form is never red, and an error disappears as soon as the value is valid. Call `reset()` after a form is emptied for a new entry (announcements, change password, a deselected product template).
- **Submit.** Start the submit handler with `if (!validate()) return;`: nothing is sent, and the first element with `data-invalid` in the form (page order) is scrolled into view (the window scrolls, or a scrolling modal body) and focused (for a picker, its first button or input). Submit buttons stay enabled; they are only disabled while a request runs. Forms use `noValidate` and no `required`/`minLength` attributes, so the browser's own bubbles never show; all messages come from `bs.json`/`en.json` (`common.fieldRequired`: "This field is required."). Modals with fields wrap them in a `<form ref={formRef} noValidate>` with a `type="submit"` button, so Enter submits too.
- **Validators** return a per-field map, never a single message: `validateProductForm`, `validateDonationForm`, or a small inline map in the component. The client checks what is required (blank counts as empty) plus cross-field checks it already knew (passwords match, donation price below the value, pickup window order); value rules such as the password length or the email format stay with the server. Server errors are toasts (see Feedback).
- **Required fields** follow the server: product name, category, both prices, quantity, unit, expiry date (description optional); the CSV file; the cart quantity and the order's pickup date and time; donation name, category, value, quantity, unit, last day (+ price when paid); move-to-donations quantity (+ price when paid); profile names (+ business name, city, phone, address for a store or restaurant); current, new and repeated password; the admin's new account email and password, the set-password pair, a reason, a credit adjustment's amount and reason, the Bosnian announcement title and text; the login email and password. The credit decision note, subscription and top-up dialogs have no required input. `RegisterPage` is not routed and keeps its old form.

## E2E tests (`e2e/`)

Playwright tests that drive the built frontend in Chromium against the real API and a real PostgreSQL database. They are a separate package (`e2e/package.json`) with its own database and seed. They complement the Vitest suites rather than replace them: each test covers one complete user flow across both sides.

### Layout

```
e2e/
├── package.json          @playwright/test, @axe-core/playwright, pg, bcryptjs, dotenv, typescript
├── playwright.config.ts  projects, web servers, reporters
├── global-setup.ts       empties the database and seeds it (support/seed.ts)
├── support/
│   ├── accounts.ts       seeded accounts, password, URLs, storageState paths, runId(), uniqueName(prefix)
│   ├── api.ts            API clients and arrange helpers (ok (the body of a successful response, else the test fails with the answer), apiAs, apiLogin, myId, setPin/setPinAs (a pin on the map, or none), createProduct, createDonation, cityId, sendOrder (pickup date and time optional),
│   │                     sendOrderOf (several products), sendDeliveryOrder, acceptOrder (with a ready time for delivery), completeOrder, simulateCourier (the dev-only mock courier route), cancelOrder, orderCode,
│   │                     recordShopSale, setProductPrice, createStoreWithoutPlan)
│   ├── ui.ts             UI helpers (open and reload (page.goto/page.reload after settleOverlays), toast, dialogWith, loginViaForm, submitLoginForm, changeTemporaryPassword,
│   │                     fillProductForm, searchMarketplace, expectNotInMarketplace, emptyCart (the page's session,
│   │                     through the API), addToCart, checkout, sentOrderCode, sentOrderId, orderFromMarketplace (empty
│   │                     cart, one product added, checkout; returns the code), storeOrderCard, pickupCard, credits)
│   ├── seed.ts           the e2e seed
│   ├── db.ts             direct database changes, only for a state the API cannot make: makePickupOverdue(orderId)
```

### Database and environment

The tests use a separate database, `food_saver_e2e_db`. Any database whose name does not end in `_e2e_db` is refused, because the run migrates it and empties every table: `playwright.config.ts` checks it before the web servers start, and the seed checks again. Configuration lives in `e2e/.env.e2e`. Like every `.env*` file it is never committed. Contents:

```
DATABASE_URL=postgres://<user>:<password>@localhost:5432/food_saver_e2e_db
JWT_SECRET=<any test value>
PORT=3100
CLIENT_ORIGIN=http://localhost:4173
TRUST_PROXY=0
DISABLE_RATE_LIMITS=true
EMAIL_PROVIDER=smtp
SMTP_HOST=localhost
SMTP_PORT=1025
MAILPIT_URL=http://localhost:8025
```

- `CLIENT_ORIGIN` must be the preview server's origin. The origin check refuses writes from any other origin.
- The frontend and the API both run on `localhost`, so the `sameSite: "strict"` cookie is sent. Don't mix in `127.0.0.1`.
- The backend web server gets `UPLOADS_DIR=uploads-e2e` from `playwright.config.ts` (not from `.env.e2e`), so its uploaded images stay in `server/uploads-e2e/` and its daily cleanup never touches the dev server's files.
- `DISABLE_RATE_LIMITS=true` turns the server's rate limiters off, as Vitest does with `NODE_ENV=test`. The server logs a warning when it is set. Never set it on a deployment.
- The email lines make the e2e server send every email to Mailpit (SMTP on 1025), and `MAILPIT_URL` is where the tests read them (`support/mailpit.ts`). Mailpit must be running: `docker compose up -d mailpit` from the root, or the `mailpit` binary (see the README). Without the email lines the server falls back to the `log` transport and `order-email.spec.ts` is skipped; the other tests do not need Mailpit. CI runs Mailpit as a service container (`axllent/mailpit:v1.32.0`). Other specs that send orders also send emails to Mailpit; the email test finds its own by the recipient and the unique product name in the message.

### What a run does

1. **Web servers.** Playwright starts these first, before global setup. Both use `reuseExistingServer: false`, so every run builds fresh.
   - **Backend** (`cwd: server/`): `npm run build && npx node-pg-migrate up && node dist/server.js` on port 3100. It gets the `.env.e2e` variables through the environment, and they take precedence over `server/.env`. The migrations run here because global setup runs after the servers start.
   - **Frontend** (`cwd: client/`): `vite build --outDir dist-e2e` with `VITE_API_URL=http://localhost:3100`, then `vite preview` on port 4173. It uses its own output folder, so the normal `dist/` is untouched. Ports 3100 and 4173 don't clash with the dev servers (3000/5173).
2. **Global setup** (`global-setup.ts` → `support/seed.ts`), written with the local seeds' account helpers (`server/src/scripts/seedAccounts.ts`, imported straight from the server's source):
   - It truncates every `public` table except `pgmigrations`, `cities`, `plans` and `topup_packages` (`wipeData`, `RESTART IDENTITY CASCADE`).
   - It then creates, in one transaction:
     - An admin `e2e-admin@josvrijedi.test`.
     - Stores and restaurants with complete profiles (key in `ACCOUNTS` → account):

       | Key | Email | Business | City | Used by |

### Writing tests

#### Arrange through the API, act through the UI

- Data a test needs but does not test (a product to order, a fresh account, a multi-product order or a shop sale that changes the cart while it is open) is created through the API with the helpers in `support/api.ts`. The behaviour under test is clicked through the UI.
  - `apiAs(role)` is an API client with a seeded role's session; `apiLogin(email, password)` logs any account in.
  - An `APIRequestContext` sends no `Origin` or `Referer`, so the server's origin check lets its writes through. If you ever add an `Origin` header, it must be exactly `http://localhost:4173`.
  - The API takes dates as `yyyy-mm-dd` (`isoDate(days)`); the UI's `DateInput` takes `dd/mm/yyyy` (`sarajevoDate(days)`).
- A state the API refuses to make (a pickup day already past) is set in the database with a helper in `support/db.ts`, never with SQL inside a spec. Keep that file to such cases.
- Keep helpers small and shared (`support/api.ts`, `support/ui.ts`, `uniqueName(prefix)`), not a page-object layer.
- Long flows wrap their parts in `test.step()` with short Bosnian names (e.g. `"Prodavnica odbija zahtjev"`), so the report shows where a test failed.
- Credit balances are asserted through the UI, never the database: `availableCredits(page)` and `expectAvailableCredits(page, n)` read "Dostupno" on the Credits page, and the dialogs show `Ovo troši 1 kredit (preostalo: N)`. Read the starting number at run time; the seeded accounts' balances change with every test.
- A test that needs a state the shared seeded accounts lose after one run creates its own account instead. For example, `credits-first-product.spec.ts` needs a store with no plan and gives it one, so it uses `createStoreWithoutPlan()` (a Visoko store with a complete profile and its password changed) rather than a seeded store. The seed runs once per `playwright test`, so a seeded account like that would fail the CI retry and `--repeat-each`.
- A test that blocks or deactivates an account uses its own seeded account (`blockStore`, `branch`), never the shared store and restaurant, and restores it in `test.afterEach` through the API (unblock, reactivate, and complete the accepted pickup it created), so it ends restored even when it fails. The saved sessions work again after a restore, because the block is checked in the database on every request.
- Products get unique names (`uniqueName(prefix)`), and a marketplace search filters by that name, so products from other tests never interfere. CSV fixtures and expiry dates are built at run time relative to today.

#### General

- Navigate with `open(page, url)` and `reload(page)` from `support/ui.ts`, never `page.goto` or `page.reload` directly. A dialog that closes goes back over its own history entry (so the phone's Back closes dialogs, `useOverlay` in the client), and that Back lands a moment later: a navigation started before it is aborted (`net::ERR_ABORTED`), and a link clicked before it is undone. Both helpers first call `settleOverlays(page)`, which waits until the history has no more overlay entries than dialogs are open; call it yourself before clicking a link (the header cart, a notification) right after a dialog closed. `addToCart` already does.

- Wait until a page has loaded its data before typing into a form it fills from the API. `MyProfilePage` overwrites its fields when `GET /users/me` answers, so the test first waits for the read-only Email field to have its value.
- Each test creates its own data with a unique suffix (`runId()`, e.g. product `E2E Mlijeko <id>`, email `e2e-rest-<id>@josvrijedi.test`). Tests never depend on each other or on order. The shared seeded accounts (`store`, `restaurant`) are never blocked and never get a changed profile or password.
- **Locators:**
  - Use `getByRole`, `getByLabel`, `getByText` and `getByPlaceholder` (the filter inputs have no label) with the Bosnian UI. The language is fixed to `bs`.
  - Scope repeated controls: dialogs by `getByRole('dialog', { name })` (or `dialogWith(page, text)` for the dialogs without an accessible name: `SubscribeModal`, `CreditRequestDecisionModal`; the add-to-cart dialog is "Dodaj u korpu" ("Izmijeni količinu u korpi" for a product already in the cart), the other-store question "Isprazniti korpu?"; cart lines are `getByTestId("cart-line")` and the confirmation is the heading "Narudžba #K7PM je poslana"), header and sidebar by `locator('header')` / `locator('aside')`.
  - Toasts are `role="status"` (so is the credit banner), so filter by text: `getByRole('status').filter({ hasText })`.
  - Use `exact: true` when a label is a substring of another (`Ime` / `Prezime`, `Nova lozinka` / `Ponovite novu lozinku`, `Email` / the `Obavijesti emailom` switch on My profile; label matching ignores case).
- **`data-testid` only where roles are ambiguous**, because these cards and rows repeat the same buttons:
  - `product-card` on `DashboardProductCard` (marketplace, dashboard and My products).
  - `order-card` on `OrderCard` (Narudžbe, Moje narudžbe, dashboards, the headquarters' branch page; the heading is the code, so filter by a product: `filter({ hasText: productName })`), `pickup-card` on `PickupCard`, `decision-line` (one item in the store's decision dialog) and `order-item` (a row of the order page's items).
  - `donation-card` on `DonationCard` ("Doniraj hranu").
  - Use them as `getByTestId('product-card').filter({ has: getByRole('heading', { name }) })`.
- **Waiting:**
  - Never use `waitForTimeout`. Rely on auto-waiting and web-first assertions (`toBeVisible`, `toHaveURL`, `toHaveCount`).
  - Notifications and the order pages update live (`/api/events`), and notifications also poll every 50 s. A test may wait for a live change with a web-first assertion, but loading the page that shows it (`goto`, `reload`) stays the most robust.
  - The list filters (name search, radius, city) are debounced by 500 ms, and the list keeps the previous results until the new answer arrives. To check that something is absent, wait for the empty state ("Nema rezultata", see `expectNotInMarketplace`). A bare `toHaveCount(0)` can pass before the search has run.
- **Dates:** `DateInput` fields take `dd/mm/yyyy`. Use `sarajevoDate(days)` and press Enter to commit the value. The product form's expiry has shortcut buttons ("Sutra", "Za 3 dana").

### Running locally

Once:
```bash
psql -U postgres -c "CREATE DATABASE food_saver_e2e_db;"
# create e2e/.env.e2e (see above)
npm run install:all          # root: dependencies of the root, server/, client/ and e2e/
cd e2e && npx playwright install chromium webkit
```

Run a single file (the whole suite runs in CI). Check a new test for flakiness with `--repeat-each=3` before pushing:
```bash
cd e2e
npm run e2e -- tests/order-flow.spec.ts
npm run e2e -- tests/store-chain.spec.ts --repeat-each=3
npm run e2e:ui                       # UI mode, pick tests interactively
npx playwright show-report           # the last run's HTML report
```

Ports 3100 and 4173 must be free, but the normal dev servers can keep running.

**VS Code:** the Playwright Test for VS Code extension finds `e2e/playwright.config.ts` by itself. The tests appear in the Testing view, and a test run from there also runs the `setup` project it depends on. Chromium and WebKit must be installed once (`npx playwright install chromium webkit` in `e2e/`). The extension loads the config from the workspace root, so the config resolves `.env.e2e` and the `.auth/` sessions from its own folder (`import.meta.url`), never from the working directory. Keep it that way for any new file path. Each run builds both sides and reseeds the database, so expect about 15–20 s before the first test starts.

### CI and failed runs

The `E2E` job in `.github/workflows/ci.yml` runs when `server/`, `client/` or `e2e/` changed (or the workflow or root package files):
- It runs a `postgres:15` service with `food_saver_e2e_db` and writes `.env.e2e` with test-only values.
- It runs `npm ci` in all three packages and caches the Chromium and WebKit downloads (`~/.cache/ms-playwright`, keyed by the Playwright version). It installs both with `--with-deps` on a cache miss, and only the system dependencies on a hit.
- It runs `npm run typecheck` and `npm run e2e` in `e2e/`.

On failure, it uploads the `e2e-report` artifact (`playwright-report/` and `test-results/`, kept 14 days). To inspect it:

```bash
gh run download <run-id> -n e2e-report -D e2e-report
npx playwright show-report e2e-report/playwright-report
npx playwright show-trace e2e-report/test-results/<test-folder>/trace.zip
```

Run these from `e2e/` so the local Playwright is used. The trace is recorded on the retry (`on-first-retry`), so it sits in the `-retry1` folder. A trace can also be dropped onto https://trace.playwright.dev.

## Pending and known limitations

- Translate `SponsorPage` when it gets real content, and switch server messages to translated keys once the backend returns them.
- The location map loads OpenStreetMap's public tiles, which their usage policy allows for light use only; a public launch needs a tile provider (or own tiles) and its URL in `LocationMap`.
- Pages without tests yet: EditProduct, EditDonation, ProductDetails, and the Header/Sidebar. Notifications is covered only for its confirmation.
- ESLint covers only `.js` files (in practice just its own config), because `typescript-eslint` does not support TypeScript 7 yet (peer range `<6.1.0`). Add it, or a TS-aware linter such as oxlint, when that changes; the config can then become `eslint.config.ts`.
