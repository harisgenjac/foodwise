# Frontend (`client/`)

Reference for working on the UI. The source of truth is the code; exact route paths are in `src/App.tsx`.

## Stack

- React 19, Vite, TypeScript, Tailwind CSS (core utility classes only), `react-router-dom` 7
- `axios` (one configured instance), `react-hot-toast`, `react-i18next` + `i18next`, `lucide-react` (icons)
- Scripts: `npm run dev` (http://localhost:5173), `npm run build`, `npm run lint`, `npm run preview`, `npm test` (Vitest, once), `npm run test:watch`, `npm run typecheck` (`tsc --noEmit`; Vite does the bundling).
- Env: optional `VITE_API_URL` (backend origin without `/api`, default `http://localhost:3000`), for example in `client/.env.local`.
- `tsconfig`: `strict`, `module esnext`, `moduleResolution bundler`, `jsx react-jsx`, `lib` with `dom`, `types: ["vite/client", "vitest/globals"]`, `verbatimModuleSyntax`, `noEmit`, `include: ["src", "vite.config.ts"]`. Everything is TypeScript (no `allowJs`); the only JS file left is `eslint.config.js` (see Pending).
- `vite.config.ts` holds both the Vite and the Vitest config (`test` block). Its `define` sets `__APP_VERSION__` to `client/package.json`'s `version` at build time (declared in `src/vite-env.d.ts`); the footer shows it, no request needed.

## Routing and layout

- `/login` is wrapped in `PublicRoute` (redirects to `/dashboard` when logged in). `/register` redirects to `/login` with `state.registrationClosed`, which shows an info banner there: an admin creates store, restaurant and admin accounts. `RegisterPage` stays in the code (not routed) for the planned public roles.
- Everything else is nested under `<ProtectedRoute><Layout /></ProtectedRoute>`, so the Header and Sidebar never render before auth is resolved. `/pickups`, `/reports`, `/credits`, the donation pages (`/donate-food`, `/donate-food/new`, `/donate-food/:id/edit`), `/sponsor`, `/products/:id` and `/reservation/:id` are open to both business roles (`<ProtectedRoute role={["STORE", "RESTAURANT"]}>`; the pages adapt to the role), so an admin is sent away from them. `/dashboard`, `/my-profile` and `/notifications` are open to every role; `DashboardPage` redirects an admin to `/admin`, which is also where an admin lands after login. The admin pages use `<ProtectedRoute role="ADMIN">`: `/admin`, `/admin/users`, `/admin/users/new`, `/admin/users/:id`, `/admin/products` (optional `?store_id=`), `/admin/donations` (optional `?donor_id=`), `/admin/reservations` (optional `?user_id=`), `/admin/announcements`, `/admin/actions`, `/admin/credits`, `/admin/credit-requests` (optional `?user_id=`). Role-specific pages are also wrapped in `<ProtectedRoute role="STORE">` (`/add-product`, `/import-products`, `/my-products`, `/edit-product/:id`, `/reservations`) or `<ProtectedRoute role="RESTAURANT">` (`/browse-products`, `/stores`, `/stores/:id`, `/my-reservations`); the wrong role is redirected to `/dashboard`. `Layout` holds `isSidebarOpen` and renders `<NotificationsProvider>` around `<Header />`, `<Sidebar />` and `<main><div className="flex-1"><AnnouncementBanner /><CreditBanner /><AccountSetupGate /><Outlet /></div><Footer /></main>` (`<main>` is a flex column, so the footer sits at the bottom of short pages and after the content of long ones), all inside `<CreditsProvider enabled>` (stores and restaurants whose account is set up). `AnnouncementBanner` (stores and restaurants only) loads `GET /announcements/active` once and shows each as a blue card (`Megaphone`, `role="status"`) in the interface language, falling back to Bosnian when the English title or body is missing; the X hides it at once and sends `POST /announcements/:id/dismiss`. **Account setup lock:** `utils/accountSetup.ts` → `getAccountSetup(user)` returns `{ needsPassword, missingFields, locked }`: `needsPassword` is `must_change_password` (any role), `missingFields` the empty `REQUIRED_PROFILE_FIELDS` (first and last name, business name, city, phone, address; stores and restaurants only). While `locked`: `AccountSetupGate` covers every page except `/my-profile` with a blurred overlay (fixed below the header, `bg-white/40 backdrop-blur-sm`) and a dialog that cannot be dismissed, listing the steps and linking to My profile; on `/my-profile` it shows an amber strip with the same steps instead. The `Sidebar` (`locked`: dimmed, `inert`) and the `Header` (`locked`: toggle, logo link and bell disabled) leave only the profile menu (My profile, logout) and the language switcher usable; `AnnouncementBanner` is hidden; `NotificationsProvider` gets `enabled={false}` while a temporary password is set (the server would answer 403). Saving the profile or the password calls `refreshUser()`, which lifts the lock.
- **Breadcrumbs** (`components/Breadcrumbs`, props `items: { label, to? }[]`, optional `className`) show where a detail page sits in the app, not the browsing history. They start at the sidebar section (labels reuse the `sidebar.*` keys) and have no "Home" item. Only detail pages get them; sidebar pages and create forms (`/add-product`, `/import-products`, `/donate-food/new`, `/admin/users/new`) do not. Each page passes its own items (no route config):
  - `/products/:id`: store `My products › {product}`; restaurant `Browse products › {product}`, or `Stores › {store} › {product}` when the link carries `state={{ fromStore: true }}` (set by the product links on `StoreDetailsPage`; a deep link or reload falls back to Browse products).
  - `/edit-product/:id`: `My products › {product} › Edit`.
  - `/reservation/:id`: `sidebar.reservations` (store) or `sidebar.myReservations` (restaurant) `› Reservation #{id}`, whatever page it was opened from.
  - `/stores/:id`: `Stores › {store}`. `/donate-food/:id/edit`: `Donate food › {donation}` (no donation detail page exists). `/admin/users/:id`: `Users › {accountName}`.

  The trail is rendered at the top of the page content, above the header, in the loading branch (the name is a `BreadcrumbPlaceholder`: a pulsing bar plus a screen-reader "Loading...") and in the not-found branch (only the parent, which stays a link). Markup: `<nav aria-label={t("breadcrumbs.label")}>` with an `<ol>`; every item but the last is a `Link`, the last is text with `aria-current="page"`; `ChevronRight` separators are `aria-hidden`; labels truncate and carry the full name in `title`. Below `sm` only a "‹ {parent}" link is shown. The detail pages no longer have back pills. List filters live in component state, so a breadcrumb back to a list opens it unfiltered.
- **Footer** (`components/Footer`, prop `showImpact`, default true): a slim footer (`max-w-6xl`, `border-t`, `text-sm text-gray-500`) at the end of `<main>` for every role, and at the bottom of the login page's form column with `showImpact={false}` (the endpoint needs a login). Row 1: the impact counter (`Leaf`, `footer.impact`, from `GET /stats/impact` once on mount, rounded to whole kg and formatted for the language: `12.480` in bs, `12,480` in en; hidden at 0 or when the request fails, no toast; `Layout` passes `showImpact={!setup.needsPassword}` because a temporary password gets 403) and the links from `FOOTER_LINKS` (`{ key, to?, href? }`: `to` renders a router `Link`, `href` an `<a>`, neither plain text with no pointer or hover; Contact is `mailto:foodwize@testing.com`, Help, Terms of use and Privacy are text until their pages exist). Row 2 (`text-xs text-gray-400`): `© {year} FoodWise · Još vrijedi` and `v{__APP_VERSION__}`. Below `sm` everything is centred and stacked, the links joined with `·`. Texts: `footer.*`.
- `<main>` is the scroll container (`overflow-y-auto`). To scroll to top use `document.querySelector("main")?.scrollTo({ top: 0, behavior: "smooth" })`, not `window.scrollTo`.

## Auth

`AuthContext` exposes `{ user, loading, login(email, password), logout(), refreshUser() }`. It installs an axios response interceptor: any 401 (except from `/auth/login`) clears `user`, so an expired session sends the user to `/login` instead of leaving a broken page. On mount it calls `GET /users/me` (full profile, not `/auth/me`). The login response has only the basic fields, so `login` calls `refreshUser()` (`GET /users/me`) right after; `MyProfilePage` also calls it after saving the profile or the logo, so the Header and dashboard hero show the current business name and city without a reload. `useAuth()` throws if used outside the provider. The cookie is httpOnly, so the client never touches the token. Role checks in UI use `user?.role === "STORE" | "RESTAURANT" | "ADMIN"`. Login shows a blocked account's server message (403, it includes the admin's reason) instead of the generic error, and the page no longer links to registration (`auth.accountByAdmin` explains that an admin creates accounts).

## Data fetching

- `useFetch<T>(url, dataKey, params)` returns `{ data: T[], total, loading, fetching, error, refetch }`. `dataKey` selects the array from the response (`"products"`, `"reservations"`, `"stores"`); `total` is the response `total` for paginated endpoints (else `null`). The first load starts immediately; later changes of `url` or the filters are debounced by 500ms, while a change of only `limit`/`offset` (Load more, a page number) loads at once; `refetch()` runs immediately. A new request aborts the previous one (`AbortController`), so a slow old response never overwrites newer filters. `loading` is true only until the first response, `fetching` while any request is in flight, `error` after a failed load (pages then show `LoadErrorState`, never a misleading "no results"). Always pass the type argument: `useFetch<Product>("/products/mine", "products", { name, status, category, expiryWithinDays })`.
- `NotificationsContext` (provider in `Layout`) holds one shared notification state, so the Header bell and NotificationsPage stay in sync. `useNotifications()` returns `{ notifications, unreadCount, loading, markAsRead, markAllAsRead, deleteNotification, deleteRead }` and throws outside the provider. It refreshes every 50s and when the window regains focus. Mark/delete update the state optimistically; if the request fails they show the `notifications.actionError` toast and reload from the server; `deleteRead` reloads afterwards because the list is capped at 50. The file also exports the `Notification` interface and `NotificationType` union (keep it in sync with `server/src/utils/notifications.ts`).
- `CreditsContext` (`CreditsProvider` in `Layout`, enabled for set-up stores and restaurants) holds one copy of `GET /credits/me` for the banner, the form hints, My profile and the Credits page, reloaded on every page change and when the window regains focus. `useCredits()` returns `{ credits, loadedAt, refresh }`; outside the provider (admins, isolated tests) `credits` is null and everything credit-related stays hidden.
- Pages that do not use `useFetch` and why: single-record pages (`EditProductPage`, `ProductDetailsPage`, `ReservationDetailsPage`), `StoreDetailsPage` (one request returns store, stats and the caller's reservation count; its products (`/products?store_id=`, the marketplace rules) and its "My reservations" tab use `useFetch`), the dashboards (three parallel fetches into local state: `/dashboard/stats` for the stat cards and two 3-row lists; the restaurant dashboard asks `/products?sort=expiry&limit=3` for its best offers and uses `total` as the offer count), `MyProfilePage`, `AddProductPage` (templates load once into local state).
- **Load more** (card lists): `usePagedLimit(pageSize, resetKey)` → `{ limit, loadMore }`; the page passes `limit` to `useFetch`, `loadMore` raises it by one page, and a new `resetKey` (`JSON.stringify` of the filters) starts from the first page again. Reloading after an action (`refetch()` after accept, reject, cancel, delete, move to donations, reserve) keeps the current `limit`, so the list does not collapse to the first page. `components/LoadMore` (props `shown`, `total`, `fetching`, `onLoadMore`) shows "Showing 12 of 40" (`common.showingOf`) and a "Load more" button (`common.loadMore`, "Loading..." and disabled while fetching), and renders nothing once everything is shown. Count pills use the server `total` (`total ?? data.length`). Used with `CARD_PAGE_SIZE` (12) on BrowseProducts, MyProducts, Reservations, MyReservations (Active; History uses `HISTORY_PAGE_SIZE` = 20), Stores, StoreDetails (both tabs), DonateFood and the Picked up tab of Pickups, and with `LIST_PAGE_SIZE` (10) for the credit requests in `SubscriptionSection`. Admin tables use numbered `Pagination` instead; a page never has both.
- Pattern for typed responses: `const data: Product[] = response.data.products; setList(data);`. Do not wrap an array response in another array.
- Query params are camelCase in state and snake_case on the wire where the backend expects it (`business_name`, `store_id`).

## Types (`types/index.ts`)

`Role`, `User` (`first_name`/`last_name` are `string | null`; `is_blocked`, `blocked_at`, `blocked_reason` only from the admin endpoints), `Product`, `Reservation`, `Favorites`, `DonationOffer` (with `DonationType`), the admin shapes `AdminStats`, `AdminAction` (`AdminActionType`), `AdminUserCounts`, `AdminProduct`, `AdminDonation`, `AdminReservation`, `Announcement`, `AdminAnnouncement` (`AnnouncementAudience`), the credit shapes `Plan`, `TopupPackage`, `CreditSubscription`, `CreditRequest` (`CreditRequestType`, `CreditRequestStatus`; never with the admin note), `CreditSummary` (`GET /credits/me`), `CreditHistory`, `AdminCreditUser`, `AdminCreditRequest`, `CreditTransaction`, and the form states `ProductFormValues` and `DonationFormValues`. Rules: `DECIMAL` columns (`original_price`, `discounted_price`, `quantity`, `available_quantity`) are `string`; ids are `number`; timestamps are ISO `string`s and `expiry_date` is a plain `YYYY-MM-DD` string; on a reservation `discounted_price` is the price agreed when it was made; statuses are literal unions (`Product.status`, `Reservation.status`); fields that only appear through a JOIN or a specific endpoint are optional (`business_name?`, `city?`, `product_name?`, `available_quantity?`, `days_until_expiry?`). For numeric comparison use `parseFloat(p.available_quantity || "0")`. A single object that may not exist is `useState<T | null>(null)`; a list is `useState<T[]>([])`. Single-use shapes stay next to their page or hook (`StoreStats`, `MyReservationsCount` in `StoreDetailsPage`, `Notification` in `NotificationsContext`).

## TypeScript patterns

- `import type { ... }` for type-only imports; local imports end in `.js` even though the files are `.ts`/`.tsx`.
- Inline handlers need no annotations (`onChange={(e) => setName(e.target.value)}`). A standalone handler does, for example `(e: React.ChangeEvent<HTMLInputElement>)`. For form submit use `React.SyntheticEvent<HTMLFormElement>` (`FormEvent` is deprecated in current `@types/react`).
- Props are typed with an interface or inline object: `({ children }: { children: React.ReactNode })`.
- Non-null assertion only where the app guarantees it: `useParams()` id inside a route that requires it, `document.getElementById("root")!`, `selectedProduct!` inside a handler that only runs with the modal open.
- `catch (err)`: use `axios.isAxiosError(err) ? err.response?.data?.error : null`, then fall back to a `t()` message. Server-provided messages are English (backend rule) and are shown as-is, in either UI language.
- Optional values used as an object key need a fallback: `categories[reservation.category || ""]`.

## Confirmations

- **When to ask.** Confirm an action that cannot be undone, notifies another party, or spends credits in bulk: accepting, rejecting or cancelling a reservation, a pickup or a missed pickup, deleting a product, the CSV import, "Delete read" notifications, withdrawing an automatic renewal request, and the admin's block, unblock, removals, reservation cancels and announcements. Do not ask for easily reversible actions (favorites, mark as read, deleting one notification, the auto-renew switch, withdrawing a request the user sent, a product template, which has its own two-step inline delete): dialogs shown too often get clicked blindly. ## Feedback

Every message is shown in exactly one place: a toast or inline, never both.

- **Toaster.** `components/AppToaster` (rendered once in `main.tsx`) wraps react-hot-toast's `Toaster`: top right, 5000 ms for every type (set in `toastOptions`; calls pass no `duration`), at most 3 visible (an effect on `useToasterStore()` dismisses older ones), a close button on each toast (`ToastBar` render with `toast.dismiss`, `aria-label` from `common.closeToast`), pause on hover (the default), full width at the top below `sm`, `z-index` 9999 so toasts sit above modals (`z-50`) and may overlap the header.
- **Toast:** a one-time success, and a one-sentence action error the user does not fix in a form field: form submit errors from the server (product add/edit, donation add/edit, My profile, logo upload, password change, admin create user, announcement send, CSV import summary), errors of actions in lists and modals (reserve, move to donations, credit requests, admin decisions, block/unblock, set password, credit adjustment, delete/cancel/accept/reject, favorites), logout, notification and announcement-dismiss failures. Server messages (`{ error }`, `{ message }`) are shown in the interface language (see i18n: server texts), with an i18n fallback when there is none.
- **Inline:** field validation (`FormField`/`FieldError`, see Form conventions), `InsufficientCreditsNotice` (it has a link), the CSV `rowErrors` table, the error inside `EditProfileModal` (the form stays open), the login error box (blocked account with the admin's reason; wrong credentials share it), load error states (`LoadErrorState`, empty states), `CreditBanner`, `AnnouncementBanner`, `AccountSetupGate`.
- **No success toast when the screen already shows the result:** a switch or the favorite heart flips, an item leaves a list, a notification is marked read or deleted, an announcement is dismissed, logout lands on the login page, a CSV download starts. Failures always show something.
- Tests spy on `toast.success` / `toast.error` and assert that the text is not also rendered inline. `AppToaster.test.tsx` stubs `matchMedia` (jsdom has none; react-hot-toast reads it).

## Form conventions

Every form with input follows the same rules for required fields and errors.

- **Required marker.** Required fields carry a red `*` on their label: `FormField` prop `required` (it also sets `aria-required` on the field), `PickerField` prop `required` for a field that is not one input (category buttons, the CSV file picker), and `FormSection` prop `required` for a section that is one preset choice (donation type, account role, announcement audience). The `*` is CSS (`requiredMark`, `after:content-['*']`), so it is not part of the accessible name. A conditionally required field toggles `required` with the condition (the donation price for a paid donation, each English announcement field once the other is filled, the business fields by role). Each form shows one `RequiredHint` ("Fields marked * are required", key `user.requiredHint`), usually next to the submit button.
- **Error state.** `FormField` prop `error` (a translated message) turns the field red (`invalidStyle`), sets `aria-invalid` and `data-invalid`, and shows `FieldError` below it, linked with `aria-describedby`; the message sits outside the `<label>`, so it stays out of the field's name. `PickerField` gives its group a red outline and the same message. `FormField`'s `icon` is optional for plain fields (the `ConfirmModal` reason, announcements, credit adjustment).
- **When errors show.** `hooks/useFormValidation(errors)` takes a `FieldErrors` map (`utils/validation.ts`: field → i18n key, recomputed from the current values on every render) and returns `formRef`, `errorFor(field)`, `blur(field)`, `validate()` and `reset()`. A field shows its error after it loses focus (`onBlur={blur("name")}`) or after a submit attempt; a fresh form is never red, and an error disappears as soon as the value is valid. Call `reset()` after a form is emptied for a new entry (announcements, change password, a deselected product template).
- **Submit.** Start the submit handler with `if (!validate()) return;`: nothing is sent, and the first element with `data-invalid` in the form (page order) is scrolled into view (`<main>` is the scroll container) and focused (for a picker, its first button or input). Submit buttons stay enabled; they are only disabled while a request runs. Forms use `noValidate` and no `required`/`minLength` attributes, so the browser's own bubbles never show; all messages come from `bs.json`/`en.json` (`common.fieldRequired`: "This field is required."). Modals with fields wrap them in a `<form ref={formRef} noValidate>` with a `type="submit"` button, so Enter submits too.
- **Validators** return a per-field map, never a single message: `validateProductForm`, `validateDonationForm`, or a small inline map in the component. The client checks what is required (blank counts as empty) plus cross-field checks it already knew (passwords match, donation price below the value, pickup window order); value rules such as the password length or the email format stay with the server. Server errors are toasts (see Feedback).
- **Required fields** follow the server: product name, category, both prices, quantity, unit, expiry date (description optional); the CSV file; reservation quantity and pickup date; donation name, category, value, quantity, unit, last day (+ price when paid); move-to-donations quantity (+ price when paid); profile names (+ business name, city, phone, address for a store or restaurant); current, new and repeated password; the admin's new account email and password, the set-password pair, a reason, a credit adjustment's amount and reason, the Bosnian announcement title and text; the login email and password. The credit decision note, subscription and top-up dialogs have no required input. `RegisterPage` is not routed and keeps its old form.
