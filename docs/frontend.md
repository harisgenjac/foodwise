# Frontend (`client/`)

Reference for working on the UI. The source of truth is the code; exact route paths are in `src/App.tsx`.

## Stack

- React 19, Vite, TypeScript, Tailwind CSS (core utility classes only), `react-router-dom` 7
- `axios` (one configured instance), `react-hot-toast`, `react-i18next` + `i18next`, `lucide-react` (icons)
- Scripts: `npm run dev` (http://localhost:5173), `npm run build`, `npm run lint`, `npm run preview`, `npm test` (Vitest, once), `npm run test:watch`, `npm run typecheck` (`tsc --noEmit`; Vite does the bundling).
- Env: optional `VITE_API_URL` (backend origin without `/api`, default `http://localhost:3000`), for example in `client/.env.local`.
- `tsconfig`: `strict`, `module esnext`, `moduleResolution bundler`, `jsx react-jsx`, `lib` with `dom`, `types: ["vite/client", "vitest/globals"]`, `verbatimModuleSyntax`, `noEmit`, `include: ["src", "vite.config.ts"]`. Everything is TypeScript (no `allowJs`); the only JS file left is `eslint.config.js` (see Pending).
- `vite.config.ts` holds both the Vite and the Vitest config (`test` block).

## Auth

`AuthContext` exposes `{ user, loading, login(email, password), logout(), refreshUser() }`. It installs an axios response interceptor: any 401 (except from `/auth/login`) clears `user`, so an expired session sends the user to `/login` instead of leaving a broken page. On mount it calls `GET /users/me` (full profile, not `/auth/me`). The login response has only the basic fields, so `login` calls `refreshUser()` (`GET /users/me`) right after; `MyProfilePage` also calls it after saving the profile or the logo, so the Header and dashboard hero show the current business name and city without a reload. `useAuth()` throws if used outside the provider. The cookie is httpOnly, so the client never touches the token. Role checks in UI use `user?.role === "STORE" | "RESTAURANT"`.

## Data fetching

- `useFetch<T>(url, dataKey, params)` returns `{ data: T[], total, loading, fetching, error, refetch }`. `dataKey` selects the array from the response (`"products"`, `"reservations"`, `"stores"`); `total` is the response `total` for paginated endpoints (else `null`). The first load starts immediately; later changes of `url` or `JSON.stringify(params)` are debounced by 500ms; `refetch()` runs immediately. A new request aborts the previous one (`AbortController`), so a slow old response never overwrites newer filters. `loading` is true only until the first response, `fetching` while any request is in flight, `error` after a failed load (pages then show `LoadErrorState`, never a misleading "no results"). Always pass the type argument: `useFetch<Product>("/products/mine", "products", { name, status, category, expiryWithinDays })`.
- `NotificationsContext` (provider in `Layout`) holds one shared notification state, so the Header bell and NotificationsPage stay in sync. `useNotifications()` returns `{ notifications, unreadCount, loading, markAsRead, markAllAsRead, deleteNotification, deleteRead }` and throws outside the provider. It refreshes every 50s and when the window regains focus. Mark/delete update the state optimistically and reload from the server if the request fails; `deleteRead` reloads afterwards because the list is capped at 50. The file also exports the `Notification` interface and `NotificationType` union (keep it in sync with `server/src/utils/notifications.ts`).
- Pages that do not use `useFetch` and why: single-record pages (`EditProductPage`, `ProductDetailsPage`, `ReservationDetailsPage`), `StoreDetailsPage` (one request returns store, products, stats and the caller's reservation count; only its "My reservations" tab uses `useFetch`), the dashboards (two parallel fetches into local state; the restaurant dashboard asks `/products?sort=expiry&limit=3` for its best offers and uses `total` as the offer count), `MyProfilePage`, `AddProductPage` (templates load once into local state).
- Pattern for typed responses: `const data: Product[] = response.data.products; setList(data);`. Do not wrap an array response in another array.
- Query params are camelCase in state and snake_case on the wire where the backend expects it (`business_name`, `store_id`).

## Types (`types/index.ts`)

`User`, `Product`, `Reservation`, `Favorites`. Rules: `DECIMAL` columns (`original_price`, `discounted_price`, `quantity`, `available_quantity`) are `string`; ids are `number`; timestamps are ISO `string`s and `expiry_date` is a plain `YYYY-MM-DD` string; on a reservation `discounted_price` is the price agreed when it was made; statuses are literal unions (`Product.status`, `Reservation.status`); fields that only appear through a JOIN or a specific endpoint are optional (`business_name?`, `city?`, `product_name?`, `available_quantity?`, `days_until_expiry?`). For numeric comparison use `parseFloat(p.available_quantity || "0")`. A single object that may not exist is `useState<T | null>(null)`; a list is `useState<T[]>([])`. Single-use shapes stay next to their page or hook (`StoreStats`, `MyReservationsCount` in `StoreDetailsPage`, `Notification` in `NotificationsContext`).

## TypeScript patterns

- `import type { ... }` for type-only imports; local imports end in `.js` even though the files are `.ts`/`.tsx`.
- Inline handlers need no annotations (`onChange={(e) => setName(e.target.value)}`). A standalone handler does, for example `(e: React.ChangeEvent<HTMLInputElement>)`. For form submit use `React.SyntheticEvent<HTMLFormElement>` (`FormEvent` is deprecated in current `@types/react`).
- Props are typed with an interface or inline object: `({ children }: { children: React.ReactNode })`.
- Non-null assertion only where the app guarantees it: `useParams()` id inside a route that requires it, `document.getElementById("root")!`, `selectedProduct!` inside a handler that only runs with the modal open.
- `catch (err)`: use `axios.isAxiosError(err) ? err.response?.data?.error : null`, then fall back to a `t()` message. Server-provided messages are Bosnian and are shown as-is for now.
- Optional values used as an object key need a fallback: `categories[reservation.category || ""]`.

## i18n

- Config: `resources: { bs, en }` under the `translation` namespace, `lng: "bs"`, `fallbackLng: "bs"`, `interpolation.escapeValue: false`. `LanguageSwitcher` is a dropdown with flag images from `flagcdn.com` (emoji flags do not render on Windows) and is used in the Header and on the login/register pages.
- Key sections in both JSON files: `common` (loading and load-error texts), `sidebar`, `header`, `auth`, `product`, `user`, `dashboard`, `filters`, `productStatus`, `reservationStatus`, `categories`, `units`, `myProducts`, `reservations`, `myReservations`, `notifications`, `store`, `templates`.
- Notification text comes from `notifications.types.<TYPE>` with `{{product}}`, `{{quantity}}`, `{{unit}}` (raw unit code, e.g. `kg`); `getNotificationText` falls back to the server's English `message` when the type or product name is missing. Pluralized count: `notifications.unreadCount` (`_one`/`_few`/`_other` in bs, `_one`/`_other` in en). Day groups: `notifications.groups.today|yesterday|earlier`. Relative time (`formatRelativeTime`) uses `notifications.time.*` plural keys rather than `Intl.RelativeTimeFormat`, which Chrome does not translate to Bosnian; older than 7 days shows the date.
- Same key name in different sections is fine (`product.editTitle`, `user.editTitle`). Reuse an existing key rather than duplicating it. Add a shared `common` section only when a string is repeated in many places.
- Categories, units and statuses are objects: `const categories = t("categories", { returnObjects: true }) as Record<string, string>;` then `categories[product.category] || product.category`. Same for `units`, `productStatus`, `reservationStatus`. Dropdown options come from `Object.entries(categories)`.
- Interpolating `t()` inside a template string needs `${}`: `` `${t("myReservations.placeholderMax")}: ${max}` ``.
- Some existing keys contain typos (`noNofiticationsTitle`, `addFavoriteSucces`, `deleteFavoriteSucces`). They are consistent across both JSON files and the code; renaming one means changing both files and every usage together.
- Raw codes that need no translation stay as they are (the unit code in the reservation modal label). `CATEGORY_IMAGES` is language-neutral and stays.
- `utils/categories.ts` and `utils/units.ts` still hold the old Bosnian label maps; the UI no longer reads them for display, but the keys mirror the backend codes.
- `DonateFoodPage` and `SponsorPage` are not translated yet. A few placeholders and fallback strings may still be hard-coded Bosnian; grep when touching a page.

## UI conventions

- Visual language: orange primary (`orange-500/600`, hover one step darker), gray neutrals, green for prices and confirm actions, red for delete/reject, white cards with `shadow` and `rounded-xl`, page container `max-w-5xl mx-auto`, card grids `grid-cols-1 md:grid-cols-3 gap-8`.
- Icons come from `lucide-react` (`strokeWidth={1.8}` in navigation). Do not add inline SVGs or emoji icons to the navigation.
- Reservation status pills use `RESERVATION_STATUS_STYLES` from `utils/reservationStatus.ts` (Pending amber, Confirmed green, Completed gray, Rejected and Cancelled red).
- StoresPage (`/stores`, restaurant): `ProductPageHeader` (store icon, `store.count`), a 3-column `FilterBar` (store name, city, and a "Favorites only" toggle button with the favorites count; "Clear filters" also turns the toggle off), a `StoreCard` grid and three empty states (no stores, no results, no favorites). `StoreCard`: soft orange gradient banner with a `FavoriteButton` (heart, icon variant, `stopPropagation`), `StoreAvatar` (logo or initials of the business name, falls back to initials if the image fails) overlapping the banner, name, city, a pill with `active_products` (`store.activeOffers`, green) or "No offers right now", the description or `store.noDescription`, a `bg-gray-50` list (address, opening hours, phone with icons) and a "View offers" button. The whole card links to `/stores/:id`.
- StoreDetailsPage (`/stores/:id`, restaurant): back pill; a profile-style hero (gradient banner, large `StoreAvatar`, name, store role pill, city, `FavoriteButton` pill variant "Add to favorites" / "In favorites", description); then a contact card (`DetailItem`s: address + city, phone as `tel:`, opening hours, pickup hours) next to four `StatCard`s (active products, sold, successful deliveries, your reservations here). Pill tabs Products (count) / My reservations. Products use `DashboardProductCard` with Details + Reserve (only with stock); reserving opens `ReserveProductModal` and then reloads the store and the reservations. My reservations has status pill filters (All + the four statuses) and a `DashboardReservationCard` grid. Each part has an `EmptyState`; a missing store shows one linking to `/stores`.
- `components/product/ReserveProductModal` (props `product`, optional `storeLine`, `onClose`, `onReserved`) is the single reservation form (product summary, quantity with unit suffix, pickup date and time limited to today .. the expiry day, `POST /reservations`, toasts; the confirm button is disabled while the request runs), used by BrowseProducts, ProductDetails and StoreDetails. Accept/Reject (`ReservationsPage`), Cancel (`MyReservationsPage`) and the product forms are guarded the same way, so a double click sends one request.
- Login and Register keep the split layout (photo with brand on the left from `lg`, form on the right with `LanguageSwitcher`); the form card is `rounded-2xl border shadow-sm`, inputs use `FormField` + `inputStyle` with icons, and Register picks the role with two icon cards (`Store`, `UtensilsCrossed`).
- Product and reservation cards: 144px image area (`h-36`) on top with a status or category badge in the corner (`absolute top-3 right-3 bg-white/90 text-xs font-semibold px-2 py-1 rounded-full`), then title, description, details block, action buttons pinned to the bottom (`mt-auto`).
- Whole-card click navigates to the details page. Buttons inside a clickable card call `e.stopPropagation()`. Clickable elements carry `cursor-pointer`.
- Lists have a filter bar (text inputs plus selects). Text search is debounced through `useFetch`.
- Empty states distinguish "nothing exists yet" from "no results for these filters" using `hasActiveFilters`; the first can include a call to action, the second only suggests changing filters.
- Loading: `if (loading) return <LoadingSpinner />` (orange spinner with vertical padding inside `<main>`; `ProtectedRoute` and `PublicRoute` use `<LoadingSpinner fullScreen />` while auth resolves). Success and error feedback uses `react-hot-toast` (`toast.success`, `toast.error`); profile and form pages also show inline error and success banners.
- Confirm dialogs and reservation dialogs are fixed overlay modals driven by `selectedProduct` (or a boolean on single-record pages).
- Tabs (`StoreDetailsPage`, `NotificationsPage`): pill group in a white rounded-full container, the active tab is `bg-orange-500 text-white` with an optional count bubble; content blocks render conditionally.
- Images: `CATEGORY_IMAGES[category] || CATEGORY_IMAGES.Other` (one Unsplash photo per category key, including `Fish` and `Frozen Food`) for products and for reservations (by the reserved product's category); it lives in `utils/categoryImages.ts`. Store and user logos come from the backend `logo_url`, built with `assetUrl(logo_url)`, with initials as the fallback (`StoreAvatar` for stores). Never hotlink images from Google, Amazon or stock-photo sites; use Unsplash or a fallback.
- Prices are shown in KM.
- Tailwind classes must be written in full (no string-built class names). A modifier such as `hover:` must be attached to the class with no space.

## Testing

- Vitest + Testing Library (`@testing-library/react`, `user-event`, `jest-dom`) in `jsdom`. Test files sit next to the code as `*.test.ts(x)`; `globals: true`, so `describe`/`it`/`expect`/`vi` need no import.
- `src/test/setup.ts` runs before every file:
  - It mocks `api/axios.js` for all tests (`get`, `post`, `put`, `patch`, `delete` and `interceptors.response.use/eject` are `vi.fn()`; `API_ORIGIN` and `assetUrl` are plain values), so no test reaches the server.
  - It raises the async timeout to 3s, because `useFetch` debounces filter changes by 500ms.
  - After each test it resets mocks, restores spies and switches the language back to `bs`.
- `src/test/utils.tsx`:
  - `apiMock`: the typed mocked instance.
  - `mockGet({ url: response })` answers `api.get` by URL; a value becomes `data`, an `Error` is thrown, and a function receives the query params.
  - `axiosError(status, error)` builds a rejection shaped like the server's `{ error }`.
  - `renderWithProviders(ui, { route, path, user, get })` renders inside the real `AuthProvider` and a `MemoryRouter`. `user` is what `/users/me` returns (null means 401). Any other path renders `LocationDisplay` (`data-testid="location"`), so redirects and navigation can be asserted.
  - `t`: the real i18n `t`. Build expected texts from keys instead of copying strings.
  - `makeUser`, `makeProduct`, `makeReservation`, `makeNotification`: fixtures that take overrides.
- Conventions:
  - Query by role and label (`FormField` wraps its input in a `<label>`; labels with a suffix such as "KM" need `{ exact: false }`).
  - Spy on `toast.success`/`toast.error` to check feedback.
  - Faking `setInterval` blocks `waitFor`, so for intervals spy on `window.setInterval` instead.
